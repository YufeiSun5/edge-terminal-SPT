# 后端原始数据到清洗数据之间缺口

本文描述当前边缘端后端从 MQTT/KIO 原始数据接入，到后续“清洗后数据”之间还缺哪些层。

当前阶段已经完成的是底层接入与变量识别，不包含正式采集存储、清洗、防抖、检测业务、热冲裁业务。

## 2. 从原始数据到清洗数据之间缺的层

当前数据链路是：

```text
MQTT消息
  -> KIO解析
  -> 原始变量 sys_tags
  -> 内存实时值 TagManager
```

要进入清洗后数据，至少还需要补成：

```text
MQTT消息
  -> 原始解析 Raw Ingest
  -> 原始变量状态 Raw State
  -> 清洗规则 Clean Rule
  -> 清洗执行 Clean Worker
  -> 清洗后变量 Clean Variable / Clean State
  -> 检测开始后按任务存储
```

## 3. 缺口一：原始数据层还没有正式建模

现在 `sys_tags` 同时承担了：

- 原始变量定义
- 展示变量名
- 部分属性配置
- 存储策略字段
- 设备绑定字段

这在快速验证阶段可以，但进入清洗前建议拆清楚。

建议底层概念：

```text
数据源 Source/Gateway
  -> 原始变量 RawVariable
      -> 原始实时状态 RawState
```

当前 `sys_tags` 可以暂时继续当 `RawVariable` 使用，但后续要明确：

- `gateway_id + source_path` 是原始变量唯一键
- `raw_name` 是上位机原始变量名
- `var_name` 是系统内部变量名
- `display_name` 是前端展示名
- `display_name` 保留为中文/默认显示名
- `display_name_en` 是英文显示名，由用户维护
- `display_name_ja` 是日文显示名，由用户维护
- `store_mode` 只表示怎么存，例如变化存、周期存、变化+周期都存
- `store_trigger` 表示什么时候允许存：
  - `always`：保留原来的持续存储方式
  - `on_detection`：默认方式，平时不存，检测/任务通知后才存
- 清洗后的变量不应该直接覆盖原始变量

## 4. 缺口二：清洗规则表还没有

需要一张或多张清洗规则表，用于定义变量如何从原始值变成可用值。

建议表：`sys_clean_rules`

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `source_var_id` | 原始变量 ID |
| `target_code` | 清洗后变量编码 |
| `target_name` | 清洗后变量名称 |
| `data_type` | 清洗后数据类型 |
| `enabled` | 是否启用 |
| `rule_type` | 规则类型 |
| `zero_debounce_enabled` | 是否启用 0 值防抖 |
| `zero_hold_ms` | 0 值观察窗口 |
| `deadband` | 数值死区 |
| `min_value` | 最小有效值 |
| `max_value` | 最大有效值 |
| `expression` | 表达式或映射规则 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

当前先不要做复杂表达式引擎，可以先支持几类固定规则：

- `pass_through`：原样通过
- `deadband`：死区过滤
- `zero_debounce`：0 值防抖
- `range_limit`：上下限过滤
- `bool_map`：布尔/枚举映射

## 5. 缺口三：清洗后的变量状态还没有

现在只有原始实时状态，没有清洗后状态。

建议新增内存结构：

```go
cleanStateByID map[CleanVarID]*CleanState
```

`CleanState` 至少包含：

- 清洗后值
- 原始值
- 原始更新时间
- 清洗更新时间
- 质量状态
- 是否被过滤
- 最后一次过滤原因

建议质量状态：

```text
good
bad_quality
filtered_zero_debounce
filtered_deadband
filtered_range
stale
no_source
```

## 6. 缺口四：清洗执行器还没有

现在 MQTT 消息进入后直接更新 `TagManager`。

后续需要在原始值更新后触发清洗执行：

```text
原始变量更新
  -> 找到引用该原始变量的清洗规则
  -> 执行规则
  -> 更新清洗后状态
  -> 如果检测任务正在运行，再进入存储队列
```

建议新增：

- `CleanRuleManager`
- `CleanStateManager`
- `CleanWorker`

注意：清洗执行不应该阻塞 MQTT 回调。

## 7. 缺口五：0 值防抖策略还没有

上位机第一次全量快照可能所有数据为 0，这个问题不应该在变量发现层处理。

建议在清洗层处理：

```text
如果变量启用 0 值防抖：
  1. 收到 0，不立即更新清洗后值
  2. 进入观察窗口
  3. 如果窗口内恢复非 0，则丢弃这个 0
  4. 如果窗口超时仍为 0，则确认更新为 0
```

需要注意：

- 有些变量 0 是合法值，不能全局过滤
- 防抖必须按变量配置
- 第一次快照是否参与清洗，要由规则决定

## 8. 缺口六：清洗后数据存储策略还没有定

当前已有检测任务和历史表雏形，但正式逻辑还没有进入清洗层。

用户需求是：

```text
平时数据只更新实时值，不存库。
只有开始检测信号来了，才开始存储。
```

因此后续存储入口应从“清洗后状态”进入，而不是直接从原始变量进入：

```text
CleanState 更新
  -> 判断是否有运行中的检测任务
  -> 判断变量是否属于该任务/工程
  -> 写入历史数据
```

暂时不要把原始 MQTT 推送全部落库。

## 9. 缺口七：内部变量还没有正式定义

已经讨论过，检测开始信号可能来自：

- MQTT 原始变量
- KIO 写入返回
- 系统内部变量
- 前端手动操作

当前还没有内部变量表。

建议后续新增：

```text
sys_internal_variables
```

用于表达：

- 几号机器开始检测
- 当前检测状态
- 当前任务编号
- 人工强制状态

内部变量应该和 MQTT 原始变量一样，可以被任务系统引用。

## 10. 缺口八：工程/检测对象绑定还没有

现在仍然有 `sys_devices`，但我们已经倾向把“设备层”虚拟化为工程/检测对象。

后续至少需要明确：

```text
工程/检测对象
  -> 引用哪些原始变量
  -> 引用哪些清洗后变量
  -> 哪个变量表示开始检测
  -> 哪个变量表示停止检测
```

建议先不要急着改名，短期可以继续用 `sys_devices` 承载虚拟对象，等模型稳定后再迁移为 `sys_projects` 或 `sys_detection_units`。

## 11. 设想：业务模块由变量变动触发

后续业务不建议写死在 MQTT 解析层，也不建议让清洗层直接知道热冲裁业务。

建议增加独立业务模块层：

```text
RawState 更新
  -> CleanWorker 清洗
  -> CleanState 更新
  -> Business Dispatcher
  -> 业务模块代码
  -> 存储 / 质量判定 / 状态更新
```

业务模块可以是固定注册的 Go 模块，例如：

```text
business/
  detection/
  hot_punching/
  quality/
```

每个业务模块只关心清洗后的变量和业务配置，不直接解析 MQTT。

### 11.1 业务模块的触发方式

业务模块应由“变量变动事件”触发，而不是定时扫全表。

建议事件结构：

```text
VariableChangedEvent
  - source_var_id
  - clean_var_id
  - project_id / detection_unit_id
  - old_value
  - new_value
  - quality
  - changed_at
  - change_reason
```

触发过程：

```text
清洗后变量发生有效变化
  -> 生成 VariableChangedEvent
  -> 根据变量绑定关系找到订阅它的业务模块
  -> 调用业务模块 Handle(event)
```

这样可以支持：

- 某个变量触发开始检测
- 某个变量触发停止检测
- 某组变量触发质量判定
- 某个状态变量触发报警或任务切换

### 11.2 业务模块负责存储与质量判定

用户需求是平时不存，检测开始后才存。

因此建议存储逻辑不放在 MQTT 层，也不直接放在清洗层，而是由业务模块判断：

```text
业务模块收到变量变化
  -> 判断当前工程/检测对象是否处于检测中
  -> 判断该变量是否属于本次检测
  -> 判断是否满足质量判定逻辑
  -> 决定是否写历史数据
  -> 更新检测过程状态 / 质量状态
```

质量判定也应在业务模块中完成，而不是在变量清洗中完成。

清洗层只回答：

```text
这个值是否可信、是否应该更新、清洗后的值是多少
```

业务层回答：

```text
这个值对当前检测业务意味着什么
是否要存
是否合格
是否触发状态变化
```

### 11.3 业务模块需要的配置

后续需要增加业务配置表，描述业务模块订阅哪些变量，以及变量在业务中的角色。

示例：

```text
sys_business_modules
sys_business_bindings
sys_business_rules
```

其中 `sys_business_bindings` 可以表达：

| 字段 | 说明 |
|---|---|
| `business_code` | 业务模块编码，例如 `hot_punching` |
| `project_id` | 工程/检测对象 |
| `clean_var_id` | 清洗后变量 |
| `role` | 变量角色，例如 `start_signal`、`stop_signal`、`pressure`、`temperature` |
| `enabled` | 是否启用 |

短期可以不急着拆这么细，但设计上要留出这个方向。

## 12. 设想：配置变更后需要热重载

当前后端启动时会加载：

- 网关配置
- 变量配置
- 已启用变量
- 检测任务

后续增加清洗规则和业务模块后，配置会变多。如果前端修改了这些配置，后端不能继续使用旧内存配置。

因此需要设计统一热重载机制。

### 12.1 哪些表变更需要热重载

至少包括：

- `sys_gateways`
- `sys_tags`
- 清洗规则表，例如 `sys_clean_rules`
- 清洗后变量表，例如 `sys_clean_variables`
- 变量绑定表，例如 `sys_project_variable_bindings`
- 业务模块配置表，例如 `sys_business_modules`
- 业务变量绑定表，例如 `sys_business_bindings`
- 质量规则表，例如 `sys_quality_rules`

### 12.2 热重载应该做什么

热重载不是重启整个服务，而是重新加载运行时配置。

建议拆成几个 reload 单元：

```text
ReloadGateways
  -> 重启变更的 MQTT 连接

ReloadRawVariables
  -> 重建 TagManager

ReloadCleanRules
  -> 重建 CleanRuleManager

ReloadBusinessBindings
  -> 重建 Business Dispatcher 路由

ReloadQualityRules
  -> 重建质量判定规则
```

变更示例：

```text
前端修改变量属性
  -> 更新 sys_tags
  -> 调用 RuntimeReloader.ReloadRawVariables()
  -> 后续变量更新使用新配置
```

```text
前端修改清洗规则
  -> 更新 sys_clean_rules
  -> 调用 RuntimeReloader.ReloadCleanRules()
  -> 后续清洗使用新规则
```

```text
前端修改网关配置
  -> 更新 sys_gateways
  -> 调用 RuntimeReloader.ReloadGateways()
  -> 对应 MQTT 连接重新启动
```

### 12.3 热重载接口

前端正常编辑接口可以自动触发热重载，不一定要求用户点按钮。

但建议保留一个维护接口：

```text
POST /api/v1/runtime/reload
```

请求示例：

```json
{
  "scope": "all"
}
```

可选 scope：

```text
all
gateways
raw_variables
clean_rules
business
quality
```

用于现场维护时手动重新加载。

### 12.4 热重载和正在运行任务的关系

如果检测任务正在运行，热重载要谨慎。

建议规则：

- 修改显示名、单位、小数位，可以热重载。
- 修改变量绑定、清洗规则、质量规则时，需要记录版本。
- 正在运行的检测任务应绑定配置版本，避免检测过程中规则变化导致前后数据口径不一致。

后续可以增加：

```text
config_version
rule_version
task_config_snapshot
```

短期可以先做到“运行时重新加载”，后续再补版本化。

## 13. 建议的整体运行链路

结合业务模块和热重载后，目标链路应是：

```text
MQTT Gateway
  -> Parser Strategy(KIO)
  -> RawVariable / RawState
  -> CleanRuleManager
  -> CleanWorker
  -> CleanState
  -> Business Dispatcher
  -> Business Module
      -> 检测状态
      -> 质量判定
      -> 按需存储
```

配置变更链路应是：

```text
前端配置页面
  -> 更新数据库配置表
  -> RuntimeReloader
  -> 重建对应内存配置
  -> 后续数据按新配置运行
```

这个设计的核心是：

```text
解析层只负责把外部数据变成原始变量
清洗层只负责把原始变量变成可信变量
业务层只负责解释变量变化并决定业务动作
热重载层负责让数据库配置变更及时进入运行时
```

## 15. 下一阶段建议顺序

建议不要直接做热冲裁业务，先按以下顺序补：

1. 稳定站点配置与变量发现页面
2. 明确 `sys_tags` 是否暂时作为原始变量表
3. 设计清洗规则表 `sys_clean_rules`
4. 实现清洗后实时状态 `CleanStateManager`
5. 实现 0 值防抖和死区过滤
6. 增加 `RuntimeReloader`，让变量表、网关表、清洗表、业务绑定表变更后能热重载
7. 增加变量变动事件和 `Business Dispatcher`
8. 再接检测开始信号和任务系统
9. 最后进入热冲裁业务模型
