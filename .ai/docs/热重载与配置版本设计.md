# 热重载与配置版本设计

本文记录边缘端后续热重载机制的设计思路，供后续实现参考。

当前系统已经有局部立即重载，但还没有完整的版本化热重载体系。

## 1. 当前已经具备的局部重载

当前不是通过版本号触发，而是在接口更新成功后直接调用对应运行时重载逻辑。

### 1.1 网关配置重载

当前流程：

```text
PATCH /api/v1/gateway-configs/:id
  -> 更新 sys_gateways
  -> k.mqtt.ApplyConfig(gateway)
  -> 停止旧 MQTT 连接
  -> 按新配置重新启动 MQTT
```

如果 `enabled=false`：

```text
更新 sys_gateways
  -> 停止对应 MQTT 连接
```

### 1.2 变量配置重载

当前流程：

```text
PATCH /api/v1/variables/:variable_id
  -> 更新 sys_tags
  -> repo.LoadTags()
  -> k.tags.Load(tagConfigs)
  -> 重建内存变量表
```

当前已经能让以下字段变更进入运行时：

- `display_name`
- `data_type`
- `unit`
- `decimal_places`
- `scale_factor`
- `offset_val`
- `store_mode`
- `store_trigger`
- `store_cycle_sec`
- `store_deadband`
- `var_group`
- `enabled`

## 2. 为什么还需要版本号

当前“接口更新后直接 reload”的方式适合单进程边缘端。

但后续会遇到这些问题：

- 清洗规则、业务绑定、质量规则会变多
- 可能有多个运行模块需要知道配置变更
- 可能有后台任务或采集进程不经过当前 HTTP 接口修改配置
- 需要审计“配置什么时候变了”
- 检测任务运行中需要知道自己使用的是哪一版规则

因此建议增加配置版本机制。

## 3. 建议新增配置版本表

表名建议：

```text
sys_config_versions
```

建议字段：

| 字段 | 说明 |
|---|---|
| `scope` | 配置域，主键 |
| `version` | 当前版本号 |
| `updated_at` | 更新时间 |
| `updated_by` | 更新人 |
| `reason` | 变更原因 |

示例数据：

```text
gateways        12
raw_variables   37
clean_rules     9
business         4
quality          2
```

## 4. scope 设计

建议先定义这些 scope：

```text
gateways
raw_variables
clean_rules
clean_variables
business
quality
all
```

含义：

| scope | 说明 |
|---|---|
| `gateways` | MQTT/KIO 数据源配置 |
| `raw_variables` | 原始变量表配置，即当前 `sys_tags` |
| `clean_rules` | 清洗规则 |
| `clean_variables` | 清洗后变量定义 |
| `business` | 业务模块、业务变量绑定 |
| `quality` | 质量判定规则 |
| `all` | 全部重新加载 |

## 5. 推荐热重载方式

### 5.1 当前阶段：主动触发 + 版本记录

推荐当前阶段使用：

```text
接口更新数据库
  -> 更新 sys_config_versions.version + 1
  -> 立即调用 RuntimeReloader.Reload(scope)
```

优点：

- 实现简单
- 前端操作后立即生效
- 版本号可以作为审计记录
- 后续可以平滑扩展到后台轮询

示例：

```text
PATCH /api/v1/variables/:id
  -> 更新 sys_tags
  -> bump raw_variables version
  -> ReloadRawVariables()
```

```text
PATCH /api/v1/gateway-configs/:id
  -> 更新 sys_gateways
  -> bump gateways version
  -> ReloadGateways() 或 ApplyGatewayConfig()
```

### 5.2 后续阶段：后台版本轮询

后续如果出现多进程或外部配置写入，可以增加后台轮询：

```text
RuntimeReloader 每 1~3 秒读取 sys_config_versions
  -> 对比内存中的 lastLoadedVersion
  -> 如果数据库版本更大
  -> Reload(scope)
  -> 更新 lastLoadedVersion
```

这样即使配置不是通过当前 HTTP 接口改的，运行时也能自动发现。

## 6. RuntimeReloader 设计

建议新增运行时重载器：

```go
type RuntimeReloader struct {
  repo  *database.Repository
  mqtt  *mqttx.Manager
  tags  *pipeline.TagManager
  clean *clean.Manager
  biz   *business.Dispatcher
}
```

建议方法：

```go
Reload(scope string) error
ReloadGateways() error
ReloadRawVariables() error
ReloadCleanRules() error
ReloadBusiness() error
ReloadQualityRules() error
```

当前已有能力可以逐步迁入：

```text
k.mqtt.ApplyConfig(gateway)
k.tags.Load(tagConfigs)
```

后续清洗和业务模块完成后，再接入：

```text
CleanRuleManager.Load()
BusinessDispatcher.LoadBindings()
QualityRuleManager.Load()
```

## 7. 配置变更和热重载关系

建议关系如下：

```text
sys_gateways 变更
  -> scope=gateways
  -> 重启或停止相关 MQTT 连接

sys_tags 变更
  -> scope=raw_variables
  -> 重建 TagManager

sys_clean_rules 变更
  -> scope=clean_rules
  -> 重建 CleanRuleManager

sys_business_bindings 变更
  -> scope=business
  -> 重建 Business Dispatcher

sys_quality_rules 变更
  -> scope=quality
  -> 重建质量规则
```

## 8. 手动热重载接口

建议保留维护接口：

```text
POST /api/v1/runtime/reload
```

请求：

```json
{
  "scope": "all"
}
```

可选：

```text
all
gateways
raw_variables
clean_rules
clean_variables
business
quality
```

用途：

- 现场维护
- 外部手动修数据库后刷新运行时
- 调试热重载问题

## 9. 任务运行中的版本一致性

检测任务运行时，配置变更可能影响数据口径。

例如：

- 检测过程中改了清洗规则
- 检测过程中改了变量绑定
- 检测过程中改了质量判定阈值

后续建议增加任务配置快照或版本引用。

可选方案：

### 9.1 简单方案

任务启动时记录当前版本：

```text
raw_variables_version
clean_rules_version
business_version
quality_version
```

历史数据中也可以记录这些版本。

### 9.2 完整方案

任务启动时保存配置快照：

```text
task_config_snapshot
```

里面包含该任务使用的变量绑定、清洗规则、质量规则。

短期建议先做版本记录，不急着做完整快照。

## 10. 当前建议落地顺序

建议分阶段：

1. 增加 `sys_config_versions`
2. 增加 `Repository.BumpConfigVersion(scope)`
3. 在网关和变量更新接口里 bump version
4. 把当前直接 reload 包装成 `RuntimeReloader`
5. 增加 `POST /api/v1/runtime/reload`
6. 后续清洗规则、业务规则完成后接入对应 scope
7. 再考虑后台轮询版本变化

## 11. 当前结论

当前不是版本号触发热重载，而是接口更新后直接调用局部重载。

后续推荐：

```text
接口更新后立即 reload
同时递增配置版本号
版本号用于审计、多模块同步、未来后台轮询、任务口径记录
```
