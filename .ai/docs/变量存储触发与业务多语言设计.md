# 变量存储触发与业务多语言设计

本文记录变量表本轮新增字段和设计边界，供后续后端、前端和 AI 继续开发时参考。

## 1. 背景

原来的变量存储设计默认偏向“一直采集、一直按规则存储”。

当前边缘检测平台的新需求是：

```text
平时只更新实时值，不落历史库。
收到检测开始/任务通知后，才允许进入历史存储。
```

同时系统是三语系统：

```text
中文
英文
日文
```

变量来自上位机时通常只有一个中文或原始名称，因此需要允许用户维护英文、日文显示名。

这属于业务数据多语言，不应该放入前端 i18n 资源文件。

## 3. store_mode 与 store_trigger 的职责划分

### 3.1 store_mode

`store_mode` 保留原有含义，表示“怎么存”。

当前语义：

```text
0  不存
1  变化存
2  周期存
3  变化 + 周期都存
```

它只描述存储策略，不描述业务时机。

### 3.2 store_trigger

`store_trigger` 是新增字段，表示“什么时候允许存”。

当前取值：

```text
always
on_detection
```

含义：

| 值 | 含义 |
|---|---|
| `always` | 保留原有方式，只要满足 `store_mode` 就允许写历史数据 |
| `on_detection` | 默认值，平时不存，只有检测/任务处于运行中才允许写历史数据 |

因此完整判断应该是：

```text
先判断 store_trigger 是否允许存
再判断 store_mode 是否满足变化/周期规则
最后进入历史存储
```

## 4. 当前后端运行逻辑

当前代码已经接入：

```text
internal/models/models.go
internal/pipeline/logic_worker.go
internal/pipeline/scanner.go
internal/runtime/kernel.go
```

### 4.1 on_detection

默认值是：

```text
store_trigger = on_detection
```

当前逻辑：

```text
变量更新
  -> 更新实时值
  -> 判断 store_mode
  -> 如果 store_trigger=on_detection
      -> 必须找到该变量绑定设备的运行中检测任务
      -> 才生成 StoreTask
```

如果没有运行中的检测任务：

```text
只更新实时值，不写历史库
```

### 4.2 always

当前逻辑：

```text
变量更新
  -> 更新实时值
  -> 判断 store_mode
  -> 如果 store_trigger=always
      -> 不需要检测任务
      -> 满足 store_mode 后直接生成 StoreTask
```

注意：`always` 是为了兼容原来“一直存储”的场景。

## 5. 为什么不把这个逻辑塞进 store_mode

不建议把 `on_detection` 塞进 `store_mode`，原因是两者维度不同。

```text
store_mode:
  怎么存
  变化 / 周期 / 两者

store_trigger:
  什么时候允许存
  一直 / 检测时
```

拆成两个字段后，组合更清晰：

| store_trigger | store_mode | 含义 |
|---|---|---|
| `always` | `1` | 一直变化存 |
| `always` | `2` | 一直周期存 |
| `on_detection` | `1` | 检测期间变化存 |
| `on_detection` | `2` | 检测期间周期存 |
| `on_detection` | `3` | 检测期间变化+周期存 |

## 6. 变量业务多语言设计

变量显示名属于业务数据，不属于系统界面 i18n。

系统界面 i18n 管：

```text
菜单
按钮
表头
提示语
固定状态文案
```

变量业务多语言管：

```text
变量显示名
设备显示名
工程显示名
工艺参数名
质量规则名称
```

本次采用兼容改动较小的第二种方案：

```text
display_name      中文/默认显示名
display_name_en   英文显示名
display_name_ja   日文显示名
```

前端显示建议：

```text
当前语言 zh:
  display_name

当前语言 en:
  display_name_en || display_name

当前语言 ja:
  display_name_ja || display_name
```

这样不会和前端 i18n 冲突。

## 7. 前端接口影响

变量查询接口会返回：

```text
display_name
display_name_en
display_name_ja
store_mode
store_trigger
```

接口：

```text
GET /api/v1/variables
GET /api/v1/realtime/variables
```

变量更新接口支持：

```text
PATCH /api/v1/variables/:variable_id
```

请求示例：

```json
{
  "display_name": "台1主轴温度",
  "display_name_en": "Station 1 Spindle Temperature",
  "display_name_ja": "1番ステーション主軸温度",
  "store_trigger": "on_detection"
}
```

前端 TypeScript 类型已同步：

```text
desktop/src/shared/api/types.ts
```

## 8. 后续注意事项

### 8.1 清洗后变量也应继承这个设计

后续如果新增清洗后变量表，例如：

```text
sys_clean_variables
```

也建议保留：

```text
display_name
display_name_en
display_name_ja
store_mode
store_trigger
```

或者让清洗后变量引用原始变量的显示名，但最终仍要支持用户覆盖。

### 8.2 业务模块存储也要尊重 store_trigger

后续增加业务模块后，存储判断顺序建议仍然保持：

```text
变量变化
  -> 清洗
  -> 业务模块判断
  -> store_trigger 判断当前是否允许存
  -> store_mode 判断是否满足变化/周期策略
  -> 写历史
```

### 8.3 运行中任务的配置版本

如果检测任务运行中修改了：

```text
store_trigger
store_mode
清洗规则
质量规则
```

可能导致同一任务前后数据口径不同。

后续需要结合配置版本设计：

```text
sys_config_versions
task_config_version
```

短期可以先接受热重载立即生效，后续再做任务配置快照。
