# 历史与计划、待检测任务方案

编写时间：2026-06-16
执行身份：`review-ai`

## 1. 最终结论

第一版可行，改动按“中等偏小的业务闭环”评估，不是重写任务系统。

核心做法：

- 新增一张 `sys_detection_plans`，只承接外部系统下发的待检测计划。
- 外部系统填好出厂编号、检测配置编码和测试项；检测配置版本/hash 可以为空。
- 工位页面点击“开始检测”时，在弹窗里选择待检测计划。
- 点击开始后，仍复用现有检测启动链路创建真实 `sys_detection_tasks`。
- 开工成功后，把计划表标记为 `started`，并写入 `started_task_id`、实际边缘机、实际工位项目。
- 甘特图和历史仍只看已经开工的 `sys_detection_tasks`。
- 数据库同步软件负责主服务器和边缘端之间的数据同步，应用层不重新实现数据库同步。

一句话：`sys_detection_plans` 是“计划池”，`sys_detection_tasks` 是“实际开工记录”。计划只有被开工后才流转到任务表。

## 2. 为什么不直接用任务表

现有任务表表达的是已经发生的检测运行记录，不适合提前塞未开工任务。

不建议给 `sys_detection_tasks.status` 增加 `pending_test`，原因：

- 会把“计划”和“运行记录”混在一张表里。
- 现有历史、甘特图、存储、报表都默认任务已经真实开工。
- 未开工任务没有采集数据、没有冻结配置版本、没有运行时间，进入任务表会污染历史语义。
- 后续判断 `running/paused/stopped` 时容易误把未开工计划当运行任务处理。

所以第一版新增 `sys_detection_plans` 更干净：计划归计划，运行归运行。

## 3. 第一版明确不做

第一版不做这些复杂能力：

- 不预分配到某一台边缘机。
- 不做认领/取消认领流程。
- 不做复杂抢占锁。
- 不做离线冲突仲裁。
- 不新增计划执行流水表。
- 不新增计划专用配置重试 worker。
- 不要求外部系统提供配置版本和配置 hash。
- 不让主服务器直接创建边缘运行任务。

现场规则是“谁实际点开始，谁就是执行设备”。因为有物理约束，同一台实物设备不会同时在两台测试机上开始检测，第一版不为这个现实上不存在的场景加重系统。

## 4. 新表设计

新增表：

```text
sys_detection_plans
```

主服务器和边缘端都使用同一张表结构；设计默认两侧数据库内容最终一致，只允许存在短时时差，应用层不实现数据库同步。

建议字段：

```text
id                         BIGINT UNSIGNED PRIMARY KEY
plan_no                    VARCHAR(128) NOT NULL
source_system              VARCHAR(64) NOT NULL
external_plan_id           VARCHAR(128) NOT NULL
external_order_no          VARCHAR(128) DEFAULT ''
factory_no                 VARCHAR(128) NOT NULL
customer_name              VARCHAR(128) DEFAULT ''
device_model               VARCHAR(128) DEFAULT ''
test_item_code             VARCHAR(64) DEFAULT ''
test_item_name             VARCHAR(128) DEFAULT ''
test_sequence              INT NOT NULL DEFAULT 0
mode                       VARCHAR(64) DEFAULT 'standard'
standard_code              VARCHAR(64) NOT NULL
report_request_json        TEXT NULL
status                     VARCHAR(32) NOT NULL DEFAULT 'pending'
owner_edge_instance_id     VARCHAR(64) DEFAULT ''
owner_project_id           BIGINT UNSIGNED NULL
owner_project_code         VARCHAR(64) DEFAULT ''
started_task_id            BIGINT UNSIGNED NULL
started_at                 DATETIME(3) NULL
cancelled_at               DATETIME(3) NULL
error_message              VARCHAR(512) DEFAULT ''
sync_scope                 VARCHAR(32) NOT NULL DEFAULT 'global'
edge_instance_id           VARCHAR(64) NOT NULL DEFAULT ''
updated_by_node            VARCHAR(64) NOT NULL DEFAULT ''
updated_by_user            VARCHAR(128) NOT NULL DEFAULT ''
created_at                 DATETIME(3) NULL
updated_at                 DATETIME(3) NULL
```

建议索引：

```text
UNIQUE KEY uk_detection_plans_plan_no (plan_no)
UNIQUE KEY uk_detection_plans_source_external (source_system, external_plan_id)
INDEX idx_detection_plans_status (status)
INDEX idx_detection_plans_factory_no (factory_no)
INDEX idx_detection_plans_standard_code (standard_code)
INDEX idx_detection_plans_owner_task (owner_edge_instance_id, owner_project_id, started_task_id)
INDEX idx_detection_plans_external_order (external_order_no)
```

关键规则：

- `factory_no` 不唯一。
- 同一 `factory_no` 可以有 2-4 条不同检测计划。
- 唯一性用 `plan_no` 或 `(source_system, external_plan_id)`。
- `standard_code` 必填。
- `report_request_json` 可空，用于保存从报表导入计划生成的报表请求快照；边缘开工创建真实任务时冻结到 `detection_run_report_requests`。
- `started_task_id` 为空表示还没有流转成真实任务。
- 检测配置版本/hash 不放在计划必填项里，真实开工时由现有检测启动链路冻结。
- 检测标准不是天然按单台设备隔离。标准作用域分三层：真全局（`project_id IS NULL` 且 `project_group=''`）、批量/类别（`project_group`，例如同一批 AC 项目）、单项目（`project_id/project_code`）。`sync_scope` 只表示数据库同步范围，不表示业务适用范围；`model_name` 是描述性型号字段，不替代 `project_group`。计划只用 `standard_code` 选择业务标准。边缘在具体项目开工时，必须把标准项按业务变量名映射到该项目的 enabled 变量，再冻结 `detection_run_standard_items`，不能直接沿用其他项目的 `var_id`。

## 5. 状态流转

计划状态只保留四个：

```text
pending    未开工，可被下拉框选择
starting   用户已点开始，后端正在启动
started    已创建真实 sys_detection_tasks
cancelled  已取消
```

正常流转：

```text
pending -> starting -> started
```

失败流转：

```text
pending -> starting -> pending
```

失败时写 `error_message`，计划仍可重试。

`starting` 只是短暂状态，用来防止同一边缘端重复点击。第一版不把计划长期挂在 `starting` 等后台重试。

## 6. 配置未同步怎么处理

配置未同步复用已有检测配置同步/下发流程，不在计划表新增一套重试系统。

计划只提供：

```text
standard_code
```

从计划开工时，后端把它映射到现有启动参数：

```text
config_enabled = true
config_code = standard_code
```

实际开工仍必须走统一任务请求变量链路：后端把计划、检测配置、报表请求和结束策略组装成 `command=start_detection` 的 JSON，写入 watched STRING 虚拟变量（默认约定 `task_request`，接口也允许传 `request_var_id/request_var_name`），由 `sys_task_flow_vars` 的 `data_change` 倒排索引命中任务流，再由 `builtin.start_detection_run` 创建真实检测任务。

处理规则：

- 本地已经有该 `standard_code`：按当前项目变量映射标准项后启动。
- 本地没有该 `standard_code`：本次启动失败，计划回到 `pending`，写 `error_message`。
- 标准项无法映射到当前项目变量：本次启动失败，计划回到 `pending`，写明缺失变量，等待变量配置或标准修正。
- 等现有配置同步/下发流程把配置补齐后，现场再次选择同一计划开工。
- 启动成功后，真实任务里冻结实际使用的配置版本和 hash。

这样不和已有配置重试流程冲突，也不会为了计划表再造一套配置等待队列。

## 7. 开工流程

边缘工位页面是主要开工入口。

部署时当前收窄为 8 台边缘机，每台边缘机只采集自己的测试机数据。工位页面默认就是当前边缘机对应的测试机，不需要让工人再选 1-8。

工位页面点击“开始检测”：

1. 弹窗加载 `status = pending` 的计划。
2. 工人从下拉框选择计划。
3. 前端带出出厂编号、机型、测试项、检测配置编码。
4. 用户点击开始。
5. 后端把计划从 `pending` 改为 `starting`。
6. 后端按 `standard_code` 解析本地检测配置，生成 `command=start_detection` 的任务请求 JSON。
7. 后端通过 `VariableWriteService` 写 watched STRING 虚拟变量，默认变量名为 `task_request`。
8. `TaskFlowExecutor` 通过 `sys_task_flow_vars` 的 `data_change` 倒排索引命中任务流，先执行可选 `builtin.write_control_variables`，再执行 `builtin.start_detection_run`。
9. `builtin.start_detection_run` 创建真实 `sys_detection_tasks`，冻结检测配置、`process_params/plc_writes/report_request/end_policy` 等参数，并装入 `TaskManager`。
10. 计划服务观察到真实任务后，把计划改为 `started`。
11. 写入 `started_task_id`、`owner_edge_instance_id`、`owner_project_id`、`owner_project_code`、`started_at`。
12. 计划从下拉框消失，历史和甘特图从真实任务里展示。

如果 watched 变量不存在、任务流未命中、任务流执行失败或任务没有落库，计划必须回到 `pending` 并写 `error_message`，不得改走直接创建任务的兜底路径。

同一个出厂编号有 2-4 个检测标准时，就是 2-4 条 `sys_detection_plans`。前端下拉框和计划页按测试项、标准编码、序号区分即可。

## 8. 主服务器和边缘端职责

边缘端职责：

- 展示本地同步到的待检测计划。
- 现场工位开工。
- 创建真实检测任务。
- 回写计划状态。
- 离线时仍允许本地开工。

主服务器职责：

- 展示同步库中的计划。
- 展示同步回来的历史和甘特图。
- 如果从主服务器页面发起开工，必须通过 edge-control 调目标边缘。
- 主服务器不直接写 `sys_detection_tasks`。

在线模式下，主服务器可以作为统一入口；离线时，边缘端工位页面仍能独立开工，等网络恢复后由同步软件回传状态。

## 9. 后端接口

边缘端接口：

```text
GET  /api/v1/detection-plans
GET  /api/v1/detection-plans/:id
POST /api/v1/detection-plans/:id/start
POST /api/v1/detection-plans/:id/cancel
```

查询参数：

```text
status
factory_no
keyword
limit
offset
```

开工请求：

```json
{
  "project_id": 1,
  "operator_note": "现场选择计划开工",
  "request_var_name": "task_request"
}
```

`request_var_name` 可省略，边缘端默认使用 `task_request`；如果现场任务流使用其他 watched STRING 变量，应显式传 `request_var_id` 或 `request_var_name`。

主服务器接口：

```text
GET  /api/v1/detection-plans
GET  /api/v1/detection-plans/:id
POST /api/v1/detection-plans/:id/start
```

主服务器开工接口只做权限校验和边缘路由，然后转发到边缘：

```text
POST /api/v1/edge-control/detection-plans/:id/start
```

## 11. 这个方案的缺点

这个方案有几个明确缺点，需要接受：

- 同步延迟会导致主服务器看到的计划状态短时间滞后。
- 边缘离线开工时，主服务器无法即时知道这条计划已经开始。
- 如果两个边缘离线时都能看到同一条 pending 计划，系统不做复杂仲裁。
- 外部系统写错 `standard_code` 时，开工会失败，只能等配置修正后重试。
- 计划表只记录最终开工归属，不记录每一次失败尝试的完整流水。

这些缺点换来的好处是实现简单、和现有任务/历史/报表体系冲突最少。

## 12. 必要防护

第一版只做必要防护：

- `factory_no` 不做唯一约束，允许一台设备多个测试计划。
- `plan_no` 或 `(source_system, external_plan_id)` 做唯一约束，避免外部重复下发。
- 开工时必须用条件更新把 `pending` 改为 `starting`，避免同一边缘重复点击。
- 只有真实任务创建成功后，计划才能改为 `started`。
- 启动失败必须回到 `pending`，并写 `error_message`。
- 甘特图和历史禁止读取未开工计划。
- 主服务器禁止直接写边缘运行任务，必须走 edge-control。

这些防护会增加一些代码量，但不是复杂架构，主要是避免计划和真实任务状态不一致。

1. 外部或手工插入计划。

验收：

- 不能只用 mock。
- 不能只看空页面。
- 必须有真实数据库/API 证据。

可复用验收工具：

```powershell
cd backend
go run ./tools/smokedetectionplanssync `
  -main-config ../main-server/backend/configs/config.json `
  -edge-config configs/config.json `
  -edge-base-url http://127.0.0.1:18080 `
  -project-code AC-01 `
  -standard-code EXISTING_STANDARD_CODE `
  -preflight-only

go run ./tools/smokedetectionplanssync `
  -main-config ../main-server/backend/configs/config.json `
  -edge-config configs/config.json `
  -edge-base-url http://127.0.0.1:18080 `
  -project-code AC-01 `
  -standard-code EXISTING_STANDARD_CODE `
  -confirm-start
```

这个工具不模拟外部复制链路，也不作为外部复制工具验收。设计默认主服务器库和边缘库最终内容一致，只允许存在短时时差；本地开发可以让两个配置指向同一套数据库。工具要求 `project-code`、`standard-code` 在主/边查询视角可见。工具会：

- `-preflight-only` 只做非破坏性预检：检查主/边项目、项目组、检测标准可见且一致，边缘 API 可登录；不插入计划、不启动任务。
- 在主服务器库插入一条 `sys_detection_plans` smoke 计划。
- 等待该计划在边缘侧数据库可见。
- 通过边缘 HTTP API 从计划开工。
- 停止 smoke 任务。
- 等待计划 `started/started_task_id` 在主服务器侧数据库可见。
- 默认清理自己插入的 smoke 计划。

如果项目、项目组、检测标准或计划状态在对应查询视角不可见，工具失败；这说明当前数据库内容还没达到业务可用条件。工具允许主服务器配置和边缘配置指向同一个数据库，作为本地一致性验证。

完整 smoke 会启动并停止一条真实检测任务，因此必须显式传 `-confirm-start`。没有该参数时工具会拒绝执行完整流程。

主/边可见性验收：

- 主服务器侧写入的计划在边缘查询视角可见。
- 边缘开工后的计划状态在主服务器查询视角可见。
- 主服务器能通过 `started_task_id` 打开历史。

## 15. 第一版完成标准

第一版完成后，应能跑通：

```text
外部系统写入待检测计划
-> 计划在边缘查询视角可见
-> 工位页面选择计划
-> 边缘创建真实检测任务
-> 计划标记 started
-> 计划状态在主服务器查询视角可见
-> 主服务器历史与计划页面可查看
```

达到这个闭环就算第一版完成。认领、复杂抢占、离线冲突审计、计划执行流水、细粒度生命周期可以作为后续增强，不进入第一版。
