# 报表 20 分钟专项测试方案

最后更新：2026-06-18

维护责任：`test-ai`

本文是报表链路的 20 分钟专项验收方案，用于在完整 40 分钟验收前快速确认当前主链路和刚修正的存储周期边界。测试必须贴近用户真实使用方式：从主服务器模板/计划导入开始，到工位选择待检测计划开工，再到历史报表预览和下载包闭合。

## 1. 测试目标

本轮只验证一条清晰主路径：

```text
主服务器模板管理
-> 主服务器导入计划
-> 创建检测配置和待检测计划
-> 工位选择待检测计划
-> watched STRING 任务流正式开工
-> 任务连续合格 20 分钟自动结束
-> 主服务器自动生成综合、温度、湿度三份 Excel
-> 历史页查看 Luckysheet 报表和检测快照
-> 数据下载页或后端下载包接口导出 zip
```

额外专项目标：

- 验证 `check_cycle_ms` 只控制业务判定节拍，不能影响历史入库周期。
- 验证本次任务冻结的 storage routes 中温度、湿度变量 `cycle_ms=20000`。
- 验证 20 分钟任务的温度/湿度历史数据量符合 20 秒入库节奏。

## 2. 测试范围

项目：

- 使用 `AC-01 / project_id=1`。
- 不使用 `AC-09+`。
- 不使用冒烟项目作为通过证据。

变量：

- 温度变量：`7943629295557820374`。
- 湿度变量：`3591294491864692082`。
- 两个变量必须在 `AC-01` 当前启用变量中存在。

检测配置：

- 使用导入计划创建的新检测配置。
- `check_enabled=true`。
- `alarm_enabled=true`。
- `store_enabled=true`。
- `check_cycle_ms=3000`，用于证明判定周期与存储周期分离。
- 上下限放宽，保证任务可以连续合格 20 分钟，例如温度、湿度都使用 `0~100`。

存储配置：

- 当前 `sys_storage_routes` 中温度、湿度变量必须为：
  - `enabled=true`
  - `trigger_mode=on_cycle`
  - `store_on_start=true`
  - `cycle_ms=20000`
- 不允许从检测配置的 `check_cycle_ms` 推导或覆盖 storage route 的 `cycle_ms`。

任务参数：

- `end_policy=qualified_hold`
- `qualified_hold_minutes=20`
- `temp_coefficient=1.10`
- `humidity_coefficient=0.95`

报表：

- 综合报表：温度和湿度在同一个业务 sheet。
- 温度报表：只写温度。
- 湿度报表：只写湿度。
- 每个 Excel 通常只验证前 1-2 个可见业务 sheet。
- 三份报表都要包含上下限、任务参数、合格时间段平均值、后端计算结果和曲线图片。

## 3. 前置检查

后端健康：

```powershell
Invoke-RestMethod http://127.0.0.1:18080/health
Invoke-RestMethod http://127.0.0.1:19080/health
```

必须满足：

- 边缘后端 `status=ok`。
- 主服务器后端 `status=ok`。
- 边缘 gateway active。
- AC-01 当前没有运行任务。

AC-01 storage route 检查：

```text
GET /api/v1/storage-routes?project_id=1
```

必须确认：

- `3591294491864692082` 的 `cycle_ms=20000`。
- `7943629295557820374` 的 `cycle_ms=20000`。
- 两条 route 都启用。

任务流检查：

- AC-01 必须存在 `data_change` 类型任务流。
- 该任务流必须 watch 一个 `STRING` 虚拟变量。
- 任务流 steps 必须包含 `builtin.start_detection_run`。
- 前端开工时必须写该 watched STRING 变量，不允许走 legacy `/api/v1/detection-runs` 直启。

## 4. 测试步骤

### T1 模板准备

用户动作：

1. 打开 `http://127.0.0.1:5273/#/report-settings/templates`。
2. 上传或复用综合、温度、湿度三份模板。
3. 保存 mapping。
4. 下载模板副本。
5. 打开模板预览。

验收点：

- 模板列表有三份模板。
- 模板 artifact key 存在。
- 下载的副本可以打开。
- Luckysheet 预览显示业务 sheet。
- mapping 刷新页面后仍存在。

停止条件：

- 没有模板副本 artifact。
- 只保存 Luckysheet JSON。
- mapping 缺失仍允许进入后续测试。

### T2 导入 20 分钟计划

用户动作：

1. 打开 `http://127.0.0.1:5273/#/report-settings/plan-imports`。
2. 上传 20 分钟专项计划 Excel。
3. 检查解析草稿。
4. 确认导入。

计划 Excel 必须包含：

- 出厂编号：建议 `RPT-20M-{yyyyMMddHHmmss}`。
- 客户名称。
- 机型。
- 检测项。
- 检测模式。
- 温度、湿度上下限。
- 三份报表模板编码。
- `qualified_hold_minutes=20`。
- `temp_coefficient=1.10`。
- `humidity_coefficient=0.95`。

验收点：

- 创建 `sys_detection_standards`。
- 创建 `sys_detection_standard_items`，温度/湿度两行都存在。
- 标准项 `check_cycle_ms=3000`。
- 创建 `sys_detection_plans(status=pending)`。
- 计划 `report_request_json` 包含三份报表请求。
- 计划参数包含 20 分钟合格结束策略和两个系数。

停止条件：

- 只创建检测配置，没有创建计划。
- `report_request_json` 为空。
- 报表请求没有变量。
- 检测配置没有写 `version/config_hash/updated_at`。

### T3 工位按计划开工

用户动作：

1. 打开 `http://127.0.0.1:5273/#/station?project_id=1`。
2. 点击开始检测。
3. 选择刚导入的待检测计划。
4. 检查带出的出厂编号、客户、机型、检测配置和报表请求。
5. 点击开始。

验收点：

- 前端通过主服务器 WS 或控制通道发起 `command.write_variable`。
- 边缘 `VariableWriteService` 写入 watched STRING 变量。
- `sys_task_flow_runs` 出现 data_change 触发记录。
- 任务流执行 `builtin.start_detection_run`。
- 创建真实 `sys_detection_tasks`。
- `sys_detection_plans.status=started`。
- `started_task_id` 指向真实任务。

冻结快照必须确认：

- `detection_run_standard_items` 中温度、湿度 `check_cycle_ms=3000`。
- `detection_run_storage_routes` 中温度、湿度 `cycle_ms=20000`。
- `detection_run_report_requests` 数量为 3。
- `qualified_hold_ms=1200000`。
- `custom_config_json` 或冻结参数中包含两个系数。

停止条件：

- 走 legacy `/api/v1/detection-runs` 直启。
- 任务创建成功但计划未回写 started。
- 报表请求没有冻结。
- storage route 冻结成 `3000` 或其它非 `20000` 周期。

### T4 运行中观察

观察周期：

- 开工后第 1 分钟。
- 第 5 分钟。
- 第 10 分钟。
- 第 20 分钟结束后。

验收点：

- 任务状态为 running，直到连续合格满 20 分钟。
- 无超限报警。
- 历史数据持续增长。
- 温度、湿度每个变量约 20 秒一条数据。

20 分钟预期：

- 每个变量理论样本约 `60` 条，加上首帧和调度偏差，接受范围建议 `55~75` 条。
- 两个变量历史行数应接近，不应再出现一个变量 3 秒、另一个变量 10 秒这种明显不同步。
- 详细数据页时间显示到秒。

停止条件：

- 任务未到 20 分钟提前结束。
- 任务超过 22 分钟仍未结束。
- 任一变量没有历史数据。
- 冻结 storage route 是 20 秒，但实际历史密度明显按 3 秒入库。

### T5 自动结束

验收点：

- 任务自动停止。
- `end_type=qualified_hold`。
- `result_status=ok`。
- `duration_ms` 大于等于 20 分钟，扣除暂停时间后不小于 `1200000ms`。
- 任务事件包含 start/stop。

停止条件：

- 只能人工停止。
- `end_type` 不是 `qualified_hold`。
- 合格结果错误。

### T6 自动报表生成

用户动作：

1. 打开历史详情 `/#/history/runs/{task_id}?tab=reports`。
2. 等待或刷新报表状态。
3. 分别查看综合、温度、湿度三份报表。

验收点：

- 主服务器生成 3 个 report job。
- 三个 job 都是 `succeeded`。
- 三个 job 都有 `.xlsx` artifact。
- 通知中心有报表 started/succeeded 通知。
- 左侧报表列表显示三份报表名称。
- 右侧 Luckysheet 加载实际 Excel artifact。
- 可见 sheet 是业务 sheet，隐藏追溯 sheet 不展示。
- 曲线图片在业务 sheet 的预期位置。
- 综合报表同一 sheet 同时包含温度和湿度。

停止条件：

- report worker 不自动生成且没有明确失败原因。
- 只能 force enqueue 才有报表。
- Luckysheet 空白。
- 预览和导出 Excel 图片位置明显不一致。

### T7 报表内容核对

三份 Excel 都要核对：

- 出厂编号正确。
- 检测编号正确。
- 温度/湿度上下限正确。
- `temp_coefficient=1.10`。
- `humidity_coefficient=0.95`。
- 合格时间段平均值来自历史数据。
- 后端计算结果使用冻结参数和历史指标。
- 不依赖 Excel 原生公式作为正式计算来源。

综合报表额外核对：

- 同一个业务 sheet 中有温度和湿度。
- 两张曲线图片或一张复合曲线图片位置正确。
- 温度和湿度指标都不为空。

停止条件：

- 报表单元格用模板默认值冒充结果。
- 参数没有冻结或被当前页面输入覆盖。
- 后端没有写计算结果。

### T8 数据下载

用户动作：

1. 打开历史详情 `/#/history/runs/{task_id}?tab=downloads`。
2. 选择任务快照、历史数据、报表、事件。
3. 点击下载所选。
4. 再执行下载全部。

验收点：

- 调用 `POST /api/v1/main-server/download-packages`。
- 下载包由后端生成。
- zip 至少包含：
  - `download-manifest.json`
  - `snapshots/task.json`
  - `snapshots/standard-items.json`
  - `snapshots/storage-routes.json`
  - `snapshots/report-requests.json`
  - `data/history-raw.csv`
  - 三份正式报表 `.xlsx`
  - report job events
- Excel 文件可打开。
- manifest 中记录 skipped 项及原因。

停止条件：

- 前端用 JSZip 自己拼包。
- zip 里没有正式 report artifact。
- 缺文件时生成半真包。

## 7. 通过标准

全部满足才算 20 分钟专项通过：

1. 开工路径是 watched STRING 任务流。
2. 检测任务自动以 `qualified_hold` 结束。
3. 温度、湿度检测标准项 `check_cycle_ms=3000`。
4. 温度、湿度冻结 storage route `cycle_ms=20000`。
5. 温度、湿度历史数据量符合 20 秒周期。
6. 三份报表请求冻结成功。
7. 三份报表 job 自动生成成功。
8. 历史 Excel 报表 Luckysheet 可预览。
9. 导出 Excel 与预览主要内容一致。
10. 下载包包含任务、配置、历史、报表和事件证据。

## 8. 本轮不覆盖

以下不是本 20 分钟专项的通过条件：

- AC-02 项目组标准复用。
- 40 分钟接近真实验收。
- 外部数据库同步软件真实延迟验收。
- 单独曲线 PNG artifact 下载。
- 下载包异步状态表。

本轮暴露的产品边界：

- 计划导入模型把“检测配置变量行”和“报表请求行”绑在一起，无法在同一计划中自然表达“综合 + 温度 + 湿度”三份报表且不重复变量；本次用开工后追加两份报表请求完成验证。后续应把导入计划的检测配置行和报表请求行拆成两个层级。
- `cell_mapping.items.var_id` 的 JSON 类型必须是数字；前端/导入器如果为了 64 位安全使用字符串，需要后端 `CellMappingItem` 支持 `var_id_text` 或自定义反序列化。
- 模板公式由源 xlsx 保留，不由 cell mapping 生成；测试模板必须显式包含公式单元格，否则无法验证公式链路。
