# 工位画面模板与边缘过滤计划

最后更新：2026-06-15

维护责任：`review-ai` / 后续实施按 `backend-ai`、`frontend-ai`

本文档固化工位画面“显示哪些点位、卡片区和列表区放什么、排序是什么、用户如何设计、主服务器如何下发、边缘端如何自动过滤”的规划。它补充边缘端与主服务器数据库同步计划，不改变当前 HTTP 控制通道 EB-056 的边界。

## 1. 当前结论

1. 工位画面配置不能继续写在前端页面代码里。
2. 工位画面配置应建成低频模板配置，可由主服务器设计和发布，也可允许边缘端本地临时覆盖。
3. 模板配置按主/边数据库内容最终一致处理，允许短时时差；实时值、检测快照、运行状态和现场控制不能依赖镜像库。
4. 边缘端后端必须按本机 `edge_instance_id`、项目归属和当前项目点位自动过滤，不能把过滤边界交给前端。
5. 模板项优先绑定业务稳定名，例如 `project_code + var_name`、`var_group + var_name` 或检测快照项；不要把主服务器模板绑定到边缘本地 `var_id`。
6. 工位主画面渲染时，实时值走边缘本地 WS，检测限值/检测值语义走边缘本地 HTTP 当前运行快照。
7. 这部分不属于 EB-056 的 `/api/v1/edge-control/*` 现场控制命令，不应和启动检测、写变量、报警静音、运行中限值调整混在一起。

## 2. 目标和非目标

### 2.1 目标

- 支持用户设计工位画面：
  - 卡片区显示什么。
  - 列表区显示什么。
  - 布局区顺序、点位顺序、卡片/表格/曲线/状态面板类型。
  - 点位过滤、分组过滤、检测标准项过滤。
- 支持一台主服务器管理多台边缘：
  - 中心节点可设计通用模板、型号模板、项目模板或边缘模板。
  - 边缘端只解析和展示属于自己的项目与点位。
- 支持边缘离线运行：
  - 模板同步到边缘本地 MySQL 后，主服务器离线不影响工位页显示。
- 支持未来主服务器 Web 复用：
  - 主服务器可读取同步镜像中的模板和历史/检测数据展示。
  - 主服务器实时聚合另行规划，不通过模板表承载实时值。

### 2.2 非目标

- 不通过模板表写现场变量。
- 不通过模板表启动、停止或调整检测任务。
- 不把模板保存做成 `/api/v1/edge-control/*` 控制命令。
- 不让主服务器直接修改边缘 `sys_tags`、`sys_projects`、`sys_storage_routes` 来控制现场。
- 不把主服务器报表、通知或跨边缘大屏运行状态回写到边缘运行表。

## 3. 表归属建议

### 3.1 新增共享配置表

建议新增独立工位画面配置表，归类为低频共享配置。第一阶段可以中心下发或边缘本地编辑；后续如果启用多主同步，必须补齐版本和冲突策略。

```text
sys_station_view_templates
sys_station_view_regions
sys_station_view_items
sys_station_view_assignments
```

含义：

| 表 | 责任 |
| --- | --- |
| `sys_station_view_templates` | 模板主表，记录模板编码、版本、状态、来源节点和布局总配置。 |
| `sys_station_view_regions` | 布局区配置，当前正式区域是 `card_pool`（卡片区）和 `list_layout`（列表区），记录布局类型、宽度、折叠和排序。 |
| `sys_station_view_items` | 布局区内条目，如指标卡、表格行、曲线、报警面板、运行状态面板。 |
| `sys_station_view_assignments` | 模板适用范围，如全局、型号、边缘、项目。 |

破坏性口径：旧 `region_key=left/right` 抽象已废弃。新 API/DTO、effective response、前端页面和测试不得再暴露“左/右区域”；数据库中的 `region_key` 只作为迁移历史和同步兼容字段保留，新配置必须写 `layout_area=card_pool|list_layout`。

这些表不能替代：

| 不替代表 | 原因 |
| --- | --- |
| `sys_tags` | 点位发现、写入约束、清洗参数和实时运行态仍由边缘端管理。 |
| `sys_detection_standards` / `sys_detection_standard_items` | 检测标准仍是业务检测配置，工位模板只引用或筛选展示。 |
| `detection_run_standard_items` | 当前运行检测快照仍由检测启动时冻结，模板不能修改运行快照。 |
| `sys_storage_routes` | 历史入库配置仍由 storage route 管理。 |

### 3.2 边缘归属表

如果同步策略是每个边缘一个库或一个 schema，第一阶段可以通过本地配置里的 `edge_instance_id` 与 schema 来源区分边缘归属，不强制所有表立即加边缘字段。

如果后续主服务器合库或某个边缘库可能同步进多个边缘的配置，建议补：

```text
sys_edge_project_bindings
```

核心字段：

| 字段 | 说明 |
| --- | --- |
| `edge_instance_id` | 边缘实例 ID。 |
| `edge_code` | 边缘编码。 |
| `project_code` | 项目编码。 |
| `enabled` | 是否归属该边缘。 |
| `source` | `local`、`main_server`、`sync` 等来源。 |

边缘端后端加载工位模板和项目时，必须先取本机 `edge_instance_id` 绑定的项目集合，再解析模板和点位。

## 5. 边缘端解析和过滤规则

边缘端后端提供工位有效模板接口时，应按以下顺序处理：

```text
1. 读取本机 edge_instance_id / edge_code。
2. 校验 project_id / project_code 是否属于本边缘。
3. 按 project > edge > model > global 选择模板。
4. 读取模板 regions/items。
5. 对每个 item 按 `layout_area` 分到卡片区或列表区，并只在当前项目范围内解析绑定。
6. 输出 resolved var_id / var_id_text / display_name / unit / decimal_places / source fields。
7. 前端仅按后端返回结果订阅 WS 和渲染。
```

严禁：

- 用 `binding_key=var_name` 在全库找同名点位。
- 当前项目找不到点位时拿其他项目点位兜底。
- 前端收到全量模板后自行过滤边缘归属。
- 把模板里的 `manual` 配置解释成现场写变量、启动检测或控制命令。

点位解析必须使用当前项目作用域：

```text
project_code + var_name
project_id + var_name
project_id + var_group
detection_run_standard_items.task_id + var_id
```

## 6. API 规划

### 6.1 边缘端第一阶段

先做只读有效模板接口，支撑前端替换硬编码。

| Method | Path | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/station-view/effective?project_id=` | 返回当前项目可用模板、区域、条目和已解析点位。 |
| `GET` | `/api/v1/station-view/templates` | 列出本边缘可见模板、版本和 assignment。 |
| `GET` | `/api/v1/station-view/items?template_uid=...` 或 `?project_id=...` | 返回模板条目配置，使用 `layout_area=card_pool|list_layout`，包含 `sort_order/pinned/visible`。 |
| `PUT` | `/api/v1/station-view/items` | 替换模板条目配置，要求每个 item 显式传 `layout_area`、`sort_order`、`visible`，可传 `pinned`。 |
| `POST` | `/api/v1/station-view/reload` | 重新校验配置、补齐默认模板并可选返回某项目 effective；需要 `system_settings`。 |
| `PATCH` | `/api/v1/station-view/templates/:id` | 低频发布/禁用模板，只支持模板状态、版本和 owner scope 元数据，不编辑布局。 |
| `PATCH` | `/api/v1/station-view/assignments/:id` | 低频启用/禁用或调整 assignment 目标和优先级。 |

`/effective` 响应要带：

```text
template
regions[]
items[]              -- 每项含 layout_area/sort_order/pinned/visible，不含旧 region_key
resolved_bindings[]
ws_subscription.var_ids[]
http_companion.current_run_required
warnings[]
```

前端工位页使用：

```text
GET /api/v1/station-view/effective?project_id=...
GET /api/v1/detection-runs/current?project_id=...
WS /api/v1/ws?topic=realtime.variables&project_id=... 或 var_id=...
```

### 6.2 主服务器后续阶段

主服务器可以增加模板设计接口和发布流程：

| 能力 | 说明 |
| --- | --- |
| 模板设计 | 主服务器维护模板草稿、预览、版本。 |
| 模板发布 | 写入共享配置表，等待同步软件同步到目标边缘。 |
| 目标分配 | 按 global/model/edge/project 分配模板。 |
| 同步状态 | 根据镜像库检查目标边缘是否已收到模板版本。 |

主服务器保存模板不是现场控制动作，不走 `/api/v1/edge-control/*`。如果主服务器需要边缘立即 reload 模板，可以后续补低风险配置 reload 命令，但必须和现场控制 scope 分开。

### 6.3 EB-066 发布、reload 和冲突策略

本阶段先收敛模板发布边界，不实现拖拽式低代码设计器，也不做多主冲突合并。

发布方向：

```text
主服务器模板设计/发布
  -> 写入主服务器配置库或共享配置源
  -> sys_station_view_* 在目标边缘查询视角可见
  -> 边缘端 /station-view/effective 按本机 edge_instance_id 和项目过滤后解析
```

边缘端本地临时覆盖允许存在，但必须遵守同一套 `target_type/target_key/priority/version/status` 规则。模板发布不是现场控制动作，不得进入 `/api/v1/edge-control/*`，也不得直接写 `sys_tags`、`sys_detection_tasks`、`detection_run_standard_items` 或运行态 `TagManager`。

reload 语义：

| 场景 | 处理 |
| --- | --- |
| 当前只读阶段 | `/station-view/effective` 每次从数据库读取模板和 assignment，不依赖独立内存模板缓存。 |
| 后续补 `POST /api/v1/station-view/reload` | 只做配置校验、默认模板补齐和缓存刷新；不启动/停止检测、不写变量、不改当前运行检测快照。 |
| 主服务器远程触发 reload | 可以后续作为低风险配置刷新命令设计，但必须和现场控制 scope 分离，并记录操作者和审计。 |

2026-06-04 EB-066 首段已实现：边缘端 `reload` 当前执行 `validate_and_seed`，没有独立模板缓存，因此它只补齐默认模板、统计 station view 表、可选返回某项目 effective 结果；不会写 `sys_detection_tasks`、`detection_run_standard_items`、`sys_tags` 或运行态 `TagManager`。主服务器同名 `POST /api/v1/station-view/reload` 只返回同步镜像诊断，`reload_mode=sync_diagnostics_only`，不调用 `/edge-control/*`。

running 检测保护：

- 工位模板只影响页面展示、区域、排序和 WS 订阅建议。
- 当前检测的上下限、报警启用、存储路由和报表请求仍以启动时冻结的运行快照为准。
- 模板变更不得修改 running 或 paused 检测任务的 `detection_run_standard_items`、`detection_run_storage_routes`、`detection_run_report_requests`。
- 如果后续模板项增加“按钮/动作”，动作仍必须调用任务系统或受控写变量服务，不能让模板表直接表达现场控制。

冲突策略：

| 冲突 | 返回 |
| --- | --- |
| 多条 assignment 命中后得到相同选择分数，且模板版本相同 | `409 station_view_template_conflict` |
| 项目不属于请求边缘 | 边缘端隐藏为 `404`；主服务器返回 `404 station_view_edge_instance_mismatch` |
| 主服务器同步库缺少模板配置 | `503 sync_not_ready` |
| 多边缘下项目未配置 `edge_instance_id`，无法唯一解析 | `409 station_view_edge_instance_ambiguous` |

冲突不能通过 assignment ID、创建时间或本地随机顺序静默兜底。修复方式应由管理员调整 `priority`、`version`、`target_key` 或禁用其中一条 assignment，然后重新发布或等待同步。

## 7. 前端实施计划

### 7.1 工位页替换硬编码

当前工位页应逐步移除：

- 固定 `metricSeed`。
- 固定 `extraRows`。
- 固定 `chartData`。
- 按数组下标匹配实时值。
- `mockProject` / `SN-20230912` 这类生产 fallback。

替换为：

```text
effective station view config
  + current run HTTP snapshot
  + realtime WS snapshot
  -> render cards / table / alarms / run panel
```

### 7.2 设计器阶段

第一阶段不必做完整拖拽设计器。可以先提供：

- 区域显示/隐藏。
- 点位分组选择。
- 条目排序。
- 卡片/表格/曲线类型选择。
- 模板预览。

等模板接口稳定后，再做拖拽布局和跨语言显示名编辑。

## 8. 与当前后端改造的关系

### 8.1 不冲突项

| 当前工作 | 关系 |
| --- | --- |
| EB-056 HTTP 控制通道 | 工位模板不是现场控制命令，不混入 `/edge-control/*`。 |
| EB-057 项目 + `var_name` 写入解析 | 工位模板也使用项目作用域解析业务名，但只用于展示和 WS 订阅，不执行写变量。 |
| EB-049 数据库同步计划 | 工位模板归类为低频共享配置，符合“配置模板可规划多向同步”的方向。 |
| EB-055 主服务器/边缘一套前端 | 有效模板接口可以在 edge/main_server role 下复用，但数据来源不同。 |

### 8.2 需要避免的冲突

| 风险 | 避免方式 |
| --- | --- |
| 把画面模板写进 `sys_tags` | 新增独立 station view 表，`sys_tags` 只保存点位资产和写入约束。 |
| 主服务器直接改边缘项目/点位表 | 项目和点位现场变更仍通过边缘服务确认。 |
| 主服务器模板绑定本地 `var_id` | 模板默认绑定业务名，边缘运行时解析 `var_id`。 |
| 边缘读到别的边缘工位 | 主服务器/同步库应写入 `sys_projects.edge_instance_id`；后端在字段有值时按本机 `edge_instance_id` 和项目归属过滤后返回。 |
| 模板同步改变 running 检测判断 | running 判断只读 `detection_run_standard_items` 快照，模板只影响显示。 |

## 9. 分阶段实施

### 阶段 A：计划和契约

1. 将本文档挂到 `AI_BOARD.md`。
2. 在数据库同步计划中把 station view 表归为低频共享配置。
3. 明确本机 `edge_instance_id` 配置来源。

### 阶段 B：边缘端只读解析

1. 增加 station view schema 和 GORM model。
2. 增加默认模板 seed 或迁移脚本，先覆盖当前工位页固定项。
3. 实现 `/api/v1/station-view/effective?project_id=...`。
4. 后端自动过滤非本边缘项目和非当前项目点位。
5. 增加 handler/service 单元测试。

### 阶段 C：前端工位页接入

1. 工位页读取 effective view。
2. 使用 effective view 的 `var_ids` 建立 WS 订阅。
3. 使用 `GET /api/v1/detection-runs/current?project_id=...` 获取检测快照。
4. 按后端返回的 region/item 顺序渲染左侧和右侧。
5. 移除生产硬编码和样例 fallback。

### 阶段 D：主服务器设计和发布

1. 主服务器增加模板设计页面。
2. 主服务器保存模板版本和 assignment。
3. 同步软件同步到目标边缘。
4. 边缘端 reload 后按本地过滤展示。
5. 主服务器查询镜像库确认模板版本到位。

## 12. 2026-06-04 最小闭环关闭结论

`review-ai` 复核后，EB-058/EB-066 的“工位自动扩容 + 模板发布/reload 最小闭环”可以关闭，关闭范围限定为当前已实现的后端 API、前端最小可见状态块、主服务器同名只读/诊断接口和保护性断言。

已关闭能力：

1. 边缘端 `GET /api/v1/station-view/effective` 按本机 `edge_instance_id` 和请求 `project_id` 过滤，只解析当前项目变量、变量组和当前 running/paused 检测快照，不把其他项目或其他边缘点位兜底给前端。
2. 前端工位页使用 `station-view/effective + detection-runs/current + WS realtime` 渲染，不再用全量变量列表做生产可见 fallback；WS 订阅只使用后端返回的 `project_id/var_ids`。
3. 主服务器同名 `GET /api/v1/station-view/effective` 只读同步库真实表，按 `project_id -> edge_instance_id` 路由和校验，不写同步业务库、不 mock、不直接执行现场控制。
4. 边缘端模板列表、模板元数据 PATCH、assignment PATCH 和 `POST /api/v1/station-view/reload` 已可用；reload 语义固定为 `validate_and_seed`，只补默认模板、做诊断和可选 effective 校验。
5. 主服务器同名模板列表和 `POST /api/v1/station-view/reload` 已可用，reload 语义固定为 `sync_diagnostics_only`，只返回同步诊断，不调用 `/api/v1/edge-control/*`。

7. reload 保护性断言已覆盖：不创建/启动/停止检测任务，不改变 running/paused 检测任务状态，不写 `sys_tags`，不修改 `detection_run_standard_items` 运行快照。
