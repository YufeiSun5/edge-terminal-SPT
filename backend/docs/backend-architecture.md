# Edge Backend Architecture

Architecture-as-code entry: `backend/docs/architecture-model/`.

That folder contains a LikeC4 model for system/component boundaries and BPMN 2.0 processes for detection-plan start and report-job generation. Use it as the review entry before adding new backend routes or duplicating existing services.

报表相关后端归属也已经收进 LikeC4。新增或修改报表 API 前，先看里面的 `报表生成全链路` 和 `报表服务内部边界` 两个视图，再判断需求属于模板资产、计划导入、同步配置写入、readiness、job worker、ReportPackage、Excel/PNG 渲染、ArtifactStore，还是报表通知。

2026-06-18 起，LikeC4 同步覆盖 watched STRING 任务请求开工链路、`project_group` 检测标准作用域、报表参数重生成 generation、以及主服务器数据下载 zip 打包边界。

This backend is initialized from the reusable SPD_JGHJ acquisition pattern:

- MQTT is the primary live data ingress.
- Gateways are data sources, not Project parents. Variables belong to a gateway/source path first, then can be assigned to a virtual Project group.
- Projects are business groupings used by pages and detection tasks. One Project may contain variables discovered from different MQTT gateways.
- The hot path is memory-first: runtime-eligible tags live in a Go `map[int64]*Tag` guarded by `sync.RWMutex`. A tag is runtime-eligible only when `enabled=true` and `project_id` is assigned.
- MQTT callbacks do not perform MySQL writes. They enqueue messages into buffered channels.
- Logic workers parse JSON and update the in-memory tag snapshot.
- Discovery workers only use the first KingIOT/KIO full snapshot after connection to create variables. Later incremental push messages update runtime values only and do not run variable discovery.
- The storage bus batches historical data into MySQL only when the variable has a Project assignment and that Project has a running detection task. During EB-037 migration they keep the compatibility narrow write to `rt_history_data` and also write registered `wide_table` routes to the generated Project table. Wide-table writes are grouped by `table/task_id/sample_bucket_ms`, so several variables sampled at the same instant become one upsert row instead of one SQL statement per variable.
- Redis is intentionally not required in this first backend slice. If needed later, add it behind a cache interface for cross-process sharing or dashboard fan-out.

## Multi-Way Configuration Sync

As of 2026-06-17, the field test scope is narrowed to 8 edge machines sharing consistent `project_id`, `var_id`, and `gateway_id`. Historical data, detection results, alarms, and task runtime records remain edge-owned and are aggregated by the main server. Low-frequency configuration tables `sys_station_view_*`, `sys_detection_standards/items`, and `sys_task_flows/vars` can be written by either edge or main server through the synchronized database.

Edge config now includes `sync.node_id`, `sync.id_block_size`, and `sync.config_watch_interval_seconds`; config write paths generate BIGINT primary keys as `node_id * id_block_size + sequence` to avoid auto-increment collisions. Syncable config rows record `sync_scope`, `edge_instance_id`, `updated_by_node`, `updated_by_user`, and `updated_at`. Parent table `version` is the completion watermark: child rows are written first, then the parent `version/updated_at` is updated last.

The edge watcher polls station-view, detection-standard, and task-flow watermarks. Task-flow changes reload enabled flows visible to the local `edge_instance_id`; detection-standard changes affect only future starts or explicit apply-config; station-view pages reread effective/items after sync. Runtime protection adds `edge_instance_id` to `sys_detection_tasks` and `task_flow_runs`; edge startup only restores local running tasks and local enabled task flows. Main server configuration writes do not replace edge-control for realtime values, WS, detection control, or KIO/variable writes.

## Runtime Flow

```text
MQTT Gateway
  -> Discovery Channel -> sys_tags discovered variables
  -> Logic Channel -> Logic Workers -> runtime-eligible topic indexed tags -> cleaning filter -> TagManager Map
  -> if Project has running detection task -> StorageBus -> bucket(project_id + table_name) -> rt_history_data insert + project wide-table upsert
  -> if running standard item enables alarm -> Alarm Channel -> MySQL Batch Insert/Recover Update -> Notify Channel -> sys_notifications + WS notification.event
```

Realtime values are normalized before they are exposed to business code. The runtime cleaning filter performs type conversion, scale/offset, quality normalization, suspicious-value filtering, debounce, runtime deadband, and runtime first-frame handling. It only handles known business variables that have been assigned to a Project and enabled; newly discovered unknown variables remain database candidates until assignment. The filter only updates the in-memory tag runtime state and must not query MySQL, calculate limits, or write history directly.

The current project concept is represented by `sys_projects.project_id`. `site_no` is an auxiliary site/project number, not the realtime map key. `edge_instance_id` is the edge ownership hint used by edge-local runtime loading, station views, and main-server routing: when it is present, an edge only serves matching Projects and the main server rejects mismatched `project_id + edge_instance_id` requests. `project_group` is the business applicability key for a batch/class of Projects that share the same detection standards by variable name; it is intentionally separate from `model_name`, because one model may still have different acceptance rules by customer, line, or batch. Project display labels come from `display_name`, `display_name_en`, and `display_name_ja`, with fallback to `name` and `project_code`.

The EB-033 runtime memory layers are:

- `GlobalTagMap`: `var_id -> *Tag`, the only stable realtime value and cleaning state for a variable.
- `GatewayTopicIndex`: `gateway_id + topic -> []*Tag`, the hot-path lookup that avoids scanning all tags on every MQTT message.
- `ProjectRealtimeView`: `project_id -> []var_id`, used to assemble project pages and WebSocket realtime variables.
- `ProjectRunContext`: `project_id -> ActiveRunContext`, used for the active detection task's store/check rules and per-task limit alarm state.
- `RuntimeDraftService`: `namespace + scope_type + scope_id -> RuntimeDraft`, a generic in-memory scratchpad for pre-run page drafts. It is intentionally edge-local and volatile: no MySQL table, no Redis, no main-server cache. First registered namespace is `station.detection_preload` for station detection preload drafts, scoped by `project`, with `expected_revision` optimistic locking, 512 KiB max payload, 24h default TTL, and write rejection while that Project has a running detection task.

Limits and detection rules do not belong in `GlobalTagMap`. They are read from detection standards and frozen into run context/snapshots. Running business limit alarms are evaluated from `ProjectRunContext` and `detection_run_standard_items`: data changes and the cycle scanner call the same in-memory state machine, then enqueue `DetectionLimitAlarmEvent` records to the async `Alarm` channel. Future running-config updates must update `ProjectRunContext` with audit/business events, not mutate global tag values.

Runtime drafts are not run snapshots. Detection start may reference a draft through `runtime_draft:{namespace,revision}`; the backend resolves it by `project_id`, validates revision/config hash/items, converts it to `StartDetectionOptions.CustomItems` and `ProcessParams`, and only clears it after `sys_detection_tasks` plus frozen snapshots are created successfully. If the referenced standard's current `config_hash` differs from the draft hash, start fails with `409` and stable code `runtime_draft_stale`; callers must reapply the detection configuration instead of silently falling back to a different start path. During a running detection, frontend pages must render `detection-runs/current.standard_items` and `detection_run_storage_routes`, not the mutable draft.

## Backend Module Boundaries

- `internal/runtime/kernel.go` wires startup, middleware, health, auth entrypoints, services, and route registration only.
- `internal/runtime/handlers` owns HTTP parameter parsing, permission binding, status-code mapping, and response DTO shape for users, Projects, variables, history, detection standards/runs, gateways/KIO, and report templates.
- `internal/services` owns business invariants and runtime coordination, such as TagManager reloads after variable changes and TaskManager updates after detection run state transitions.
- `internal/database` keeps one `Repository` type in one package, split by business file for auth, gateways, variables, Projects, history, detection, and reports.
- `internal/models` keeps one package for GORM models and runtime tag DTOs, split by domain file without changing table names, JSON fields, or GORM tags.

## Core Data Model

- `sys_gateways`: MQTT station/source configuration. `edge_instance_id` marks the owning edge node; edge startup loads enabled gateways for the local `Auth.EdgeInstanceID` plus legacy unassigned gateways, and main-server synchronized gateway views expose the field for diagnostics.
- `sys_tags`: variables discovered from the first full snapshot or maintained manually. Key fields are `gateway_id`, `source_path`, `source_type`, `project_id`, `var_group`, `enabled`. `source_type=mqtt` is auto-discovered ingress, `source_type=manual` is manually mapped upstream data, and `source_type=virtual` is a backend/user-created variable with `gateway_id=0`, `discovered=false`, and `placeholder=true`. Auto-discovered unknown variables are inserted as disabled, unassigned candidates; only tags with `enabled=true` and an assigned `project_id` are loaded into the runtime `TagManager` for cleaning, WebSocket snapshots, storage, and detection. Variable storage timing, target table, dynamic column, start snapshot, and change deadband are not variable attributes; they are owned by `sys_storage_routes`. Write constraint fields (`rw_mode`, `writable`, `write_source_id`, `write_path`, `write_data_type`, `write_min`, `write_max`, `write_enum`, `write_requires_audit`) are the only backend-approved basis for future API/WS variable writes. Debounce fields (`suspicious_value`, `debounce_threshold`, `debounce_ms`, `deadband`) are stored in the variable config for runtime filtering. Variable default limit fields (`default_alarm_enabled`, `default_limit_ll`, `default_limit_l`, `default_limit_h`, `default_limit_hh`, `default_limit_deadband`, `default_violation_hold_ms`, `default_recover_hold_ms`) are asset defaults; they do not live in `GlobalTagMap` and do not override detection-standard business limits.
- `sys_storage_routes`: dynamic storage route metadata for variables assigned to Projects. A route owns `storage_target`, target table, dynamic column, column type, form/query aliases, `trigger_mode`, `cycle_ms`, change `deadband`, `store_on_start`, and `enabled`. Default routes are created as disabled suggestions only with `cycle_ms=20000`; users or backend configuration must enable and tune them. The default table is `rt_project_{project_id}_data`, but a user-provided backend-validated table name is also allowed. A variable may have multiple routes, and all route table and column identifiers must be backend-validated and registered here before writes use them.
- `sys_task_rules`: legacy first-stage task trigger rules. This is no longer the active orchestration model for new work; new task logic must use `sys_task_flows` and `sys_task_flow_vars` so runtime data-change handling reaches flows through the `var_id -> flow_ids` reverse index. Any remaining rows or tests are compatibility/reference material until the legacy path is explicitly removed.
- `sys_task_flows`: developer-authored conditional event tasks. A task flow belongs to one project, declares `trigger_type`, optional JavaScript condition, `action_type`, script/action payload, optional `steps_json`, timeout, cooldown, hold time, and priority. `steps_json` is the preferred platform model for multi-step built-in modules; old `action_type/action_payload/action_script` remains a single-step compatibility path. The API contract recommends an ordered array, and the executor also accepts a single step object as one-step shorthand for developer tooling tolerance. Data-change tasks are not scanned globally; they are reached through `sys_task_flow_vars`. Built-in modules currently cover storage snapshot/prepare, context set, JavaScript, controlled variable write, detection start/stop/pause/resume, fixed-duration stop guard, qualified-hold stop guard, detection alarm mute, running limit update, feature refresh, report result registration, and controlled HTTP request. Formal business parameters must come from watched `STRING` virtual variables whose values are JSON objects. Step parameter bindings support `literal`, `trigger_param`, `event`, and `context` sources, plus `optional=true` and `default` so templates can represent optional parameters without failing when a key is omitted. JavaScript can read multiple realtime variables through `realtime.get`, `realtime.getMany`, `realtime.getByName`, and `realtime.project`; `realtime.get/getMany/write` accept decimal-string 64-bit variable IDs and return `var_id_text` in snapshots/write results. The JavaScript `trigger` object and task-flow run context also expose `trigger_var_id_text`. JavaScript writes and `builtin.write_variable` are limited to virtual variables and write audit rows, with `trigger=false` by default for JavaScript. Physical variable downlink must use WS/HTTP `VariableWriteService + KIOWriteService`, not the task executor's in-memory write path. STRING task parameter payloads are capped at 256 KiB; oversized or invalid JSON is rejected by the task module instead of being treated as a valid command. The 520-item custom detection payload budget is currently about 166 KiB, with millisecond-level parse/convert cost, so it remains a low-frequency command payload rather than a realtime data stream.
- `sys_task_flow_vars`: task-to-variable references. Runtime builds `var_id -> flow_ids` from rows with role `watch`, so a changed variable only evaluates tasks that depend on it. Roles `read` and `write` document script access intent for UI and review.
- `task_flow_runs`: execution records for task flows. Each run stores trigger metadata, origin/depth recursion metadata, input snapshot, result JSON, error text, script logs, duration, and status. The executor builds a per-run context and passes values between built-in modules through that context instead of using global temporary state.
- `task_flow_sql_logs`: SQL statements executed by developer scripts through the shared repository connection. Scripts may use `db.query` and `db.exec`, but they do not create their own database connection and each statement is logged with duration and error text.
- `sys_projects`: virtual Project groups. These drive auto-expanded pages and detection tasks. `project_group` groups Projects that can share one detection standard by identical business `var_name`; `model_name` remains descriptive equipment/model metadata and must not be the only standard applicability key. `edge_instance_id` should be populated in main-server/database-sync deployments so edge startup `LoadTags(edgeInstanceID)`, station view resolution, and main-server route selection can keep Projects on their owning edge; empty values remain a legacy compatibility fallback for local-only data. `name` remains the legacy/default name; UI-facing labels should use `display_name`, `display_name_en`, and `display_name_ja` with fallback to `name` or `project_code`.
- `sys_project_members`: local edge Project membership/follow records. Each row links one local `sys_users` account to one Project, stores a Project-local `member_role`, and controls whether that user receives Project-scoped notifications through `notify_enabled`. Notification targeting uses this table only when a Project has configured members; Projects without configured members temporarily keep the old all-enabled-users fallback so existing deployments do not silently lose detection notifications before the UI config is filled.
- `sys_station_view_templates`, `sys_station_view_regions`, `sys_station_view_items`, and `sys_station_view_assignments`: low-frequency station-screen layout configuration. Templates define the station page card pool and list layout, item order, pinned state, display metadata, and binding intent; assignments select a template by Project, edge instance, model, or global fallback. Public DTOs use `layout_area=card_pool|list_layout`; `region_key` is a deprecated storage compatibility field only and must not be used by new frontend/API contracts. The effective station view resolver never trusts a template to expose variables directly: if `sys_projects.edge_instance_id` is set it must match the local edge instance, then the resolver resolves `var_group`, `var_name`, or current detection item bindings only inside the requested `project_id`, and returns the exact WS `var_ids` the page may subscribe to. These tables are suitable for main-server design/publish plus external database sync, while edge runtime remains responsible for final project filtering. If multiple assignments resolve to the same final score and template version, the resolver returns `409 station_view_template_conflict` instead of using assignment ID as a hidden tie-breaker. Low-frequency metadata and item configuration operations update `sys_station_view_items.sort_order/pinned/visible` but do not mutate running detection snapshots or realtime tags.
- `sys_detection_standards`: reusable detection standard headers. Detection standards are not inherently one-device configs: they may be true global (`project_id IS NULL` and empty `project_group`), project-group/batch scoped (`project_group`), or single-project scoped (`project_id/project_code`). `project_id/project_code` can still be an import anchor, but `project_group` is the intended middle grain when a batch of Projects share the same standard. `sync_scope` only describes database synchronization scope and must not be used as business applicability. When a run starts for a concrete Project, the backend remaps standard items to that Project's enabled `sys_tags` by business `var_name` before freezing `detection_run_standard_items`; if a required item cannot be mapped or the target Project has multiple enabled variables with the same `var_name`, start fails instead of freezing another device's `var_id`. A standard carries a version, a backend-calculated `config_hash`, and may reference a default Excel report template through `report_template_id`. The hash is SHA-256 over the normalized standard header plus standard items, excluding row IDs and timestamps; item order is canonicalized so equivalent item sets hash the same. Standard create/update/replace-items recompute the hash, and version is the synchronization waterline written after the affected config rows and hash are updated.
- `sys_detection_standard_favorites`: per-user favorite detection-standard links for the configuration UI. Favorites are query/configuration state, not a live control action.
- `sys_detection_standard_recents`: recently used detection standards. Task-system detection start records recent usage when it starts from a `standard_id`; `user_id=0` represents system/task-flow usage when no local UI user is attached.
- `sys_detection_standard_items`: reusable per-variable detection rules under one standard. `check_enabled` controls pass/fail evaluation participation and also makes the variable mandatory for this run's history storage; `alarm_enabled` controls whether a detected violation should create a limit-alarm lifecycle record; `store_enabled` remains an explicit storage request for standard items that are not checked. `check_cycle_ms` controls only the business evaluation cadence and is separate from route storage cadence; it must never be used as storage `cycle_ms` or as a storage fallback. `check_on_start` controls whether detection start should immediately evaluate the current value. Numeric limits are `limit_ll`, `limit_l`, `limit_h`, and `limit_hh`; check semantics are described by `check_method`, `target_value`, `limit_deadband`, `violation_hold_ms`, `recover_hold_ms`, and `quality_policy`.
- `sys_detection_plans`: externally dispatched pending detection plans synchronized by database sync software. A plan stores source identity (`source_system/external_plan_id/plan_no`), business inputs (`factory_no/device_model/customer_name/test_item_*`), the required `standard_code`, and optional `report_request_json`; `factory_no` is intentionally repeatable so one serial number can carry several different planned tests. Plan status is limited to `pending`, `starting`, `started`, and `cancelled`: station start moves `pending -> starting`, resolves the local detection standard by `standard_code`, builds a `command=start_detection` JSON request, writes the watched STRING task request variable through `VariableWriteService`, and waits for the configured task flow to create a real `sys_detection_tasks` row through `builtin.start_detection_run`. Only then does it write `started_task_id`, owner edge/project fields, and `started_at` before marking `started`. If local config, the watched variable, the task flow, or task creation is not ready, the plan returns to `pending` with `error_message`; the plan table does not create a separate background retry queue or direct-start fallback.
- `sys_detection_tasks`: one running or paused task per Project. It stores run metadata such as `factory_no` business serial number, optional `customer_name` and `device_model`, unique detection `test_no`, whether this run enables limit checking (`limit_check_enabled`), whether this run may use detection config (`config_enabled`), current config lifecycle state (`disabled|pending|waiting|applied|failed`), current applied config identity (`config_code/config_name/config_version/config_hash`), and `current_config_revision`. It also stores the end policy (`manual`, `fixed_duration`, or `qualified_hold`), planned duration, qualified hold duration, expected end time, pause start time, accumulated paused duration, stop type, operator note, optional custom-config JSON, and the frozen report template identity used by that run. `factory_no` is intentionally repeatable for business lookup; `test_no` remains the unique detection identifier and may be auto-generated by the edge when omitted. `custom_config_json` is compact trace metadata for custom starts, not the run-time judgement source; custom item snapshots are still frozen into `detection_run_standard_items`. Task-flow starts may also freeze low-frequency process/report parameters such as `process_params.inlet_area_m2`, the matching `plc_writes` trace, and `report_request` so the same request can drive local detection, controlled PLC writes, and main-server report generation without duplicating frontend input. `status=paused` removes the run from runtime storage/alarm evaluation until it is resumed; it does not delete the run snapshot. Paused time does not count toward accumulated detection duration: resume shifts `expected_end_at` by the pause delta, and `detection_run_summaries.duration_ms` subtracts `paused_duration_ms` plus the current open pause segment. Running tasks loaded on backend startup recover fixed-duration and qualified-hold guards from this row.
- `detection_run_standard_items`: immutable standard item snapshots copied when a detection run starts or when an explicit running-config apply command succeeds. It freezes the check/alarm/store flags, `check_cycle_ms`, `check_on_start`, limit config, check semantics, the variable default limit snapshot (`variable_default_*`) for later judgement, plus `config_revision/effective_from/effective_to`. Running config apply closes the old open revision with `effective_to` and inserts a new revision; it does not overwrite old rows and does not automatically follow later database synchronization changes. Task-flow custom detection starts can also freeze `custom_items` directly into this table with `standard_id=0/standard_item_id=0`; this is still the single run-time source of truth for judgement. Later judgement should read this table, not the latest standard or variable configuration. `PATCH /variables/{id}` may sync only the `variable_default_*` snapshot for currently running tasks when `apply_to_running=true`; it must not overwrite the business limit fields.
- `runtime_settings`: low-frequency runtime parameter storage. Detection config readiness uses `detection_config_ready_timeout_ms` and `detection_config_ready_interval_ms`, defaulting to 60000 and 5000. The edge loads these values into memory and uses them for main-server initiated config wait/apply wait loops; the hot start path must not depend on repeatedly reading MySQL.
- `detection_run_storage_routes`: immutable storage route snapshots copied when a detection run starts. Startup ensures a default route exists for each checked or explicitly stored standard item; checked variables force that default route on so values needed for judgment and reports are persisted. The run snapshot also freezes every currently enabled `sys_storage_routes` row for the project, even when that variable is not in the detection standard, so configured process variables are stored under the same `task_id/test_no`. It freezes each enabled route's target, Project table, dynamic column, column type, form/query aliases, trigger mode, cycle, deadband, and start-storage flag. Detection start prepares the Project-wide table and missing dynamic columns from this snapshot before the run becomes available to the storage hot path. `ActiveTask` and `StoreTask` carry these route snapshots so the store worker can write without querying route metadata on every sample.
- `detection_run_notes`: multiple memo/remark rows attached to one detection run.
- `detection_run_events`: lightweight event timeline rows for one detection run. It records run lifecycle events such as start, normal stop, and abnormal stop. Alarm details stay in `detection_limit_alarms` to avoid duplicating high-volume per-variable alarm rows.
- `detection_run_summaries`: one aggregate row per detection run. It stores result status, duration, history row count, alarm totals, active/recovered counts, above/below limit counts, first/last alarm time, and the last refresh time.
- `detection_run_features`: per-run numeric feature rows grouped by variable. The first slice stores `sample_count`, `avg_value`, `min_value`, `max_value`, `first_sample_time`, and `last_sample_time`, calculated from persisted history rows after a run stops or when explicitly refreshed. API responses include `var_id_text` for exact browser round-tripping.
- `detection_limit_alarms`: unified limit alarm lifecycle records. `scope=detection` rows represent one variable's violation inside a detection run and keep task, standard item, variable display, limit, quality, status, and duration snapshots. `scope=default` rows represent variable-asset default alarms, use `task_id=0`, do not use detection mute, and are driven from `sys_tags.default_*` fields. Both scopes share the `Alarm` queue and notification path; detection summaries continue to aggregate by `task_id`, so default rows do not affect run OK/NG summaries. `GET /api/v1/limit-alarms` is the unified read model for both scopes and returns `var_id_text`.
- `sys_notifications`: edge notification bodies persisted from `Channels.Notify`. Each row stores a stable event UID, type, level, target scope (`all`, `user`, `role`, or `project`), Project/task/variable context, message, JSON payload, occurrence time, and optional `expires_at`. Alarm notification types (`alarm.*`) expire from the notification center 90 days after `occurred_at`; non-alarm notifications do not expire by default. These rows support UI notification history but do not replace domain source tables such as `detection_run_events`, `detection_run_summaries`, or `detection_limit_alarms`.
- `sys_notification_recipients`: per-user read state for persisted notifications. Recipient generation now honors `target_type=all|user|role|project`: `all` fans out to all enabled local edge users, `user` targets one enabled local user ID, `role` targets enabled local users with that role, and `project` targets enabled users listed in `sys_project_members` with `notify_enabled=true`. If a Project has no configured member rows, project notifications fall back to all enabled local users for transition safety. Each recipient row stores its own `read_at`.
- `main_notification_reads`: main-server-owned read-state overlay for synchronized edge notifications. It stores `notification_id`, main-server `user_id`, and `read_at`, with a unique row per notification/user. Main-server notification list and unread-count queries use `COALESCE(main_notification_reads.read_at, sys_notification_recipients.read_at)` so main-server users can mark synchronized edge notifications read without mutating externally synchronized `sys_notification_recipients`.
- Runtime notifications: edge events carried by `Channels.Notify`, persisted by `NotificationDispatcher`, and fanned out online by `NotificationHub`. Current notification types include `alarm.limit.enter`, `alarm.limit.recover`, `alarm.limit.level_change`, `detection.run_started`, `detection.run_stopped`, `detection.run_abnormal_stop`, `detection.run_paused`, `detection.run_resumed`, `detection.result_ok`, `detection.result_ng`, and `detection.features_updated`.
- Edge service WebSocket: `GET /api/v1/edge-control/ws` requires `service_realtime_read` and reuses the same edge WS message protocol as `/api/v1/ws` for realtime variables, detection runs, notifications, heartbeat, ack, and error messages. It exists for the main-server WS facade and is not a browser raw proxy target.
- Main-server WS facade: `main-server/backend` exposes `GET /api/v1/ws` to main-server JWT users. It accepts browser `access_token` query auth, resolves the target edge through the configured `edges[]` registry by `project_id`, `task_id`, or explicit `edge_instance_id`, rejects mismatched project/edge combinations, connects to that edge service WebSocket with its service token, injects top-level `edge_instance_id` into bridged realtime and notification messages, and converts supported `command.*` messages into existing `/api/v1/edge-control/*` HTTP commands so edge-side command lifecycle, idempotency, operator mapping, and audit remain authoritative. `topic=notifications` is supported for main-server notification-center live refresh; missed online events remain recoverable through HTTP notification list/unread-count APIs. The bridge read limit is 4 MiB to allow large initial snapshots while the future batching contract is still pending.
- `sys_report_templates`: registered Excel report templates. The database stores metadata, file references, version, and optional `params_schema_json` for formula/input parameters; it does not store file binary content. The main-server report worker seeds a system default template when its schema is ensured: `template_code=SPINDLE_DEFAULT_REPORT`, `version=1`, `file_ref=templates/default-report-template.xlsx`. That default row is enabled and points to an `.xlsx` file in the main-server local report asset store; it is usable only when the report request explicitly selects it.
- `detection_run_reports`: generated report file records attached to one detection run.
- `detection_run_report_requests`: per-run report request snapshots for main-server consumption. One row means one report request for that detection run, and the row may reference one variable or a group of variables. Report request input binds variables by business `var_name`; the edge backend resolves each name under the concrete `project_id` and freezes the resulting `var_id` into this snapshot. Input `var_id/var_id_text/var_ids` is rejected for report binding so templates and plans stay reusable across AC-01..AC-08. Rows freeze `task_id/test_no/project_id/project_code`, optional template snapshot (`template_id/template_code/template_version`), first-variable summary fields for compatibility, `variables_json` for the full variable list, `params_json` for template formula parameters, `status=pending`, and legacy reserved fields `ext_1/ext_2/ext_3`. This table is a request/snapshot handoff, not an Excel file table; generated files still use `detection_run_reports`.
- Main-server report artifacts now include a `ReportPackage` contract. The JSON manifest stores `report_package`, and the generated workbook keeps internal trace sheets such as `Report_Package` hidden while curve images are inserted into the mapped customer sheet. One `detection_run_report_requests` row produces one Excel file; a task can therefore produce multiple files such as comprehensive, temperature, and humidity reports instead of forcing those reports into one workbook. `ReportPackage` includes task identity (`edge_instance_id/task_id/test_no/project_id/project_code`), the report request, frozen variables, full-detection metrics from `detection_run_features`, effective limits from `detection_run_standard_items` with variable-default fallback, and `params_json`. The main-server worker fills requested workbook sheet/cell values from `task.*`, `request.*`, `summary.*`, `param.*`, `variable.*`, `metric.*`, or `limit.*` using `sys_report_templates.params_schema_json.cell_mapping` as the template default; if `params_json.cell_mapping` is present on a request, it overrides the template default. `cell_mapping.chart_sheet` and `cell_mapping.chart_cell` control curve image placement; without `chart_sheet`, images use the mapped business sheet. Required missing values fail the job. When a request template cannot be found or opened, the job fails and does not silently fall back to `SPINDLE_DEFAULT_REPORT`. Generated manifest and workbook files are addressed by `artifact_key` through the main-server local `ArtifactStore`; new job statuses are `pending/waiting_for_sync/generating/succeeded/failed`, with temporary read compatibility for legacy `waiting/running/success`. The worker can auto-enqueue stopped tasks that already have synchronized report requests and no job. The continuous qualified two-hour window metric is calculated by scanning synchronized history per requested variable, resetting the window on limit/quality violation, and returning `available` only when the continuous qualified span reaches at least two hours.
- `rt_history_data`: legacy/compatibility narrow history table with `project_id`, `task_id`, and `test_no`.
- `rt_project_{project_id}_data`: generated Project-wide tables for this project. Fixed columns include `task_id`, `test_no`, `project_id`, `project_code`, `sample_time`, and `sample_bucket_ms`; dynamic columns are added from `detection_run_storage_routes`. DDL is a low-frequency startup/config action and must not run in the MQTT write hot path. Schema prepare also repairs legacy generated wide tables that are missing `project_id` or `project_code`, and default `rt_project_{project_id}_data` tables backfill `project_id` from the table owner.
- `sys_users`: local edge users with bcrypt password hashes, role, enabled flag, and `permissions_version`.
- `sys_service_clients`: main-server service credentials. Only token hashes are stored; scopes control service calls. `allowed_cidrs` optionally restricts service calls by source IP/CIDR, and `last_used_at` is updated on successful service-token authentication.
- `sys_sso_tickets`: one-time SSO handoff tickets. Only ticket hashes are stored and successful verification marks `used_at`.
- `sys_audit_logs`: security and write-action audit records. Sensitive token/password values must not be stored in audit detail.
- `edge_control_commands`: service-to-service command lifecycle records for the main-server HTTP control channel. The unique key is `client_id + command_id`; records store mapped operator fields, `edge_user_id`, action, target, request JSON, status, result JSON, error code/message, and received/completed timestamps. Repeated commands return the stored result instead of re-executing field actions. `GET /api/v1/edge-control/commands/:command_id` lets the same service client read its command status without exposing `request_json`.

## Basic API Surface

API naming rules for this project:

- Prefix business APIs with `/api/v1`.
- Use short business nouns: `variables`, `projects`, `gateways`, `detection-runs`.
- Use `PATCH` for assignment/configuration changes.
- Use explicit command endpoints only for industrial control transitions such as stopping a run.

Current endpoints:

- `POST /api/v1/auth/login`: public local-user login, returns `access_token`, user, and permissions.
- `GET /api/v1/auth/me`: authenticated local-user profile and permissions.
- `POST /api/v1/auth/logout`: authenticated local-user logout acknowledgement.
- `POST /api/v1/auth/sso-ticket`: authenticated local-user SSO ticket creation, requires `sso_handoff`.
- `POST /api/v1/auth/sso-ticket/verify`: main-server service verification endpoint, requires `service_sso_verify` service scope.
- `POST /api/v1/edge-control/detection/start`: main-server service control endpoint, requires service scope `edge.detection.start`. Request uses the common `{command_id, operator_id, operator_username, operator_name, reason, payload}` envelope; `payload` follows the detection start fields `project_id/test_no/mode/standard_id/duration_sec/operator_note/report_template_id/report_request`. The handler maps `operator_username` to an enabled local edge user, records `edge_control_commands`, then starts the run through `DetectionRunsService`.
- `POST /api/v1/edge-control/detection/stop`: main-server service control endpoint, requires `edge.detection.stop`. `payload.task_id` is required and `payload.reason` or envelope `reason` is recorded as the stop reason. It reuses `DetectionRunsService.Stop`.
- `POST /api/v1/edge-control/detection/abnormal-stop`: main-server service control endpoint, requires `edge.detection.stop`. `payload.task_id` is required and a reason is required by the service path. It reuses `DetectionRunsService.AbnormalStop`.
- `POST /api/v1/edge-control/detection/pause`: main-server service control endpoint, requires `edge.detection.stop`. `payload.task_id` is required and `payload.reason` or envelope `reason` is recorded as the pause reason. It reuses `DetectionRunsService.Pause`, removes the run from `TaskManager`, and writes the pause lifecycle event through the service.
- `POST /api/v1/edge-control/detection/resume`: main-server service control endpoint, requires `edge.detection.start`. `payload.task_id` is required. It reuses `DetectionRunsService.Resume`, reloads the run snapshot into `TaskManager`, and keeps paused time out of fixed-duration accumulation.
- `POST /api/v1/edge-control/detection/mute-alarms`: main-server service control endpoint, requires `edge.alarm.mute`. `payload.task_id` is required and the target task must be `running`. It mutes active in-memory detection alarm states through `DetectionRunsService.MuteDetectionAlarms`, records command/audit/event evidence, but does not yet persist a `muted` flag on `detection_limit_alarms` because the table has no such column.
- `POST /api/v1/edge-control/detection/update-limits`: main-server service control endpoint, requires `edge.detection.limit_update`. `payload.task_id` and `payload.items[]` are required; each item accepts `var_id` as number/string and optional `alarm_enabled`, `check_enabled`, `store_enabled`, `check_on_start`, `check_cycle_ms`, `violation_hold_ms`, `recover_hold_ms`, `limit_ll`, `limit_l`, `limit_h`, `limit_hh`, and `limit_deadband`. The target task must be `running`; the service updates `detection_run_standard_items`, refreshes the running task map, and writes a `limits_updated` event.
- `POST /api/v1/edge-control/detection/refresh-features`: main-server service control endpoint, requires `edge.feature.refresh`. `payload.task_id` is required. It refreshes `detection_run_features` and writes a `features_updated` event through `DetectionRunsService`.
- `POST /api/v1/edge-control/detection/report-requests`: main-server service control endpoint, requires `edge.report.request`. `payload.task_id` and `payload.report_request` are required. The request parser is the same as detection start `report_request`: it accepts `reports[]`, variable names through `variables[].var_name` or `variable_names[]`, template identity, and `params`, then appends rows to `detection_run_report_requests` for main-server sync/consumption. It rejects `var_id/var_id_text/var_ids` as report variable input and resolves names against the task's project before freezing the concrete IDs.
- `POST /api/v1/edge-control/detection-plans/{id}/start`: main-server service control endpoint, requires `edge.detection.start`. `payload.project_id` is required; `payload.operator_note`, `payload.request_var_id`, and `payload.request_var_name` are optional. The handler maps the main-server operator to a local enabled edge user and records `edge_control_commands`, then `DetectionPlansService` moves the plan to `starting`, resolves `standard_code`, builds the same JSON task request used by现场开工, and writes the watched STRING virtual variable (default `task_request`) through `VariableWriteService`. The real `sys_detection_tasks` row must be created by the configured `data_change` task flow and `builtin.start_detection_run`; the plan is marked `started` only after that task is observed. If the variable, task flow, or config is not ready, the plan returns to `pending` with `error_message`. The main server must not write synchronized `sys_detection_plans` or `sys_detection_tasks` directly.
- `POST /api/v1/edge-control/variables/write`: main-server service control endpoint, requires `edge.variable.write`. `payload` accepts `var_id` as number/string or `project_id/project_code + var_name`, plus `value`, `quality`, `trigger`, `wait_ack`, and `ack_timeout_sec`. It reuses `VariableWriteService`, so virtual variables update memory and can trigger task flows, while physical variables still require write constraints and publish through `KIOWriteService`. Successful responses return `result.var_id_text`, `result.broker_accepted`, `result.project_confirmed`, and optional `result.kio`. If KIO publish/ack fails after a partial write attempt, the non-2xx response still includes `result` so PID/operator pages can show whether the broker accepted the command and whether KIO timed out, rejected, or confirmed it.
- `GET /api/v1/variables`: all configured and discovered variables manageable by the current edge. It supports `gateway_id`, `project_id`, `assigned`, `project_code`, `var_group`, `writable`, `enabled`, `discovered`, `source_type`, `keyword`, `edge_instance_id`, `limit`, and `offset` filters. When `limit` or `offset` is present, the response is `{items,total,limit,offset}` with `limit` capped at 500; without pagination parameters it keeps the legacy `TagConfig[]` response for compatibility. Edge-side requests are always constrained to local `Auth.EdgeInstanceID`; an explicit non-local `edge_instance_id` returns an empty list instead of exposing another edge's variables. Assigned variables are filtered through `sys_projects.edge_instance_id`, while unassigned candidate variables remain visible only when their gateway is local, legacy-unassigned, or `gateway_id=0` for virtual/manual pool entries. `device_id` is no longer an active query alias and is rejected as `400 unsupported_query_param`; callers must use `project_id`. PID and other operator pages should use this low-frequency configuration list to resolve editable variables, then use realtime APIs or WS for values.
- `POST /api/v1/variables`: create a virtual variable (`source_type=virtual`) or a manually mapped variable (`source_type=manual`). Virtual variables support `INT`, `FLOAT`, `BOOL`, and `STRING`, use `gateway_id=0`, and become visible in realtime snapshots only after they are enabled and assigned to a Project.
- `PATCH /api/v1/variables/{variable_id}`: update variable attributes such as display name, type, unit, scale, cleaning fields, write constraints, default limit/alarm fields, and enabled state. Variable storage cadence and table/column routing are not changed here. Optional `apply_to_running=true` syncs the variable default limit snapshot into current running task items for the same variable without changing business standard limits. A missing variable returns `404`.
- `POST /api/v1/variables/bulk-remap/kio-projects`: batch helper for KingIOT/KIO local commissioning. It ensures project codes such as `AC-01` through `AC-08`, maps raw names like `台1_39` to project 1, keeps `raw_name/source_path` unchanged, writes business `var_name` such as `kio_01_39`, fills `display_name/display_name_en/display_name_ja`, enables matched variables by default, creates disabled default storage-route suggestions, reloads `TagManager`, and returns per-variable remap evidence including `var_id_text`. If an existing default storage route is still disabled, its generated column metadata is synchronized to the new business `var_name`; enabled routes are left unchanged. Request options include `project_count` (default/max 8), `project_code_prefix`, display prefixes, `raw_project_prefix`, `var_group`, `var_name_prefix`, `remap_var_name`, `enable`, and `dry_run`.
- `GET/POST/PATCH/DELETE /api/v1/storage-routes`: list and manage route-owned storage configuration. Routes are where users choose the target table, column, trigger mode, cycle, change deadband, start snapshot behavior, and enabled state. Request `var_id` may be a JSON string when the frontend needs exact 64-bit IDs, and responses include `var_id_text` for exact reuse. Missing routes return `404`, and routes already frozen into a detection run return `409 Conflict` on delete.
- `GET /api/v1/task-modules`: list backend-supported task modules for the frontend dynamic task editor. Requires `system_settings`. Current modules include detection start/stop/pause/resume, fixed-duration guard, qualified-hold guard, alarm mute, running limit update, feature refresh, storage snapshot/prepare, controlled variable write, report registration, controlled HTTP request, context set, and JavaScript. Detection start declares `custom_items`, `limit_check_enabled`, `end_policy`, `duration_sec`, `qualified_hold_ms`, `process_params`, and `plc_writes` so future editors can bind the full watched STRING task request variable: detection config, process/report parameters, and controlled PLC write traces. `builtin.refresh_features` refreshes `detection_run_features`, writes a `features_updated` detection event, and publishes `detection.features_updated` through the notification bus. The JavaScript module schema also exposes its runtime API names so the frontend can render developer help without hard-coding backend capabilities; runtime variable helpers accept string IDs and return exact `var_id_text` fields.
- `GET /api/v1/task-flow-templates`: list backend-provided task-flow templates for the frontend task editor. Requires `system_settings`. Templates now cover variable-request start/stop, fixed-duration detection, qualified-hold detection, pause, resume, storage snapshot, alarm mute, running limit update, feature refresh, report registration, and controlled write-variable command. The start, fixed-duration, and qualified-hold detection templates all place `builtin.write_control_variables` before `builtin.start_detection_run` when `plc_writes` is present, so process parameters such as inlet area can be written to PLC before the run snapshot is created. These templates also pass `runtime_draft`, `operator_note`, and `report_template_id` through to the detection start module. The designed path is explicit: the watched STRING payload carries `runtime_draft` and the intended `end_policy`, and the task-flow step maps those fields. Compatibility fallback remains only for existing old task flows or abnormal requests; when it is used, the task-flow run records `WARN start_detection fallback ...` in `script_logs` and the start step result.
- `GET/POST/PATCH /api/v1/task-flows`: developer task-flow configuration. Requires `system_settings`. Task flows support data-change/manual/project lifecycle/schedule triggers. Automatic execution currently covers data-change, project lifecycle events, and schedule flows. A detection run start emits `project_start`; normal, task-flow, or abnormal stop emits `project_end`. `schedule_interval_ms` controls scheduled execution frequency; if it is omitted but `cooldown_ms` is set on a schedule flow, the backend temporarily uses `cooldown_ms` as the interval for compatibility. A `schedule` flow must have either `schedule_interval_ms > 0` or `cooldown_ms > 0`; otherwise the schedule scanner would never execute it. `timeout_ms` may be omitted on create to use the backend default, but negative timing values are invalid, and patching `timeout_ms` requires a value greater than 0. Manual run remains developer debugging. Payload may include `steps_json`, normally an ordered array of `{code,module,params,script}` steps; the backend also accepts a single step object and treats it as a one-step flow, but an explicit empty array is invalid because it would create a no-op task. Explicit step `code` values must be unique because step results are stored in the run context by code. Formal business parameters must come from a watched `STRING` virtual variable whose changed value is a JSON object. `data_change` flows must bind at least one `watch` variable because only watch variables enter the `var_id -> flow_ids` runtime index. Parameter bindings support only `literal`, `trigger_param`, `event`, and `context` sources; `event` keys are limited to `trigger_type`, `project_id`, `trigger_var_id`, `trigger_var_id_text`, `trigger_value`, `gateway_id`, `topic`, `origin_flow_id`, `origin_run_id`, `depth`, `request_id`, and `at`. Create requires `project_id > 0`, non-empty `flow_code`, and non-empty `name`; patch rejects zero `project_id` and blank `flow_code/name` when those fields are supplied. Create, patch, and list reject invalid task-flow enums early: `trigger_type`, `action_type`, invalid timing fields, `vars.role`, `vars.var_id <= 0`, `data_change` without a watch var, `schedule` without an effective interval, empty `steps_json` arrays, duplicate explicit `steps_json[].code`, every `steps_json[].module`, every explicit `steps_json[].params.*.source`, and every explicit `event` key must use backend-supported values, otherwise the API returns `400`.
- `GET /api/v1/task-flows/runtime`: task-flow runtime diagnostics. Requires `system_settings`; returns the task-flow execution queue's `name/len/cap/usage/pressure/impact/next_action`, cumulative `submitted/enqueued/dropped` counters, `pressure_threshold`, top-level `pressure`, and current guard count for fixed-duration and qualified-hold detection guards. `submitted` counts task-flow jobs that attempted to enter the executor queue, `enqueued` counts accepted jobs, and `dropped` counts jobs rejected because the executor queue was full. This is the task-flow companion to `/runtime/channels/detail`.
- `GET /api/v1/task-flows/{id}`: get one task-flow configuration with variable bindings for editor detail/refresh.
- `DELETE /api/v1/task-flows/{id}`: delete one task-flow configuration and its variable bindings. Existing `task_flow_runs` and `task_flow_sql_logs` are retained for audit/history, and the in-memory task-flow index is reloaded after deletion.
- `POST /api/v1/task-flows/{id}/run`: manually enqueue one task flow for developer debugging only. It does not carry formal business parameters; normal business entry should write a `STRING` virtual variable and let data-change trigger the task flow. Execution is asynchronous and recorded in `task_flow_runs`.
- `GET /api/v1/task-flow-runs`: list task-flow execution records. Requires `system_settings`; supports project, flow, trigger, status, origin, time, limit, and offset filters. `status` is restricted to `pending|running|success|failed|timeout|skipped`, `trigger_type` is restricted to `manual|data_change|schedule|project_start|project_end`, `project_id`/`flow_id`/`trigger_var_id`/`origin_flow_id` must be positive when present, `limit` must be positive, `offset` must be non-negative, and `from` must be before or equal to `to`; invalid enum, id, time-range, or paging values return `400` instead of an empty list.
- `GET /api/v1/task-flow-runs/{id}`: get one task-flow execution record. Missing runs return `404`.
- `GET /api/v1/task-flow-runs/{id}/sql-logs`: list SQL statements executed by one task-flow run through the shared repository connection. Optional `limit` must be positive; invalid values return `400`, and a missing run returns `404` instead of an empty log list.
- `DELETE /api/v1/variables/{variable_id}`: delete a wrongly discovered variable. A missing variable returns `404`.
- `PATCH /api/v1/variables/{variable_id}/assignment`: assign a variable to a virtual Project and enable it. A missing variable or Project returns `404`.
- `GET /api/v1/realtime/variables`: current values for enabled variables. It supports `source_type`, `gateway_id`, `project_id`, and repeated or comma-separated `var_id`. `device_id` is no longer an active query alias and is rejected as `400 unsupported_query_param`; callers must use `project_id`. No filter means an intentional full snapshot. Project pages should send `project_id`; point inspectors should send one or more `var_id` values.
- `GET /api/v1/edge-control/realtime/variables`: service-token read-only realtime mirror for the main server. It uses the same filters and `TagSnapshot[]` response as `/api/v1/realtime/variables`, requires service scope `service_realtime_read`, and reads the in-memory `TagManager`; it does not create an `edge_control_commands` row because it does not change field state.
- `GET /api/v1/edge-control/task-modules` and `GET /api/v1/edge-control/task-flow-templates`: service-token read-only task metadata mirrors for the main server. They require `service_metadata_read` and return the same module/template DTOs as the user-side task editor endpoints; they do not read or write synchronized main-server tables.
- `GET /api/v1/edge-control/runtime/channels`, `/runtime/channels/detail`, `/runtime/notifications`, `/runtime/workers`, and `/task-flows/runtime`: service-token read-only runtime diagnostics mirrors for the main server. They require `service_runtime_read` and return the same edge runtime queue, notification hub, worker, and task-flow queue diagnostics as the user-side settings endpoints; they read edge memory and do not create `edge_control_commands` rows.
- `GET /api/v1/station-view/effective?project_id=...`: returns the selected station-screen template, layout regions, visible items, resolved project-local bindings, WS subscription hints, and HTTP companion requirements for the requested Project. Regions and items expose `layout_area=card_pool|list_layout`; the response does not expose deprecated `region_key`. It requires `view_realtime`. The resolver seeds a default global template when no templates exist, but if `sys_projects.edge_instance_id` is present and differs from local `Auth.EdgeInstanceID`, the endpoint returns 404; if matched assignments are ambiguous after priority and version sorting, the endpoint returns `409 station_view_template_conflict`. Every resolved variable still comes from enabled `sys_tags` rows under the requested Project or from that Project's current running/paused detection snapshot. The desktop station page uses this endpoint for display order and filtering, WS for realtime values, and `GET /api/v1/detection-runs/current?project_id=...` for current-run detection limits/snapshot data.
- `GET /api/v1/station-view/templates`: returns station view template IDs, codes, versions, status, owner scope, and assignments. It requires `view_realtime` and is for page/admin visibility, not realtime data.
- `GET /api/v1/station-view/items?template_uid=...` or `?project_id=...`: returns raw template item configuration with `layout_area=card_pool|list_layout`, `item_uid`, binding metadata, `sort_order`, `pinned`, and `visible`. `project_id` resolves the currently effective template first. It requires `view_realtime`.

Request body is `{ "template_uid": "...", "items": [...] }`; every item must explicitly include `layout_area` (`card_pool` or `list_layout`) and `visible`, and may include `pinned`. The backend auto-ensures the matching layout region exists, rejects duplicate `item_uid`, and does not touch running tasks, detection snapshots, variables, or `TagManager`. The station page uses this endpoint for drag sorting and click-to-pin persistence; it must not persist station display preferences in `localStorage`.

It ensures the default template exists, returns table diagnostics, and may include an effective response when `project_id` is provided. It does not start/stop detection, write variables, mutate `TagManager`, or change running/paused detection snapshots.
- `PATCH /api/v1/station-view/templates/:id` and `PATCH /api/v1/station-view/assignments/:id`: require `system_settings`; they are low-frequency configuration endpoints for publishing/disabling template metadata and enabling/disabling assignment selection. Effective view keeps returning `409 station_view_template_conflict` if the edited configuration creates an ambiguous winner.
- `GET /api/v1/ws`: WebSocket realtime, notification, and command channel. It requires an Edge user JWT with `view_realtime`; browser clients may pass the token as `access_token` query parameter because the native WebSocket API cannot set `Authorization`. Query filters are `topic=realtime.variables|detection.runs|notifications`, `source_type`, `gateway_id`, `project_id`, and repeated or comma-separated `var_id`. Runtime `subscribe` messages also accept `var_ids` as JSON numbers or decimal strings; `connection.ready` and `subscription.updated` include `var_id_texts` beside numeric `var_ids` so browser clients can keep exact 64-bit IDs. No `project_id` or `var_id` means an intentional full realtime snapshot; UI pages should avoid that unless they are global dashboards. Server messages use an envelope with `type`, `request_id`, `command_id`, `at`, `payload`, and `error`; read messages include `connection.ready`, `subscription.updated`, `realtime.variables.snapshot`, `detection.runs.snapshot`, `notification.event`, `heartbeat`, and `error`. `notification.event` payload is a `RuntimeNotification` with `id/type/level/target_type/target_id/project_id/task_id/var_id/var_id_text/message/payload/occurred_at`; it is emitted for limit-alarm enter/recover/level_change and detection lifecycle/result events. The realtime snapshot path uses the project index for `project_id` subscriptions and direct tag lookup for `var_id` subscriptions, so single/multi-point views do not first assemble the full tag list. The server sets a 256 KiB read limit, read/write deadlines, ping/pong keepalive, and treats reconnects as stateless: clients should reconnect and resubscribe, then expect a fresh ready message and snapshot. Supported commands are `command.detection.start`, `command.detection.stop`, `command.detection.abnormal_stop`, and `command.write_variable`; each command must include `request_id`, `command_id`, and a `payload`, and writes `sys_audit_logs`. Detection commands run through `DetectionRunsService`. Variable writes require `kio_write` permission, run through `VariableWriteService`, update virtual variables in memory, and publish physical writes through `KIOWriteService` only when `writable=true`, `rw_mode=W|RW`, and `write_path` are configured. `command.write_variable` accepts `payload.var_id` first; if it is omitted, it can resolve by `payload.project_id + payload.var_name` or `payload.project_code + payload.var_name`. `var_name` is the backend business mapped variable name, never `raw_name` or `source_path`. Missing project/name matches return `error.code=variable_not_found`; duplicate names inside one Project return `error.code=ambiguous_variable`; successful acks include `result.var_id_text`. Physical-write failures preserve `result.kio`: `kio.status=gateway_offline` with `broker_accepted=false` means not published because the gateway was offline; `kio.status=ack_timeout_or_unmatched` with `broker_accepted=true` means already published to the broker but not confirmed by KIO. Unsupported command types return `error.code=unsupported_command`.
- 2026-06-24 realtime update: the WS realtime snapshot interval is configurable through `realtime.ws_snapshot_interval_ms` or `EDGE_WS_SNAPSHOT_INTERVAL_MS`, defaults to `500`, and is clamped to `250..5000` ms. The shared desktop frontend uses WS as the normal realtime channel and HTTP `GET /api/v1/realtime/variables` only for first paint or while WS is disconnected/reconnecting. UI consumers commit the latest WS value at most every 500 ms and intentionally drop intermediate frames; charts can still consume a slower throttled view. With现场 MQTT values changing once per second, table-style realtime views target p95 display latency below one second, while curve rendering is optimized for smoothness rather than one-point-per-frame parity.

Invalid or expired tokens return the standard `401 unauthorized`. The desktop auth store refreshes before expiry so long-lived WS reconnects can use the newest access token; WS command clients remain one-shot and never replay commands automatically.
- `GET /api/v1/history/data`: persisted history samples, requires `view_history`, supports `project_id`, `task_id`, `project_code`, `test_no`, `start`, `end`, and `limit` query filters. When `task_id`, `project_id`, or `test_no` matches `detection_run_storage_routes`, the repository first reads `rt_project_{project_id}_data` and reconstructs the existing `HistoryData` DTO; otherwise it falls back to the compatibility table `rt_history_data`. Legacy wide tables without `project_id/project_code` are tolerated during reconstruction by falling back to the frozen storage route's Project metadata, so old generated tables do not make project-filtered history queries fail. Response rows include `var_id_text`.
- `GET /api/v1/projects`: virtual Project groups, including `display_name`, `display_name_en`, and `display_name_ja`.
- `POST /api/v1/projects`: create a virtual Project group. Request accepts `name` for compatibility and the UI-facing `display_name`, `display_name_en`, `display_name_ja`; at least `name` or `display_name` is required.
- `PATCH /api/v1/projects/{id}`: update a virtual Project group, including UI-facing display names. A missing Project returns `404`.

Detection configuration page contract:

- Page data sources are HTTP APIs, not direct database reads: `GET /api/v1/detection-standards`, `GET /api/v1/detection-standards/{id}`, `GET /api/v1/projects`, `GET /api/v1/variables`, and `GET /api/v1/report-templates`.
- Persistent tables are `sys_detection_standards`, `sys_detection_standard_items`, `sys_projects`, `sys_tags`, and `sys_report_templates`. Starting a run freezes selected rules into `detection_run_standard_items`; main-server report needs are a separate run snapshot in `detection_run_report_requests`.
- Standard items associate variables by `sys_tags.var_id`. `var_name` is a stable business code and maintenance locator, not the display identity. UI labels should use `display_name`, `display_name_en`, and `display_name_ja` with frontend language fallback, then fall back to `var_name` only when no display name exists.
- When creating or replacing standard items, the repository preserves the submitted three-language display fields. If an item omits display fields, unit, or decimal places, the backend fills missing values from `sys_tags` before saving the item snapshot. Later variable renames do not mutate saved standard items or `detection_run_standard_items`.
- Fixed dropdown labels are owned by frontend i18n. The backend exposes and validates stable values: `check_method=numeric_range` means compare numeric limits; `bool_equals` means compare `target_value` as a boolean; `string_equals` means exact string comparison; `regex` means match `target_value` as a regular expression. `quality_policy=ignore_bad` skips bad-quality samples, `record_invalid` records the sample as invalid while keeping the run alive, and `fail_on_bad` treats bad quality as a failed check. Known detection-standard `mode` values are `standard` for normal reusable standards and `task_flow` for task-template generated standards; `custom` is used by runtime tasks when no reusable standard is selected. Future dynamic module schemas should return a stable `value` plus either `label_key` or trilingual labels.

## Audit And Runtime Logs

- Auth flows write explicit audit rows for login, logout, SSO ticket creation, and SSO verification.
- Protected HTTP write requests (`POST`, `PATCH`, `PUT`, `DELETE`) are audited by runtime middleware after route handling.
- HTTP write audit rows use `action=http.<method>`, `target_type=http_endpoint`, and `target_id` as the Gin route pattern, for example `/api/v1/projects`.
- Audit detail stores only metadata: `request_id`, optional `command_id`, method, path, route, status, client IP, user agent, latency, actor display name, and a short error summary. Request/response bodies are intentionally not stored, so passwords, KIO credentials, database credentials, tokens, and report file contents are not persisted in `sys_audit_logs`.
- `GET /api/v1/audit-logs` provides a paged read model for the settings/audit UI. It is restricted to `system_settings` and caps `limit` at 200.
- `X-Request-ID` is echoed for audited write requests. If the caller does not provide one, the backend generates a request ID. WebSocket write commands must carry `request_id`/`command_id` and reuse the same audit model.
- Runtime queue pressure is logged by a lightweight monitor. Every 5 seconds it checks `Channels.Logic`, `Channels.Discovery`, `Channels.Store`, `Channels.Alarm`, and `Channels.Notify`; if any queue is at or above 80% capacity it writes a line like `[runtime] channel pressure channel=store len=... cap=... usage=...%`. This is an operational log signal only and does not write MySQL. Operators can read the same queue capacity and pressure state through `GET /api/v1/runtime/channels/detail`; each queue row includes cumulative `dropped`, `impact`, and `next_action`, so the diagnostics show both the blocked path and the next check. Task-flow queue diagnostics expose the same actionable fields plus `submitted/enqueued/dropped` counters under `GET /api/v1/task-flows/runtime`. Online notification fan-out pressure is exposed separately through `GET /api/v1/runtime/notifications`.
- Core background goroutines are started through a recovery wrapper. Logic workers, the cycle scanner, discovery worker, storage bus, storage bucket workers, alarm workers, notification dispatcher, notification hub, task-flow workers, task-flow schedule scanner, task-flow fixed-duration guards, task-flow qualified-hold guards, and the channel pressure monitor log `[worker] panic recovered name=... err=... stack=...` if they panic, so operational logs retain the worker name and stack instead of losing the failure context. `GET /api/v1/runtime/workers` exposes the same recovery state as counters and actionable diagnostics, including whether a worker name is still active, degraded, or stopped after panic.
- Concurrent backend latency smoke uses `go run -tags smoke_tools ./tools/smokelatency`. It intentionally avoids live MQTT/KIO/PLC dependencies: it creates a temporary project, a watched `STRING` virtual variable, and a data-change task-flow with `builtin.context_set`, then writes JSON requests through WS `command.write_variable` and waits for `task_flow_runs` success. The printed latency distribution measures the controllable backend path from WS write request through virtual variable update, task-flow inverted index dispatch, queue execution, and run persistence. Optional `-p95-max` and `-max-max` flags make the latency check fail when the measured p95 or max latency exceeds the configured threshold.

## KingIOT/KIO Parser

The JGHJ KingIOT/KIO rule has been moved into `internal/protocol/kio`.

- Read: variables are discovered from the first full snapshot's `Objs[].N`; values default to `Objs[].1`, and quality defaults to `Objs[].3`.
- Fallback: if an object exists but does not contain the requested property, `PVs.{property}` is used as the shared value.
- Quality: raw quality code `192` maps to internal quality `1`; other raw values map to `0`.
- Data change topic: `datachange_{client_id}`. The project may configure this topic on the upper-computer side.
- Write topic: `setdata_{client_id}`. `KIOWriteService` builds the KIO write payload with `Writer`, `WriteTime`, `Qid`, `PNs`, `PVs`, and `Objs`; `Username` and `Password` are optional compatibility fields only. HTTP KIO write and WS `command.write_variable` reuse this service so publish/ack handling stays behind the backend.
- Write result topic: `setdata_result_{client_id}_{writer}`. A write is fully successful only when a matching `Qid` returns `ProcessStep=100` and `Result=ok`; `received`, `doing`, `some ok`, and `all error` are not treated as full success.
- Generated write `Qid` values stay below `1_000_000_000`. KingIO developer tests showed very large nanosecond IDs can publish successfully but fail to match the returned ack, while small explicit/generated IDs return matching `ProcessStep=100` acks.
- Query-all topic: `Query_AllKIOTags_{client_id}`. It is used to actively request the full tag list; the response is pushed through the configured data-change topic.

KIO source configuration belongs in `sys_gateways`, not in each write request:

- MQTT connection: `broker`, `client_id`, `username`, `password`, `topic`, `qos`.
- KIO identity and topics: `kio_client_id`, `kio_writer`, `setdata_topic`, `write_result_topic`, `query_all_topic`.
- KIO write credentials: `kio_write_username`, `kio_write_password`.

The local KIO test proved that MQTT connection credentials and KIO write credentials are different concerns. The EMQX broker accepted empty credentials and `Admin/admin`, but KIO down-write confirmation only returned when the write payload used `kio_write_username=sa` and `kio_write_password=C12E01F2A13FF5587E1E9E4AEDB8242D`.

## Backend Smoke Tools

These smoke tools require a running backend, valid MySQL config, and the local test account from `AI_BOARD.md`.

```powershell
go run -tags smoke_tools ./tools/smokebackend -latency-n 30 -latency-c 10
go run -tags smoke_tools ./tools/smokehealth
go test -tags smoke_tools ./tools/smokehealth
go run -tags smoke_tools ./tools/smokeeb017
go run -tags smoke_tools ./tools/smokeeb045

go test ./internal/pipeline -run TestProcessMessageKIOPayloadUpdatesOnlyIndexedKnownTags -count=1
```

- `smokebackend` is the one-command backend acceptance runner. It executes `smokehealth`, `smokeeb017`, `smokeeb045`, and `smokelatency` in sequence against the running backend. By default it gates latency with `-latency-p95-max 2s` and `-latency-max-max 5s`; it also captures `/runtime/channels/detail`, `/task-flows/runtime`, `/runtime/notifications`, and `/runtime/workers` before and after the suite. The runner fails if any required core channel or always-on core worker is missing, if runtime channel or worker diagnostics contain duplicate names, if any always-on core worker is inactive at the baseline or final snapshot, if any worker is already unhealthy at the baseline or ends unhealthy, if any core channel, task-flow queue, or notification hub `dropped` counter is missing or grows, if any core channel, task-flow queue, or notification hub reports `pressure=true`, if worker lifecycle diagnostics (`active/starts/exits/panics`) are missing, or if any worker's panic counter grows. Use `-skip-business` only when you intentionally want a quick health+latency check.
- `smokehealth` verifies backend readiness for frontend testing: `/health` status and its compact core channel map, login, `auth/me`, Projects, Project members, Variables, Runtime Channels, the compact `/runtime/channels` compatibility map, the detailed required core runtime channels (`logic`, `discovery`, `store`, `alarm`, and `notify`), required always-on core workers (`alarm-worker`, `channel-pressure-logger`, `cycle-scanner`, `discovery`, `logic`, `notification-dispatcher`, `storage-bus`, `task-flow-schedule-scanner`, and `task-flow-worker`) with `active>0`, actionable diagnostics fields (`impact/next_action`) on every runtime channel, task-flow, notifications, and workers, runtime channel drop counters on every channel, task-flow submit/drop counters, notification hub `published/delivered/dropped` counters, worker lifecycle counters (`active/starts/exits/panics`) and `health=ok`, Gateway Configs, task modules/templates/runs, notification unread count, active detection runs, and the intentionally removed legacy `/api/v1/devices=404` contract. Dynamic workers such as storage buckets and fixed-duration/qualified-hold guards may appear during business smoke, but they are not required in a plain startup health check.
- `smokeeb017` verifies multi-Project detection isolation, virtual variable writes, and history ownership.
- `smokeeb045` verifies the formal watched `STRING` task request path: WS writes JSON into a request variable, task-flow data-change triggers run, a developer JavaScript step can read realtime project data, call `db.query`, write script logs, and expose SQL logs through `GET /api/v1/task-flow-runs/{id}/sql-logs`, and a `schedule` JavaScript flow runs through the schedule scanner before being disabled. The same smoke then verifies `custom_items` are frozen into run standard snapshots, `process_params/plc_writes` are frozen, storage routes are prepared through `builtin.storage_prepare`, running limits are updated through `builtin.update_detection_limits`, active detection alarms are muted through `builtin.mute_detection_alarms` with `muted=1`, report outputs are registered through `builtin.register_report`, controlled HTTP calls run through `builtin.http_request`, pause/resume work, manual task-flow stop works, feature refresh writes a `features_updated` event and publishes `detection.features_updated` through both WS notification events and persisted HTTP notifications, fixed-duration and qualified-hold runs stop automatically with the expected end types, run lifecycle notifications (`detection.run_started`, `detection.run_paused`, `detection.run_resumed`, `detection.run_stopped`, and `detection.run_abnormal_stop`) are visible through the same WS/HTTP unread/read path, `detection.result_ok` notifications are visible through that path, and a start-frame above-H run produces `alarm.limit.enter`, the current active alarm can be muted, a later above-HH value still produces `alarm.limit.level_change`, a return-to-qualified value produces `alarm.limit.recover`, then stopping the run still produces `detection.result_ng` because the run had a limit alarm. The smoke also creates an independent default-alarm variable, enables `sys_tags.default_*` limits through `PATCH /api/v1/variables/{id}`, writes `43 -> 50 -> 25`, verifies default `alarm.limit.enter/level_change/recover` through WS and persisted HTTP notifications with `task_id=0`, then confirms the recovered row through `GET /api/v1/limit-alarms?scope=default`. It also asserts the write-audit path by reading `/api/v1/audit-logs`: the formal STRING request must create a `ws.command.write_variable` audit with the same `command_id`, WS `command.detection.abnormal_stop` must create a success audit with the same `command_id`, and the control-variable downset inside `builtin.write_control_variables` must create a `task_flow.write_variable` audit for the target variable.
- `smokelatency` measures concurrent backend-controlled task triggering latency without requiring live IO/KIO/MQTT. It creates a watched `STRING` virtual variable and a `data_change` flow, writes JSON through WS, waits for `task_flow_runs` success, prints min/p50/p90/p95/max/avg, and can fail the run through `-p95-max` or `-max-max`.
- `TestProcessMessageKIOPayloadUpdatesOnlyIndexedKnownTags` verifies the MQTT/KIO hot path with a real KingIOT/KIO `Objs/PVs` payload: remapped business `var_name` still reads through the raw KIO `JSONPath`, `PVs` fallback works for objects without a local value, quality codes are kept in runtime snapshots, and the `gateway/topic` index prevents updates from leaking to tags on other topics.
