# 任务变量流转与内置模块设计

## 结论

变量是一切任务业务的根基。前端填写的业务参数不通过 HTTP 手动运行接口传入任务执行器，而是写入一个 `STRING` 虚拟变量。任务系统通过变量变化触发，解析该字符串中的 JSON，生成本次任务上下文，再执行内置模块链。

## 主链路

```text
前端填写业务参数
  -> 后端受控写入 STRING 虚拟变量
  -> TagManager 更新该虚拟变量当前值
  -> TaskFlowIndex 通过 var_id -> flow_ids 命中任务模板
  -> TaskFlowExecutor 解析 trigger_value JSON
  -> 生成 task_params 和 run context
  -> 按 steps_json 执行内置模块链
```

示例虚拟变量值：

```json
{
  "request_id": "REQ-20260530-001",
  "command": "start_detection",
  "project_id": 1,
  "standard_id": 3,
  "duration_sec": 7200,
  "qualified_hold_sec": 7200,
  "operator_note": "连续合格2小时检测",
  "storage_route_ids": [1, 2, 3]
}
```

## 模板和参数

`sys_task_flows` 仍是任务模板。`steps_json` 保存后端模块链：

```json
[
  {
    "code": "store",
    "module": "builtin.storage_snapshot",
    "params": {
      "project_id": {"source": "trigger_param", "key": "project_id"}
    }
  }
]
```

参数来源：

- `literal`：固定值。
- `trigger_param`：来自触发变量 JSON，例如 `project_id`、`duration_sec`。
- `event`：来自触发事件，例如 `trigger_var_id`、`trigger_value`。
- `context`：来自前面步骤输出。
- 简写值：非对象值按 `literal` 处理。

## 当前内置模块

- `builtin.storage_snapshot`
  - 从项目实时变量 map 读取变量，按当前检测任务和 storage routes 投递到 StorageBus。
  - 不直接写历史库。

- `builtin.context_set`
  - 把参数写入 run context，作为步骤间中间变量。

- `javascript`
  - 开发者高级模块。
  - 可读 `task_params`、`params`、`context`、`trigger`，可调用受控 `realtime/storage/db/log`。
  - `realtime.get(var_id)`、`realtime.getMany([var_id])`、`realtime.getByName(var_name, project_id?)` 和 `realtime.project(project_id?)` 用于多变量条件读取。
  - `realtime.write(var_id, value, options?)` 复用任务流写变量审计，但只允许写虚拟变量，默认 `trigger=false`；如果确实要继续触发下游任务，必须显式传 `{"trigger":true,"max_depth":n}`。
  - 物理变量下设不能在任务执行器里直接改内存，必须走 WS/HTTP 的 `VariableWriteService + KIOWriteService`，等待现场写入链路确认。

## HTTP 手动运行边界

`POST /api/v1/task-flows/:id/run` 只保留开发者调试触发，不承载正式业务参数。正式业务参数必须写入虚拟变量并通过变量变化触发。

## 配置管理边界

- `GET /api/v1/task-flows/:id` 返回单条任务流配置和变量绑定，供编辑器详情刷新使用。
- `PATCH /api/v1/task-flows/:id` 可以修改任务所属 `project_id`，并在替换 `vars` 时把变量绑定同步到新的项目。
- `DELETE /api/v1/task-flows/:id` 只删除任务流配置和变量绑定。
- 已产生的 `task_flow_runs` 和 `task_flow_sql_logs` 不删除，用于审计和追溯。

## 项目生命周期任务

检测任务启动和结束也会进入同一套任务流总线：

- 检测启动成功后派发 `project_start`。
- 正常结束、任务流结束和异常结束后派发 `project_end`。
- 生命周期事件的 `task_params` 包含 `task_id`、`project_id`、`project_code`、`test_no`、`status`、`end_type` 和 `trigger_type`。
- 适合承载存储准备、特征值刷新、报表登记、通知、归档标记等不应该阻塞采集热路径的业务。

## 定时任务

`schedule` 触发类型已接入轻量定时扫描器：

- 后端每秒扫描一次已启用的 `trigger_type=schedule` 任务流。
- `schedule_interval_ms` 表示执行间隔，单位毫秒。
- 如果 `schedule_interval_ms` 为空但 `cooldown_ms` 有值，后端临时把 `cooldown_ms` 当作间隔，便于旧前端表单过渡。
- 到期后仍进入 `TaskFlowExecutor.input`，不会在扫描器里直接执行脚本。
- `cooldown_ms` 仍可作为额外防抖节流；定时任务不应使用很小间隔承载高频采集逻辑。

## 防递归

写变量闭环已经带递归上下文：

- `origin_flow_id`
- `origin_run_id`
- `depth`
- `allow_reentrant`
- `max_depth`

默认同一个 flow 不允许由自己的写入再次触发。
