# 报表设置、计划导入与历史报表展示设计

最后更新：2026-06-16

维护责任：`review-ai` 负责设计边界；后续 API/生成实现由 `backend-ai`、`frontend-ai`、`test-ai` 分工落地。

## 1. 目标

报表能力拆成三个前端画面，并把“配置、查看、打包下载”分开：

1. `报表设置 / 模板管理`：维护客户 Excel 模板、模板原始副本、单元格映射、图片落点和模板版本。
2. `报表设置 / 导入计划`：从用户上传的计划或报表文件中解析检测任务、检测规则、上下限和设定值，创建检测配置和测试计划。
3. `历史 / Excel 报表`：查看某一次检测实际生成的报表。左侧仅按检测报告名称切换，右侧用只读 Luckysheet 加载后端生成的实际 Excel 报表。

下载不放在 `历史 / Excel 报表` 中。下载统一由 `历史 / 数据下载` 负责，按用户选择打包生成 zip。

## 2. 非目标

- 不在前端拼最终 Excel。
- 不在前端计算正式平均值、极值、上下限判定或曲线图片。
- 不把 Luckysheet JSON 作为交付文件或模板真源。
- 不做缺模板、缺映射、缺文件的静默兜底策略。
- 不继续用 `ext_1/ext_2/ext_3` 承载新报表参数。

## 3. 页面职责

### 3.1 报表设置 / 模板管理

模板管理面向“生成前配置”。

职责：

- 上传客户 `.xlsx` 模板。
- 保存一份不可变或可版本化的原始模板副本。
- 维护模板元数据：`template_code`、模板名称、版本、启用状态、适用项目或检测类型。
- 用 Luckysheet 预览模板，但预览不是文件真源。
- 配置单元格映射：
  - 任务字段：`task.test_no`、`task.project_code`、`task.started_at`、`task.ended_at` 等。
  - 报表请求字段：`request.report_name`、`request.template_code` 等。
  - 变量字段：变量名、显示名、单位。
  - 指标字段：平均值、最小值、最大值、样本数、连续合格窗口结果。
  - 上下限字段：上限、下限、报警上下限、回差、保持时间。
  - 参数字段：设定值、面积、备注等 `param.*`。
- 配置曲线图片落点：
  - sheet；
  - 起始单元格或像素锚点；
  - 宽高；
  - 曲线使用变量集合；
  - 是否显示上下限线、极值点、报警标记。
- 校验模板保存条件：
  - 必填映射必须能解析；
  - 图片落点合法；
  - 模板副本存在；
  - 版本号和 hash 可追溯。

第一版可沿用当前 `params_json.cell_mapping` 契约，但应把模板级 mapping 和本次报表参数分开存储：模板管理保存“默认映射”，检测报表请求只冻结“本次使用的映射快照和参数值”。

### 3.2 报表设置 / 导入计划

导入计划面向“从客户计划文件生成系统配置”。

职责：

- 上传 Excel 或 CSV 计划文件。
- 解析检测任务信息：
  - 测试编号或计划编号；
  - 项目/设备；
  - 测试类型；
  - 客户、机型、出厂编号；
  - 计划开始时间或备注。
- 解析检测规则：
  - 变量名称或测点名称；
  - 上下限；
  - 设定值；
  - 保持时间、检测周期、报警启用、存储启用等。
- 解析报表请求：
  - 检测报告名称；
  - 使用的报表模板名或模板编码；
  - 报表变量；
  - 报表参数。
- 匹配系统变量和检测配置：
  - 按变量显示名、内部名、别名、单位匹配；
  - 给出未匹配项；
  - 给出多候选冲突；
  - 不直接用模糊结果写正式配置。
- 创建两个结果：
  - `检测配置`：创建后立即可被检测启动使用。
  - `测试计划`：创建后进入 `待测试` 阶段，等待用户选择或到时执行。

导入计划必须先生成草稿和校验结果，用户确认后才写正式配置和测试计划。

### 3.3 历史 / Excel 报表

历史报表面向“某次检测的报表查看”。

职责：

- 读取当前检测任务的报表请求和报表 job。
- 左侧只显示检测报告名称列表，用于切换报表。
- 根据选中的检测报告名称，加载对应的报表 job 和实际生成的 Excel artifact。
- 右侧使用只读 Luckysheet 加载实际 Excel 文件。
- 显示必要状态：
  - 等待生成；
  - 生成中；
  - 生成失败；
  - 预览失败；
  - 已生成但文件不可用。
- 不放单报表下载按钮。
- 不在前端根据数据重新拼报表。

如果 Luckysheet 预览失败，只提示预览失败和原因；不能构造假预览。真实下载仍由 `数据下载` 页面统一打包。

### 3.4 历史 / 数据下载

数据下载面向“打包导出”。

职责：

- 展示可打包项树：
  - 原始采样数据；
  - 过滤后数据；
  - 曲线图片；
  - 详细数据表；
  - Excel 报表；
  - 报警与事件；
  - 检测配置、上下限、报表请求快照、存储路由快照。
- 支持下载所选和下载全部。
- 后端异步生成 zip 包。
- zip 中的 Excel 报表必须来自报表 job 生成的正式 `.xlsx` artifact，不从 Luckysheet 当前预览导出。

## 4. 后端生成链路

推荐链路：

```text
导入计划
-> 用户确认
-> 创建检测配置
-> 创建测试计划(待测试)
-> 启动检测时冻结 report_request
-> 检测结束后报表 job 入队
-> 等待同步库中历史数据、规则快照、上下限、特征值齐全
-> 后端生成指标、曲线图片、Excel
-> 历史 / Excel 报表只读预览
-> 历史 / 数据下载统一打包
```

生成时机：

- 检测停止接口不应同步生成 Excel。
- 检测结束后可以自动入队报表 job。
- 历史页打开时只读 job 状态；允许后续提供“补生成/重试”入口，但不放在下载职责里。
- 数据未同步到位时 job 保持 waiting；确定无法满足时 failed。

生成物：

- `.xlsx`：正式客户报表。
- `manifest.json`：完整追溯包，记录模板版本、映射、变量、上下限、计算结果、曲线图片引用。
- `chart/*.png`：曲线图片，供 Excel 插图和历史预览复用。
- job events：生成过程、失败原因、等待原因。

## 4.1 生成与文件存储技术选型

第一版采用“主服务器硬盘文件存储”，不引入对象存储。

### 4.1.1 Excel 生成

后端生成正式 `.xlsx` 使用 `github.com/xuri/excelize/v2`。

理由：

- 主服务器后端已经在 `main-server/backend/internal/reports` 使用 `excelize` 生成报表、打开模板、写单元格和保存 `.xlsx`，继续沿用成本最低。
- `excelize` 是 Go 生态里成熟的 Office Open XML 处理库，适合读取客户模板、写入单元格、保留 workbook 结构、插入图片和输出 `.xlsx`。
- 报表交付物必须是后端生成的真实 Excel 文件，不能依赖 Luckysheet 导出。

实现边界：

- 模板真源是上传的 `source.xlsx`。
- 后端用 `excelize.OpenFile()` 打开模板副本，写入映射单元格、明细 sheet、manifest sheet、公式输入区和图片。
- Excel 原生公式仅作为模板兼容内容尽量保留；正式结果由后端业务公式写入明确值。
- 后端业务指标包括平均值、极值、样本数、连续合格窗口、上下限判定等，不把这些正式计算交给前端。
- 当前代码里的默认模板兜底需要收敛：客户报表缺模板、缺文件、缺 required mapping 时应让 job 失败并记录原因，不能静默生成空白默认报表。

### 4.1.2 曲线图片生成

曲线图片应由后端生成为 PNG，再由 `excelize` 插入 Excel，并作为独立 artifact 供历史预览和打包下载复用。

第一版建议选一个服务端静态图片方案：

- 优先：Go 侧静态绘图库，例如 `gonum.org/v1/plot`，直接输出 PNG，部署简单。
- 备选：使用前端图表配置加 headless browser 截图，视觉一致性更强，但运行依赖和失败面更大。

不建议第一版把曲线图片交给 Luckysheet 或浏览器临时截图生成，因为历史报表和下载包必须可由后台队列稳定复现。

最小验证已经覆盖“历史采样行 -> 曲线 PNG -> chart artifact -> 插入 Excel -> 再读回图片元数据”：

- 测试中用 history-like rows 模拟历史采样数据；
- 后端计算平均值并写入 Excel 指标单元格；
- 后端按采样值和上下限生成 PNG 曲线；
- PNG 先保存为 `charts/*.png` artifact；
- 再由 `excelize.AddPictureFromBytes()` 插入模板指定位置；
- 生成后的 `.xlsx` 读回后可校验单元格、公式计算值和图片存在。

未验证范围：

- 尚未直接连接真实历史数据库查询；
- 尚未选定生产级曲线图库；
- 尚未做中文标题、坐标轴、图例、极值点、报警标记、长时间序列抽稀和多变量曲线的视觉验收。

### 4.1.3 文件管理

文件管理不要继续在业务代码里手写 `os.MkdirAll`、`filepath.Join`、绝对路径拼接和下载路径判断。既然文件只存储在主服务器硬盘上，建议引入轻量文件系统抽象 `github.com/spf13/afero` 作为本地 `ArtifactStore` 的底层实现。

推荐形态：

```text
ReportService
-> ArtifactStore interface
-> LocalArtifactStore
-> afero.Fs
-> data/report-assets
```

第一版只实现本地硬盘 driver，根目录为主服务器配置项 `artifact_store.root_dir`，默认 `data/report-assets`。报表业务代码只使用 `artifact_key`，不直接接触本机绝对路径。

实现要求：

- 代码层定义 `ArtifactStore` 抽象，内部基于 `afero.Fs`，使用 `artifact_key` 访问文件，不让业务代码依赖本机绝对路径。
- `artifact_key` 使用 `/` 分区，保存到本地时集中映射为 Windows/Linux 安全路径。
- `LocalArtifactStore` 必须校验 key：禁止绝对路径、`..`、空 key、非法分隔符和越过根目录。
- 业务表只保存 `artifact_key`、`content_type`、`size`、`sha256`、`generation_id`、`created_by` 等元数据，不保存本机绝对路径。
- zip 打包可继续使用 Go 标准库 `archive/zip`，但 zip 内容的读取和最终包写入都走 `ArtifactStore`。

选择理由：

- 报表生成发生在主服务器，模板副本、生成 Excel、曲线图片、下载包都由主服务器读写，第一版不需要把文件同步到边缘端。
- 当前项目历史数据同步依赖外部数据库同步软件，该同步不保证文件同步；因此模板文件和生成报表统一放在主服务器硬盘。
- 本地文件系统部署简单，适合现场服务器和客户内网部署；Afero 能把文件操作集中到一个本地 driver 中，避免业务代码散落路径处理。

禁止项：

- 禁止把本机绝对路径作为跨端合同。
- 禁止把 Luckysheet JSON 当作模板或报表交付真源。
- 禁止把大二进制文件直接塞进现有业务同步表。
- 禁止第一版引入对象存储、S3、MinIO 或云 OSS 作为必要运行依赖。

### 4.1.4 最小技术验证

2026-06-16 已在主服务器后端增加最小 spike 测试 `TestReportArtifactStoreExcelizeSpike`。该测试最初验证过 Go CDK `fileblob`，随后按用户确认的“只存主服务器硬盘”收敛为 Afero 本地硬盘方案。

验证范围：

- 使用 Afero 本地文件系统按 `artifact_key` 写入模板 `.xlsx`；
- 从 `artifact_key` 读回模板；
- 使用 `excelize.OpenReader()` 打开模板；
- 写入任务字段、指标字段和上下限字段；
- 写入并保留 Excel 公式；
- 插入后端生成的 PNG 曲线图片；
- 使用 `excelize.WriteToBuffer()` 生成正式 `.xlsx`；
- 将生成报表写回 `reports/.../report.xlsx`；
- 再次读回并校验单元格、公式计算结果和图片元数据。

验证命令：

```powershell
cd main-server/backend
go test ./internal/reports -run TestReportArtifactStoreExcelizeSpike -count=1 -v
go test ./internal/reports -count=1
```

结果：两项均通过。

结论：

- 功能上，`excelize + Afero` 可以满足第一版模板副本、本地 artifact key 存储、Excel 生成、公式保留、历史采样曲线 PNG 插入和生成物读回校验需求。
- 依赖上，Afero 明显轻于 Go CDK，`go mod tidy -go=1.24.0` 能直接通过，不会把模块抬到 Go 1.25。
- 由于用户已确认只存主服务器硬盘，Go CDK、S3、MinIO、OSS 暂不进入第一版设计。

## 4.2 Luckysheet 样式同步到 Excel 的策略

第一版不建议把 Luckysheet 编辑后的完整 JSON 反向转换成 `.xlsx` 作为交付真源。Luckysheet 是预览和配置工具，最终 `.xlsx` 仍由后端基于模板副本和结构化 mapping 生成。

原因：

- Luckysheet 已是 legacy 组件，官方文档已提示不再维护，完整 Excel 兼容性风险高。
- LuckyExcel 更适合把 `.xlsx` 转成 Luckysheet JSON 做预览；从 Luckysheet JSON 完整导回 Excel 时，行高、列宽、合并单元格、图片、边框、条件格式、公式、打印设置、像素锚点等很难保证 1:1。
- 客户交付物要求稳定可追溯，不能依赖浏览器当前状态导出。

推荐同步方式是“结构化样式补丁”，而不是“Luckysheet JSON 全量反写”。

### 4.2.1 模板样式的权威来源

客户上传的 `source.xlsx` 是样式真源：

- 表头；
- 字体；
- 边框；
- 合并单元格；
- 列宽；
- 行高；
- 打印设置；
- Excel 原生公式；
- 固定静态文本。

后端生成报表时先 `excelize.OpenReader(source.xlsx)`，然后只填数据、图片和必要的样式补丁。

### 4.2.2 前端可修改的样式范围

如果前端在 Luckysheet 里允许改样式，第一版只支持一组可控白名单，并保存为模板 mapping 的一部分：

```json
{
  "style_patches": [
    {
      "sheet": "Report",
      "range": "B3:D3",
      "font": {"bold": true, "color": "#1f2937"},
      "fill": {"color": "#f3f4f6"},
      "border": "thin",
      "number_format": "0.00"
    }
  ]
}
```

建议第一版白名单：

- 字体加粗；
- 字体颜色；
- 背景色；
- 水平/垂直对齐；
- 数字格式；
- 单元格边框；
- 行高；
- 列宽；
- 合并单元格；
- 图片落点和大小。

暂不建议支持：

- 条件格式；
- 复杂图表对象；
- 透视表；
- 任意公式编辑；
- 打印区域复杂调整；
- 浏览器像素级拖拽布局反写。

### 4.2.3 同步流程

```text
模板管理上传 source.xlsx
-> LuckyExcel 转 Luckysheet 预览
-> 用户点击单元格配置数据 mapping、图片落点、有限样式补丁
-> 保存 mapping.json
-> 后端生成时打开 source.xlsx
-> 写入数据和业务指标
-> 应用 style_patches
-> 插入 charts/*.png
-> 保存 report.xlsx
```

也就是说，前端不是导出 Excel；前端只提交结构化配置。后端把这些结构化配置翻译成 Excelize 样式操作。

### 4.2.4 对用户可见的产品边界

模板管理里需要明确区分两类操作：

1. `上传/替换 Excel 模板`
   - 修改大范围排版、复杂样式、打印设置、复杂公式时，用户应在 Excel/WPS 中改好模板后重新上传。

2. `配置映射和轻量样式`
   - 在系统里配置单元格填什么数据、图片放哪里、少量字体/边框/数字格式。

这个边界能避免承诺“网页里怎么改，导出的 Excel 就 1:1 一样”。第一版的目标是交付稳定，不是做一个完整在线 Excel 编辑器。

## 4.3 文件分区和 artifact_key

文件按“模板资产、导入计划、检测快照、报表生成、下载包”分区。

### 模板资产

模板是可版本化资产，原始 `.xlsx` 是生成真源。

```text
templates/{template_code}/v{template_version}/{template_hash}/source.xlsx
templates/{template_code}/v{template_version}/{template_hash}/mapping.json
templates/{template_code}/v{template_version}/{template_hash}/preview.json
```

说明：

- `source.xlsx` 是用户上传的原始模板副本。
- `mapping.json` 保存模板级默认 cell mapping 和 chart mapping。
- `preview.json` 可选，用于缓存 LuckyExcel 转换结果，不作为交付真源。
- `template_hash` 使用模板文件内容 hash，避免同版本文件被静默覆盖。

### 导入计划资产

导入计划保存原始上传文件、解析结果和用户确认后的创建结果。

```text
plan-imports/{yyyy}/{import_id}/source.xlsx
plan-imports/{yyyy}/{import_id}/parse-result.json
plan-imports/{yyyy}/{import_id}/confirmed-config.json
```

说明：

- `source.xlsx` 是用户上传的计划文件原件。
- `parse-result.json` 保存检测任务、检测规则、上下限、设定值、变量匹配、冲突和人工确认标记。
- `confirmed-config.json` 保存最终创建检测配置和测试计划时使用的结构化输入。

### 检测快照资产

检测快照是某次检测的生成依据，不是模板文件。

```text
run-snapshots/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/report-requests.json
run-snapshots/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/standard-snapshot.json
run-snapshots/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/limits-snapshot.json
run-snapshots/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/storage-routes.json
```

说明：

- 快照可由数据库同步数据重新构建，但保存成文件能让打包下载和排查更直接。
- `factory_no` 可作为 manifest 字段和查询条件，但不单独作为唯一分区，因为同一出厂编号可能有多次检测、多张报表。

### 报表生成资产

一个出厂编号的设备可能有多次检测；一次检测可能有多张报表；同一张报表可能因为模板或公式变化被重新生成多次。因此必须有 `task_id/test_no`、`request_id` 和 `generation_id`。

```text
reports/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/requests/{request_id}/generations/{generation_id}/report.xlsx
reports/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/requests/{request_id}/generations/{generation_id}/manifest.json
reports/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/requests/{request_id}/generations/{generation_id}/charts/{chart_id}.png
reports/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/requests/{request_id}/generations/{generation_id}/luckysheet-preview.json
```

说明：

- `request_id` 对应 `detection_run_report_requests.id`，也就是一份检测报告。
- `generation_id` 表示重新生成版本，首次生成可为 `1` 或 UUID。
- `report.xlsx` 是历史 Excel 报表右侧 Luckysheet 预览和数据下载打包的来源。
- `charts/*.png` 是后端生成曲线图片，插入 Excel，同时可供预览和打包。
- `luckysheet-preview.json` 可选缓存，不是权威。

### 下载包资产

```text
download-packages/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/{package_id}/package.zip
download-packages/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/{package_id}/manifest.json
```

说明：

- 下载包由 `历史 / 数据下载` 创建。
- `manifest.json` 记录用户选择了哪些项和对应 artifact key。
- zip 中的 Excel 报表来自 `reports/.../report.xlsx`，不是前端导出。

## 4.4 重新生成策略

历史 `Excel 报表` 页面需要有重新生成入口，但重新生成仍由后端队列执行。

建议提供两个动作：

1. `按冻结快照重新生成`
   - 使用本次检测冻结时的模板版本、mapping、参数、变量和检测快照。
   - 用于修复生成失败、图片生成失败、artifact 丢失等情况。
   - 不受当前模板变更影响。

2. `按当前模板重新生成`
   - 使用当前启用模板版本和当前 mapping。
   - 仍使用该次检测的历史数据、检测规则快照、上下限快照、设定值快照。
   - 适用于用户修改模板或公式后，希望用同一次检测数据生成新版报表。
   - 必须生成新的 `generation_id`，不能覆盖旧 artifact。

每次重新生成都必须记录：

- `generation_id`；
- 生成类型：`frozen_snapshot` 或 `current_template`；
- 使用的 `template_code/version/hash`；
- 使用的 mapping hash；
- 操作人；
- 操作时间；
- 失败原因；
- 旧 generation 是否仍可查看。

历史页左侧仍只显示检测报告名称；右侧默认展示最新成功 generation，并可在报告详情处切换 generation 或查看重新生成记录。

## 4.5 报表公式与参数取值

报表正式计算不认可 Excel 原生公式。Excel 模板里如果已经存在公式，可以作为客户模板内容被保留，但系统不把它作为正式结果来源，也不承诺解析、迁移、校验或执行任意 Excel 公式。

第一版公式模型以“后端业务公式 + 冻结参数”为准：

- 后端计算正式报表值；
- 前端只配置单元格映射、参数、受控表达式和图片落点；
- Luckysheet 不参与正式计算；
- Excel 原生公式只做模板兼容保留。

### 4.5.1 Excel 原生公式的边界

Excel 原生公式的处理规则：

- 客户上传模板中已有的公式可以保留；
- 后端不新增 Excel 原生公式作为正式计算逻辑；
- 后端不解析任意 Excel 原生公式的业务含义；
- 后端不依赖 Excel 打开后的自动重算结果作为任务判定或报表正式指标；
- 如果某个交付单元格需要正式值，应由后端业务公式计算后写入明确结果值。

原因：

- Excel 公式执行环境不可控，不同 Excel/WPS/在线预览引擎可能存在差异；
- 公式依赖区域和外部引用难以审计；
- Luckysheet 与 Excel 的公式兼容不能作为正式质量依据；
- 报表需要可追溯和可重放，正式计算必须由后端用冻结快照完成。

### 4.5.2 后端业务指标公式

平均值、极值、样本数、连续合格窗口、上下限判定、报警统计等正式业务结果应由后端计算，再写入 Excel。前端 Luckysheet 不参与正式计算。

业务指标引用建议使用结构化 source，而不是让用户直接写 SQL 或随意访问数据库：

```json
{
  "source": "metric",
  "metric": "avg",
  "variable": "supply_air_temperature",
  "window": "full_detection"
}
```

可支持的指标：

- `avg`；
- `min`；
- `max`；
- `count`；
- `first`；
- `last`；
- `qualified_hold_duration`；
- `alarm_count`；
- `ng_reason`；
- `custom_expression`。

`custom_expression` 可以支持受控表达式，例如：

```text
(metric.avg("supply_air_temperature") - param.target_temperature) / param.area
```

但表达式引擎必须白名单化，只能访问本次报表冻结快照中的变量、指标、规则和参数，不能访问任意文件、网络、数据库或系统函数。

### 4.5.3 启动参数、计划导入参数和设定值

公式可能引用前端任务开始时传递的参数，也可能引用计划导入解析出来的参数和设定值。

这些参数必须在检测启动或计划确认时冻结，进入本次检测的 report request snapshot，例如：

```json
{
  "params": {
    "target_temperature": 12.0,
    "area": 35.5,
    "customer": "ACME",
    "report_level": "factory"
  },
  "limits": {
    "supply_air_temperature": {
      "lower": 10,
      "upper": 20
    }
  }
}
```

模板 mapping 可以引用：

```text
param.target_temperature
param.area
limit.supply_air_temperature.lower
limit.supply_air_temperature.upper
task.factory_no
task.test_no
request.report_name
metric.supply_air_temperature.avg
```

生成原则：

- 后端只使用本次检测冻结的 `params_json`、检测规则快照、上下限快照和历史采样数据。
- 如果参数缺失，报表 job 应失败并记录明确原因，不能用默认值静默兜底。
- 参数类型要在模板管理或计划导入确认时校验，例如 number、string、percent、date、enum。
- `10~20%`、`10±5` 等文本解析结果要同时保留原始文本、归一化值和单位。

### 4.5.4 公式保存位置

模板管理中保存公式配置时，建议把“写到哪个单元格”和“值怎么来”分开：

```json
{
  "cell_mapping": [
    {
      "sheet": "Report",
      "cell": "B3",
      "source": "metric",
      "variable": "supply_air_temperature",
      "metric": "avg",
      "window": "full_detection",
      "required": true
    },
    {
      "sheet": "Report",
      "cell": "B4",
      "source": "param",
      "path": "target_temperature",
      "required": true
    },
    {
      "sheet": "Report",
      "cell": "B5",
      "source": "expression",
      "expression": "metric.avg(\"supply_air_temperature\") - param.target_temperature",
      "required": true
    }
  ]
}
```

这样模板可以同时支持：

- 一个变量出现在多张报表；
- 一张报表包含多个变量；
- 公式引用变量指标；
- 公式引用任务开始参数；
- 公式引用计划导入解析出的设定值和上下限；
- Excel 模板中已有公式可被保留，但不作为正式计算来源。

## 4.6 模板变更和公式变更

Excel 原生公式只属于模板兼容内容，不属于系统正式公式模型。

- 模板管理上传新模板或修改公式后，必须生成新模板版本或新 `template_hash`。
- 旧检测已经生成的报表不自动改变。
- 需要变化时，由历史页触发“按当前模板重新生成”。
- 如果只改 mapping，不改 Excel 文件，也必须生成 mapping hash，并写入 generation manifest。

后端不应尝试解释任意 Excel 原生公式作为业务规则；后端只负责写入映射单元格、插入图片并尽量保留模板原有结构。需要后端计算的平均值、极值、上下限判定、曲线数据和参数表达式，必须由报表 job 使用同步历史、任务开始参数和检测快照计算。

## 5. 上下限与设定值解析

导入计划需要能从 Excel 文本中解析常见上下限写法。

解析职责放在后端。前端只提供预览、人工修正和确认。

原因：

- 解析结果会创建检测配置和测试计划，属于业务写入依据，必须由后端统一校验。
- 同一份计划导入应能被测试复现，不能依赖浏览器临时代码。
- 后端解析器可以做单元测试，覆盖 `10~20%`、`10±5`、`10±5%`、`>=10` 等格式。

前端职责：

- 上传文件。
- 展示后端解析结果。
- 对低置信度或歧义项让用户选择。
- 用户确认后提交结构化草稿。

不建议前端手写正式解析逻辑。第一版前端最多做输入提示或轻量格式高亮，不能作为最终解析依据。

### 5.1 百分比范围

示例：`10~20%`

解析结果：

```json
{
  "lower": 0.10,
  "upper": 0.20,
  "unit": "%",
  "display_lower": "10%",
  "display_upper": "20%"
}
```

如果目标变量单位或配置字段使用百分数数值，也可以按业务配置保存为 `10` 和 `20`。必须在解析结果中保留原始文本和归一化策略，不能隐式混用 `0.10` 与 `10`。

### 5.2 中心值加偏差

示例：`10±5`

解析结果：

```json
{
  "target": 10,
  "tolerance_minus": 5,
  "tolerance_plus": 5,
  "lower": 5,
  "upper": 15
}
```

示例：`10±5%`

需要先确认业务语义：

- 若表示绝对百分点：`lower=5%`、`upper=15%`。
- 若表示相对误差 5%：`lower=9.5`、`upper=10.5`。

默认不自动猜测相对误差。无法确定时进入导入草稿冲突项，由用户确认。

### 5.3 其它建议支持格式

- `10-20`
- `10 ~ 20`
- `>=10`
- `<=20`
- `10以上`
- `20以下`
- `目标10，上限20，下限5`
- `10 +5/-3`

每个解析结果必须保留：

- 原始文本；
- 解析类型；
- 上限；
- 下限；
- 设定值；
- 单位；
- 置信度；
- 是否需要人工确认。
