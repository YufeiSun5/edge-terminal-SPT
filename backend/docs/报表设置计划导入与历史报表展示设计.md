# 报表设置、计划导入与历史报表展示设计

最后更新：2026-06-17

维护责任：`review-ai` 负责设计边界；后续 API/生成实现由 `backend-ai`、`frontend-ai`、`test-ai` 分工落地。

## 1. 目标

报表能力拆成三个前端画面，并把“配置、查看、打包下载”分开：

1. `报表设置 / 模板管理`：维护客户 Excel 模板、模板原始副本、单元格映射、图片落点和模板版本。
2. `报表设置 / 导入计划`：从用户上传的计划或报表文件中解析检测任务、检测规则、上下限和设定值，创建检测配置和测试计划。
3. `历史 / Excel 报表`：查看某一次检测实际生成的报表。左侧仅按检测报告名称切换，右侧用只读 Luckysheet 加载后端生成的实际 Excel 报表。

下载不放在 `历史 / Excel 报表` 中。下载统一由 `历史 / 数据下载` 负责，按用户选择打包生成 zip。

## 2. 非目标

- 不在前端拼最终 Excel。
- 不在前端计算正式平均值、极值、上下限判定或曲线图片。
- 不把 Luckysheet JSON 作为交付文件或模板真源。
- 不做缺模板、缺映射、缺文件的静默兜底策略。
- 不继续用 `ext_1/ext_2/ext_3` 承载新报表参数。

## 3. 页面职责

### 3.1 报表设置 / 模板管理

模板管理面向“生成前配置”。

职责：

- 上传客户 `.xlsx` 模板。
- 保存一份不可变或可版本化的原始模板副本。
- 维护模板元数据：`template_code`、模板名称、版本、启用状态、适用项目或检测类型。
- 用 Luckysheet 预览模板，但预览不是文件真源。
- 配置单元格映射：
  - 任务字段：`task.test_no`、`task.project_code`、`task.started_at`、`task.ended_at` 等。
  - 报表请求字段：`request.report_name`、`request.template_code` 等。
  - 变量字段：变量名、显示名、单位。
  - 指标字段：平均值、最小值、最大值、样本数、连续合格窗口结果。
  - 上下限字段：上限、下限、报警上下限、回差、保持时间。
  - 参数字段：设定值、面积、备注等 `param.*`。
- 配置曲线图片落点：
  - sheet；
  - 起始单元格或像素锚点；
  - 宽高；
  - 曲线使用变量集合；
  - 是否显示上下限线、极值点、报警标记。
- 校验模板保存条件：
  - 必填映射必须能解析；
  - 图片落点合法；
  - 模板副本存在；
  - 版本号和 hash 可追溯。

第一版已经把模板级 mapping 和本次报表参数分开存储：模板管理保存 `sys_report_templates.params_schema_json.cell_mapping` 作为默认映射；检测报表请求冻结本次 `params_json` 参数，若本次请求携带 `params_json.cell_mapping`，则覆盖模板默认映射。

### 3.2 报表设置 / 导入计划

导入计划面向“从客户计划文件生成系统配置”。

职责：

- 上传 Excel 或 CSV 计划文件。
- 解析检测任务信息：
  - 测试编号或计划编号；
  - 项目/设备；
  - 测试类型；
  - 客户、机型、出厂编号；
  - 计划开始时间或备注。
- 解析检测规则：
  - 变量名称或测点名称；
  - 上下限；
  - 设定值；
  - 保持时间、检测周期、报警启用、存储启用等。
- 解析报表请求：
  - 检测报告名称；
  - 使用的报表模板名或模板编码；
  - 报表变量；
  - 报表参数。
- 匹配系统变量和检测配置：
  - 按变量显示名、内部名、别名、单位匹配；
  - 给出未匹配项；
  - 给出多候选冲突；
  - 不直接用模糊结果写正式配置。
- 创建两个结果：
  - `检测配置`：创建后立即可被检测启动使用。
  - `测试计划`：创建后进入 `待测试` 阶段，等待用户选择或到时执行。

导入计划必须先生成草稿和校验结果，用户确认后才写正式配置和测试计划。

当前实现状态：

- `parse` 草稿接口已能解析 `.xlsx`、保存源文件 artifact、匹配项目/变量/模板并解析上下限。
- `confirm` 确认接口已能把确认后的导入行创建为 `sys_detection_standards/sys_detection_standard_items` 检测配置。
- `confirm` 复用主服务器公共 `CreateDetectionStandard` 写入路径，不单独手写检测配置落库；公共路径已按规范校验项目、变量和边缘归属，并使用边缘端同算法计算 `config_hash`。
- `confirm` 现在同时创建 `sys_detection_plans(status=pending)` 作为待检测计划，不再另建 `test_plans`。计划写入 `standard_code`，并把导入文件里的模板、报表名、变量和参数整理到 `report_request_json`。
- 边缘从计划开工时会先解析本地 `standard_code` 对应检测配置，创建真实 `sys_detection_tasks`，再把 `report_request_json` 传入现有启动链路并冻结为 `detection_run_report_requests`。

### 3.3 历史 / Excel 报表

历史报表面向“某次检测的报表查看”。

职责：

- 读取当前检测任务的报表请求和报表 job。
- 左侧只显示检测报告名称列表，用于切换报表。
- 根据选中的检测报告名称，加载对应的报表 job 和实际生成的 Excel artifact。
- 一条 `detection_run_report_requests` 对应一份 Excel 文件。同一次检测可以生成多份报表，例如综合报表、温度报表、湿度报表三份文件；左侧列表切换的是这些文件，不是同一个文件里的多个业务报表。
- 右侧使用只读 Luckysheet 加载实际 Excel 文件。
- 右侧预览必须解析 `.xlsx` 内嵌图片并转换为 Luckysheet 图片对象；后端 Excel 已包含曲线 PNG 时，前端预览不能只显示单元格而丢图。
- Luckysheet 预览必须保持 Excel 文件可见 sheet 的原始顺序和首个可见 sheet 激活状态，隐藏/veryHidden 的内部追溯 sheet 不展示；不能为了显示图片强行切到后置 `Report_Charts` 页，避免预览与正式 Excel 打开效果不一致。
- Luckysheet 图片定位必须按 Excel 实际列宽、行高换算 anchor，不能用固定像素估算，否则会出现图片不在单元格或第二张图漂移。
- 显示必要状态：
  - 等待生成；
  - 生成中；
  - 生成失败；
  - 预览失败；
  - 已生成但文件不可用。
- 不放单报表下载按钮。
- 不在前端根据数据重新拼报表。

如果 Luckysheet 预览失败，只提示预览失败和原因；不能构造假预览。真实下载仍由 `数据下载` 页面统一打包。

### 3.4 历史 / 数据下载

数据下载面向“打包导出”。

职责：

- 展示可打包项树：
  - 原始采样数据；
  - 过滤后数据；
  - 曲线图片；
  - 详细数据表；
  - Excel 报表；
  - 报警与事件；
  - 检测配置、上下限、报表请求快照、存储路由快照。
- 支持下载所选和下载全部。
- 第一版由主服务器后端同步生成 zip 下载流；后续如包体过大再升级为异步 package job。
- zip 中的 Excel 报表必须来自报表 job 生成的正式 `.xlsx` artifact，不从 Luckysheet 当前预览导出。
- 单独曲线 PNG 尚未作为独立 artifact 落盘时，不生成伪图片；下载包在 `download-manifest.json.skipped` 中记录原因，曲线仍以正式 Excel 内嵌图片为准。

## 4. 后端生成链路

推荐链路：

```text
导入计划
-> 用户确认
-> 创建检测配置
-> 创建测试计划(待测试)
-> 启动检测时冻结 report_request
-> 检测结束后报表 job 入队
-> 等待主服务器侧可见的历史数据、规则快照、上下限、特征值齐全
-> 后端生成指标、曲线图片、Excel
-> 历史 / Excel 报表只读预览
-> 历史 / 数据下载统一打包
```

生成时机：

- 检测停止接口不应同步生成 Excel。
- 检测结束后可以自动入队报表 job；当前主服务器 report worker 的 `RunDueOnce` 会先扫描已停止且有报表请求但尚无 job 的任务并入队。
- 历史页打开时只读 job 状态；允许后续提供“补生成/重试”入口，但不放在下载职责里。
- 数据暂未可见时 job 保持 `waiting_for_sync`；确定无法满足时 `failed`。
- 生产环境主/边数据库最终内容一致但允许短时时差，报表 job 必须按关键数据完整性判断是否可生成，不能因为历史页打开时查不到数据就生成空报表。

生成物：

- `.xlsx`：正式客户报表。
- `manifest.json`：完整追溯包，记录模板版本、映射、变量、上下限、计算结果、曲线图片引用。
- `chart/*.png`：曲线图片，供 Excel 插图和历史预览复用。
- job events：生成过程、失败原因、等待原因。
- report notification：报表 job 开始、成功、失败事件写入 `main_report_notifications`，payload 必须包含 `task_id/request_id/test_no/project_id/project_code/report_name/template_code`，供现有通知中心合并展示和跳转历史报表页。

可见性等待判断至少包含：

- 检测任务记录在主服务器侧可见；
- `detection_run_report_requests` 在主服务器侧可见；
- 检测规则快照、上下限快照、存储路由快照在主服务器侧可见；
- 该次检测的历史采样行达到任务结束时间或达到报表所需的完整窗口；
- 需要的变量、项目、边缘实例元数据可解析；
- 当前模板副本、mapping 和后端业务公式在主服务器本地可用。

如果短时时差导致上述条件暂时不满足，job event 记录缺失项和下一次检查时间；如果超过配置的最大等待时间，job 失败并给出明确 `visibility_timeout` 或 `missing_required_data` 原因。历史页只展示该状态，不在前端构造临时报表。兼容旧状态码时可以继续保留 `sync_timeout` 字符串，但产品语义是“主服务器侧数据暂不可见”。

## 4.1 生成与文件存储技术选型

第一版采用“主服务器硬盘文件存储”，不引入对象存储。

### 4.1.1 Excel 生成

后端生成正式 `.xlsx` 使用 `github.com/xuri/excelize/v2`。

理由：

- 主服务器后端已经在 `main-server/backend/internal/reports` 使用 `excelize` 生成报表、打开模板、写单元格和保存 `.xlsx`，继续沿用成本最低。
- `excelize` 是 Go 生态里成熟的 Office Open XML 处理库，适合读取客户模板、写入单元格、保留 workbook 结构、插入图片和输出 `.xlsx`。
- 报表交付物必须是后端生成的真实 Excel 文件，不能依赖 Luckysheet 导出。

实现边界：

- 模板真源是上传的 `source.xlsx`。
- 后端用 `excelize.OpenFile()` 打开模板副本，写入映射单元格、公式输入区和图片；内部追溯 sheet 可以写入 workbook，但必须隐藏，历史页只展示客户可见业务 sheet。通常只写前两个业务 sheet，超过部分不主动加工，除非 mapping 明确指定。
- Excel 原生公式仅作为模板兼容内容尽量保留；正式结果由后端业务公式写入明确值。
- 后端业务指标包括平均值、极值、样本数、连续合格窗口、上下限判定等，不把这些正式计算交给前端。
- 当前代码里的默认模板兜底需要收敛：客户报表缺模板、缺文件、缺 required mapping 时应让 job 失败并记录原因，不能静默生成空白默认报表。

### 4.1.2 曲线图片生成

曲线图片应由后端生成为 PNG，再由 `excelize` 插入 Excel，并作为独立 artifact 供历史预览和打包下载复用。

第一版建议选一个服务端静态图片方案：

- 优先：Go 侧静态绘图库，例如 `gonum.org/v1/plot`，直接输出 PNG，部署简单。
- 备选：使用前端图表配置加 headless browser 截图，视觉一致性更强，但运行依赖和失败面更大。

不建议第一版把曲线图片交给 Luckysheet 或浏览器临时截图生成，因为历史报表和下载包必须可由后台队列稳定复现。

最小验证已经覆盖“历史采样行 -> 曲线 PNG -> chart artifact -> 插入 Excel -> 再读回图片元数据”：

- 测试中用 history-like rows 模拟历史采样数据；
- 后端计算平均值并写入 Excel 指标单元格；
- 后端按采样值和上下限生成 PNG 曲线；
- PNG 先保存为 `charts/*.png` artifact；
- 再由 `excelize.AddPictureFromBytes()` 插入模板指定位置；
- 生成后的 `.xlsx` 读回后可校验单元格、公式计算值和图片存在。

未验证范围：

- 尚未直接连接真实历史数据库查询；
- 尚未选定生产级曲线图库；
- 尚未做中文标题、坐标轴、图例、极值点、报警标记、长时间序列抽稀和多变量曲线的视觉验收。

### 4.1.3 文件管理

文件管理不要继续在业务代码里手写 `os.MkdirAll`、`filepath.Join`、绝对路径拼接和下载路径判断。既然文件只存储在主服务器硬盘上，建议引入轻量文件系统抽象 `github.com/spf13/afero` 作为本地 `ArtifactStore` 的底层实现。

推荐形态：

```text
ReportService
-> ArtifactStore interface
-> LocalArtifactStore
-> afero.Fs
-> data/report-assets
```

第一版只实现本地硬盘 driver，根目录为主服务器配置项 `artifact_store.root_dir`，默认 `data/report-assets`。报表业务代码只使用 `artifact_key`，不直接接触本机绝对路径。

实现要求：

- 代码层定义 `ArtifactStore` 抽象，内部基于 `afero.Fs`，使用 `artifact_key` 访问文件，不让业务代码依赖本机绝对路径。
- `artifact_key` 使用 `/` 分区，保存到本地时集中映射为 Windows/Linux 安全路径。
- `LocalArtifactStore` 必须校验 key：禁止绝对路径、`..`、空 key、非法分隔符和越过根目录。
- 业务表只保存 `artifact_key`、`content_type`、`size`、`sha256`、`generation_id`、`created_by` 等元数据，不保存本机绝对路径。
- zip 打包可继续使用 Go 标准库 `archive/zip`，但 zip 内容的读取和最终包写入都走 `ArtifactStore`。

选择理由：

- 报表生成发生在主服务器，模板副本、生成 Excel、曲线图片、下载包都由主服务器读写，第一版不需要把文件同步到边缘端。
- 当前项目历史数据同步依赖外部数据库同步软件，该同步不保证文件同步；因此模板文件和生成报表统一放在主服务器硬盘。
- 本地文件系统部署简单，适合现场服务器和客户内网部署；Afero 能把文件操作集中到一个本地 driver 中，避免业务代码散落路径处理。

禁止项：

- 禁止把本机绝对路径作为跨端合同。
- 禁止把 Luckysheet JSON 当作模板或报表交付真源。
- 禁止把大二进制文件直接塞进现有业务同步表。
- 禁止第一版引入对象存储、S3、MinIO 或云 OSS 作为必要运行依赖。

### 4.1.4 最小技术验证

2026-06-16 已在主服务器后端增加最小 spike 测试 `TestReportArtifactStoreExcelizeSpike`。该测试最初验证过 Go CDK `fileblob`，随后按用户确认的“只存主服务器硬盘”收敛为 Afero 本地硬盘方案。

验证范围：

- 使用 Afero 本地文件系统按 `artifact_key` 写入模板 `.xlsx`；
- 从 `artifact_key` 读回模板；
- 使用 `excelize.OpenReader()` 打开模板；
- 写入任务字段、指标字段和上下限字段；
- 兼容保留模板里已有的 Excel 原生公式，但不把它作为正式计算来源；
- 插入后端生成的 PNG 曲线图片；
- 使用 `excelize.WriteToBuffer()` 生成正式 `.xlsx`；
- 将生成报表写回 `reports/.../report.xlsx`；
- 再次读回并校验单元格、模板公式兼容保留状态和图片元数据。

验证命令：

```powershell
cd main-server/backend
go test ./internal/reports -run TestReportArtifactStoreExcelizeSpike -count=1 -v
go test ./internal/reports -count=1
```

结果：两项均通过。

结论：

- 功能上，`excelize + Afero` 可以满足第一版模板副本、本地 artifact key 存储、Excel 生成、模板公式兼容保留、历史采样曲线 PNG 插入和生成物读回校验需求。
- 依赖上，Afero 明显轻于 Go CDK，`go mod tidy -go=1.24.0` 能直接通过，不会把模块抬到 Go 1.25。
- 由于用户已确认只存主服务器硬盘，Go CDK、S3、MinIO、OSS 暂不进入第一版设计。

## 4.2 Luckysheet 样式同步到 Excel 的策略

第一版不建议把 Luckysheet 编辑后的完整 JSON 反向转换成 `.xlsx` 作为交付真源。Luckysheet 是预览和配置工具，最终 `.xlsx` 仍由后端基于模板副本和结构化 mapping 生成。

原因：

- Luckysheet 已是 legacy 组件，官方文档已提示不再维护，完整 Excel 兼容性风险高。
- LuckyExcel 更适合把 `.xlsx` 转成 Luckysheet JSON 做预览；从 Luckysheet JSON 完整导回 Excel 时，行高、列宽、合并单元格、图片、边框、条件格式、公式、打印设置、像素锚点等很难保证 1:1。
- 客户交付物要求稳定可追溯，不能依赖浏览器当前状态导出。

推荐同步方式是“结构化样式补丁”，而不是“Luckysheet JSON 全量反写”。

### 4.2.1 模板样式的权威来源

客户上传的 `source.xlsx` 是样式真源：

- 表头；
- 字体；
- 边框；
- 合并单元格；
- 列宽；
- 行高；
- 打印设置；
- Excel 原生公式兼容内容；
- 固定静态文本。

后端生成报表时先 `excelize.OpenReader(source.xlsx)`，然后只填数据、图片和必要的样式补丁。

注意：这里的 Excel 原生公式只表示客户模板已有内容可尽量保留，不表示系统认可它作为正式计算来源。正式报表值必须由后端业务公式、冻结参数、检测规则快照、上下限快照和历史数据计算后写入。

### 4.2.2 前端可修改的样式范围

如果前端在 Luckysheet 里允许改样式，第一版只支持一组可控白名单，并保存为模板 mapping 的一部分：

```json
{
  "style_patches": [
    {
      "sheet": "Report",
      "range": "B3:D3",
      "font": {"bold": true, "color": "#1f2937"},
      "fill": {"color": "#f3f4f6"},
      "border": "thin",
      "number_format": "0.00"
    }
  ]
}
```

建议第一版白名单：

- 字体加粗；
- 字体颜色；
- 背景色；
- 水平/垂直对齐；
- 数字格式；
- 单元格边框；
- 行高；
- 列宽；
- 合并单元格；
- 图片落点和大小。

暂不建议支持：

- 条件格式；
- 复杂图表对象；
- 透视表；
- 任意公式编辑；
- 打印区域复杂调整；
- 浏览器像素级拖拽布局反写。

### 4.2.3 同步流程

```text
模板管理上传 source.xlsx
-> LuckyExcel 转 Luckysheet 预览
-> 用户点击单元格配置数据 mapping、图片落点、有限样式补丁
-> 保存 mapping.json
-> 后端生成时打开 source.xlsx
-> 写入数据和业务指标
-> 应用 style_patches
-> 插入 charts/*.png
-> 保存 report.xlsx
```

也就是说，前端不是导出 Excel；前端只提交结构化配置。后端把这些结构化配置翻译成 Excelize 样式操作。

### 4.2.4 对用户可见的产品边界

模板管理里需要明确区分两类操作：

1. `上传/替换 Excel 模板`
   - 修改大范围排版、复杂样式、打印设置、复杂公式时，用户应在 Excel/WPS 中改好模板后重新上传。

2. `配置映射和轻量样式`
   - 在系统里配置单元格填什么数据、图片放哪里、少量字体/边框/数字格式。

这个边界能避免承诺“网页里怎么改，导出的 Excel 就 1:1 一样”。第一版的目标是交付稳定，不是做一个完整在线 Excel 编辑器。

## 4.3 文件分区和 artifact_key

文件按“模板资产、导入计划、检测快照、报表生成、下载包”分区。

### 模板资产

模板是可版本化资产，原始 `.xlsx` 是生成真源。

```text
templates/{template_code}/v{template_version}/{template_hash}/source.xlsx
templates/{template_code}/v{template_version}/{template_hash}/mapping.json
templates/{template_code}/v{template_version}/{template_hash}/preview.json
```

说明：

- `source.xlsx` 是用户上传的原始模板副本。
- `mapping.json` 保存模板级默认 cell mapping 和 chart mapping。
- `preview.json` 可选，用于缓存 LuckyExcel 转换结果，不作为交付真源。
- `template_hash` 使用模板文件内容 hash，避免同版本文件被静默覆盖。

### 导入计划资产

导入计划保存原始上传文件、解析结果和用户确认后的创建结果。

```text
plan-imports/{yyyy}/{import_id}/source.xlsx
plan-imports/{yyyy}/{import_id}/parse-result.json
plan-imports/{yyyy}/{import_id}/confirmed-config.json
```

说明：

- `source.xlsx` 是用户上传的计划文件原件。
- `parse-result.json` 保存检测任务、检测规则、上下限、设定值、变量匹配、冲突和人工确认标记。
- `confirmed-config.json` 保存最终创建检测配置和测试计划时使用的结构化输入。

### 检测快照资产

检测快照是某次检测的生成依据，不是模板文件。

```text
run-snapshots/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/report-requests.json
run-snapshots/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/standard-snapshot.json
run-snapshots/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/limits-snapshot.json
run-snapshots/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/storage-routes.json
```

说明：

- 快照可由数据库同步数据重新构建，但保存成文件能让打包下载和排查更直接。
- `factory_no` 可作为 manifest 字段和查询条件，但不单独作为唯一分区，因为同一出厂编号可能有多次检测、多张报表。

### 报表生成资产

一个出厂编号的设备可能有多次检测；一次检测可能有多张报表；同一张报表可能因为模板文件、mapping 或后端业务公式变化被重新生成多次。因此必须有 `task_id/test_no`、`request_id` 和 `generation_id`。

```text
reports/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/requests/{request_id}/generations/{generation_id}/report.xlsx
reports/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/requests/{request_id}/generations/{generation_id}/manifest.json
reports/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/requests/{request_id}/generations/{generation_id}/charts/{chart_id}.png
reports/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/requests/{request_id}/generations/{generation_id}/luckysheet-preview.json
```

说明：

- `request_id` 对应 `detection_run_report_requests.id`，也就是一份检测报告。
- `generation_id` 表示重新生成版本，首次生成可为 `1` 或 UUID。
- `report.xlsx` 是历史 Excel 报表右侧 Luckysheet 预览和数据下载打包的来源。
- `charts/*.png` 是后端生成曲线图片，插入 Excel，同时可供预览和打包。
- `luckysheet-preview.json` 可选缓存，不是权威。

### 下载包资产

```text
download-packages/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/{package_id}/package.zip
download-packages/{edge_instance_id}/{project_code}/{yyyy}/{task_id}_{test_no}/{package_id}/manifest.json
```

说明：

- 下载包由 `历史 / 数据下载` 创建。
- `manifest.json` 记录用户选择了哪些项和对应 artifact key。
- zip 中的 Excel 报表来自 `reports/.../report.xlsx`，不是前端导出。

## 4.4 重新生成策略

历史 `Excel 报表` 页面需要有重新生成入口，但重新生成仍由后端队列执行。

建议提供两个动作：

1. `按冻结快照重新生成`
   - 使用本次检测冻结时的模板版本、mapping、参数、变量和检测快照。
   - 用于修复生成失败、图片生成失败、artifact 丢失等情况。
   - 不受当前模板变更影响。

2. `按当前模板重新生成`
   - 使用当前启用模板版本和当前 mapping。
   - 仍使用该次检测的历史数据、检测规则快照、上下限快照、设定值快照。
   - 适用于用户修改模板文件、mapping 或后端业务公式后，希望用同一次检测数据生成新版报表。
   - 必须生成新的 `generation_id`，不能覆盖旧 artifact。

这里的“公式”只指系统受控的后端业务公式或表达式配置，不指 Excel/WPS/Luckysheet 原生公式。Excel 原生公式的变化可以作为模板文件变化被保存，但不能成为正式计算规则。

当前已实现一个最小的第三类动作：`修改参数后重新生成`。

- 入口在历史 `Excel 报表` 页，用户编辑该报表请求的参数 JSON 后提交。
- 后端接口为 `POST /api/v1/main-server/report-jobs/:id/regenerate`，请求体可传 `params` 对象或 `params_json` 字符串。
- 后端创建新的 `main_report_jobs` 行，记录 `parent_job_id`、`generation_type=params_override` 和 `params_override_json`。
- 生成时只对新 job 使用覆盖参数，不回写 `detection_run_report_requests.params_json`，也不修改检测开始时冻结的原始请求。
- 新 job 使用新的 artifact key，旧 Excel 和旧 manifest 继续可下载和追溯。
- job event 会记录 `reason/operator/params_override`，用于审计本次参数变更。

每次重新生成都必须记录：

- `generation_id`；
- 生成类型：`frozen_snapshot` 或 `current_template`；
- 使用的 `template_code/version/hash`；
- 使用的 mapping hash；
- 操作人；
- 操作时间；
- 失败原因；
- 旧 generation 是否仍可查看。

历史页左侧仍只显示检测报告名称；右侧默认展示最新成功 generation，并可在报告详情处切换 generation 或查看重新生成记录。

## 4.5 报表公式与参数取值

报表正式计算不认可 Excel 原生公式。Excel 模板里如果已经存在公式，可以作为客户模板内容被保留，但系统不把它作为正式结果来源，也不承诺解析、迁移、校验或执行任意 Excel 公式。

第一版公式模型以“后端业务公式 + 冻结参数”为准：

- 后端计算正式报表值；
- 前端只配置单元格映射、参数、受控表达式和图片落点；
- Luckysheet 不参与正式计算；
- Excel 原生公式只做模板兼容保留。

### 4.5.1 Excel 原生公式的边界

Excel 原生公式的处理规则：

- 客户上传模板中已有的公式可以保留；
- 后端不新增 Excel 原生公式作为正式计算逻辑；
- 后端不解析任意 Excel 原生公式的业务含义；
- 后端不依赖 Excel 打开后的自动重算结果作为任务判定或报表正式指标；
- 如果某个交付单元格需要正式值，应由后端业务公式计算后写入明确结果值。

原因：

- Excel 公式执行环境不可控，不同 Excel/WPS/在线预览引擎可能存在差异；
- 公式依赖区域和外部引用难以审计；
- Luckysheet 与 Excel 的公式兼容不能作为正式质量依据；
- 报表需要可追溯和可重放，正式计算必须由后端用冻结快照完成。

### 4.5.2 后端业务指标公式

平均值、极值、样本数、连续合格窗口、上下限判定、报警统计等正式业务结果应由后端计算，再写入 Excel。前端 Luckysheet 不参与正式计算。

业务指标引用建议使用结构化 source，而不是让用户直接写 SQL 或随意访问数据库：

```json
{
  "source": "metric",
  "metric": "avg",
  "variable": "supply_air_temperature",
  "window": "full_detection"
}
```

可支持的指标：

- `avg`；
- `min`；
- `max`；
- `count`；
- `first`；
- `last`；
- `qualified_hold_duration`；
- `alarm_count`；
- `ng_reason`；
- `custom_expression`。

`custom_expression` 可以支持受控表达式，例如：

```text
(metric.avg("supply_air_temperature") - param.target_temperature) / param.area
```

但表达式引擎必须白名单化，只能访问本次报表冻结快照中的变量、指标、规则和参数，不能访问任意文件、网络、数据库或系统函数。

### 4.5.3 启动参数、计划导入参数和设定值

公式可能引用前端任务开始时传递的参数，也可能引用计划导入解析出来的参数和设定值。

这些参数必须在检测启动或计划确认时冻结，进入本次检测的 report request snapshot，例如：

```json
{
  "params": {
    "target_temperature": 12.0,
    "area": 35.5,
    "customer": "ACME",
    "report_level": "factory"
  },
  "limits": {
    "supply_air_temperature": {
      "lower": 10,
      "upper": 20
    }
  }
}
```

模板 mapping 可以引用：

```text
param.target_temperature
param.area
limit.supply_air_temperature.lower
limit.supply_air_temperature.upper
task.factory_no
task.test_no
request.report_name
metric.supply_air_temperature.avg
```

生成原则：

- 后端只使用本次检测冻结的 `params_json`、检测规则快照、上下限快照和历史采样数据。
- 如果参数缺失，报表 job 应失败并记录明确原因，不能用默认值静默兜底。
- 参数类型要在模板管理或计划导入确认时校验，例如 number、string、percent、date、enum。
- `10~20%`、`10±5` 等文本解析结果要同时保留原始文本、归一化值和单位。

### 4.5.4 公式保存位置

模板管理中保存公式配置时，建议把“写到哪个单元格”和“值怎么来”分开：

```json
{
  "cell_mapping": [
    {
      "sheet": "Report",
      "cell": "B3",
      "source": "metric",
      "variable": "supply_air_temperature",
      "metric": "avg",
      "window": "full_detection",
      "required": true
    },
    {
      "sheet": "Report",
      "cell": "B4",
      "source": "param",
      "path": "target_temperature",
      "required": true
    },
    {
      "sheet": "Report",
      "cell": "B5",
      "source": "expression",
      "expression": "metric.avg(\"supply_air_temperature\") - param.target_temperature",
      "required": true
    }
  ]
}
```

这样模板可以同时支持：

- 一个变量出现在多张报表；
- 一张报表包含多个变量；
- 公式引用变量指标；
- 公式引用任务开始参数；
- 公式引用计划导入解析出的设定值和上下限；
- Excel 模板中已有公式可被保留，但不作为正式计算来源。

## 4.6 模板变更和公式变更

Excel 原生公式只属于模板兼容内容，不属于系统正式公式模型。

- 模板管理上传新模板或修改公式后，必须生成新模板版本或新 `template_hash`。
- 旧检测已经生成的报表不自动改变。
- 需要变化时，由历史页触发“按当前模板重新生成”。
- 如果只改 mapping，不改 Excel 文件，也必须生成 mapping hash，并写入 generation manifest。

后端不应尝试解释任意 Excel 原生公式作为业务规则；后端只负责写入映射单元格、插入图片并尽量保留模板原有结构。需要后端计算的平均值、极值、上下限判定、曲线数据和参数表达式，必须由报表 job 使用同步历史、任务开始参数和检测快照计算。

## 5. 上下限与设定值解析

导入计划需要能从 Excel 文本中解析常见上下限写法。

解析职责放在后端。前端只提供预览、人工修正和确认。

原因：

- 解析结果会创建检测配置和测试计划，属于业务写入依据，必须由后端统一校验。
- 同一份计划导入应能被测试复现，不能依赖浏览器临时代码。
- 后端解析器可以做单元测试，覆盖 `10~20%`、`10±5`、`10±5%`、`>=10` 等格式。

前端职责：

- 上传文件。
- 展示后端解析结果。
- 对低置信度或歧义项让用户选择。
- 用户确认后提交结构化草稿。

不建议前端手写正式解析逻辑。第一版前端最多做输入提示或轻量格式高亮，不能作为最终解析依据。

### 5.1 百分比范围

示例：`10~20%`

解析结果：

```json
{
  "lower": 0.10,
  "upper": 0.20,
  "unit": "%",
  "display_lower": "10%",
  "display_upper": "20%"
}
```

如果目标变量单位或配置字段使用百分数数值，也可以按业务配置保存为 `10` 和 `20`。必须在解析结果中保留原始文本和归一化策略，不能隐式混用 `0.10` 与 `10`。

### 5.2 中心值加偏差

示例：`10±5`

解析结果：

```json
{
  "target": 10,
  "tolerance_minus": 5,
  "tolerance_plus": 5,
  "lower": 5,
  "upper": 15
}
```

示例：`10±5%`

需要先确认业务语义：

- 若表示绝对百分点：`lower=5%`、`upper=15%`。
- 若表示相对误差 5%：`lower=9.5`、`upper=10.5`。

默认不自动猜测相对误差。无法确定时进入导入草稿冲突项，由用户确认。

### 5.3 其它建议支持格式

- `10-20`
- `10 ~ 20`
- `>=10`
- `<=20`
- `10以上`
- `20以下`
- `目标10，上限20，下限5`
- `10 +5/-3`

每个解析结果必须保留：

- 原始文本；
- 解析类型；
- 上限；
- 下限；
- 设定值；
- 单位；
- 置信度；
- 是否需要人工确认。

- 下载包 `ReportPackage` 或等价模块，负责创建 zip、查询状态和提供下载流。

边缘端与同步库：

- 边缘端继续负责检测执行、历史采样入库、检测规则快照、上下限快照和 `detection_run_report_requests` 冻结。
- 主服务器只读取同步后的历史和快照数据生成报表，不通过应用代码实现历史数据库同步。
- 数据库同步软件必须把报表生成所需表同步到主服务器；同步延迟是正常状态，不能被当成业务失败。
- Excel 文件、曲线图片、下载包不通过数据库同步软件传输；它们只存在主服务器文件资产目录。

前端：

- 只有一套主线前端页面，优先在 `desktop/src` 的 `main_server` 模式实现；`main-server/desktop` 不能继续扩成第二套业务页面。
- Luckysheet 只能通过 `src/features/spreadsheet/luckysheetAdapter.ts` 使用。
- 页面不能直接拼后端请求，必须经 `src/shared/api` 或 feature API。
- 所有可见文案必须补中文、英文、日文 i18n key。

测试与样本：

- 至少准备一个真实或接近真实的客户模板 `.xlsx` 样本，包含合并单元格、边框、列宽、行高、固定文本和图片落点。
- 至少准备一组历史采样数据，覆盖单变量、多变量、上下限、设定值、平均值、极值和曲线图片。
- 至少准备一份计划导入样本，覆盖 `10~20%`、`10±5`、`10±5%`、单边上下限和人工确认。

### 6.5 不符合时停止施工

出现以下情况时，应该停止继续开发对应功能，先回到设计或补基础能力：

- 找不到主服务器后端 `main-server/backend` 的报表 job、artifact 或 readiness 基础，不能先做前端假页面。
- 主服务器不能访问模板副本或 `ArtifactStore`，不能继续做报表生成。
- 主服务器查询视角暂时看不到检测任务、报表请求、历史采样、规则快照或上下限快照时，不能把空数据生成成正式报表。
- 短时可见性延迟没有等待状态和超时策略，不能把“查不到数据”直接当生成失败或成功空报表。
- 客户模板缺 required mapping，不能用默认模板、默认变量或空白单元格静默兜底。
- Luckysheet 只能导出 JSON 而不能加载真实 `.xlsx` 预览时，不能把 JSON 导出当正式 Excel。
- 前端仍在 `ExcelReportsTab` 提供单报表下载主入口时，不能宣布历史报表页完成。
- 新施工继续依赖 `ext_1/ext_2/ext_3` 或前端本地公式计算作为正式结果时，必须停止并改回 `report_request.reports[]`、结构化参数和后端业务公式。

## 7. 施工顺序

施工顺序以主服务器后端为第一优先级。原因是正式报表、曲线图片、下载包和历史页预览都依赖主服务器生成的 artifact；前端不应该先拼 Excel 或计算指标。

### 7.1 第 0 步：现状核对和停止条件检查

Owner：`review-ai` + `backend-ai`。

动作：

- 核对 `main-server/backend/internal/reports` 现有 job、readiness、artifact、package 代码。
- 核对主服务器是否已有同步库访问能力和目标表。
- 核对 `desktop/src` 与 `main-server/desktop` 是否仍分叉；若分叉，声明主线只在 `desktop/src` 施工。
- 核对客户模板样本、历史采样样本和计划导入样本是否可用。

通过条件：

- 缺失项列入 `AI_BOARD.md` 当前 handoff。
- 不满足 6.5 时停止产品施工，只允许补基础或改设计。

### 7.2 第 1 步：主服务器后端模板资产和 ArtifactStore

Owner：`backend-ai`。

动作：

- 实现或收敛 `ArtifactStore`，底层使用 Afero 本地硬盘 driver。
- 建立模板资产 API：上传、读取、版本化、hash、metadata、mapping 保存。
- 建立 artifact key 安全校验，禁止业务代码保存或暴露本机绝对路径。
- 明确默认模板 seed 只能作为显式系统模板，不能作为缺模板兜底。

通过条件：

- 可以上传 `source.xlsx`，保存 `mapping.json`，按 artifact key 读回。
- 缺模板、缺文件、hash 不匹配、缺 required mapping 都返回明确错误。

### 7.3 第 2 步：主服务器后端计划导入

Owner：`backend-ai`。

动作：

- 实现计划文件上传和草稿保存。
- 后端解析检测任务、检测规则、上下限、设定值和报表模板引用。
- 支持 `10~20%`、`10±5`、`10±5%`、`>=10`、`<=20`、`10 +5/-3` 等文本。
- 用户确认后创建检测配置，并创建状态为待测试的测试计划。

通过条件：

- 每个解析字段保留原文、单位、归一化策略、置信度和人工确认标记。
- 低置信度或冲突项必须要求人工确认，不能自动落库。

### 7.4 第 3 步：主服务器后端报表生成队列

Owner：`backend-ai`。

动作：

- 报表 job 在检测结束后自动入队，历史页只读状态并可触发补生成/重试。
- readiness 必须等待主服务器查询视角中的任务、报表请求、历史采样、规则快照、上下限快照齐全。
- 数据暂不可见时进入等待状态，记录缺失项、下一次检查时间和最大等待时间；当前代码可兼容旧 `waiting_for_sync` 状态名。
- 用后端业务公式计算平均值、极值、样本数、连续合格窗口、上下限判定、报警统计和受控表达式。
- 生成 PNG 曲线图片并插入 Excel。
- 生成 `report.xlsx`、`manifest.json`、`charts/*.png`，每次重新生成写新 `generation_id`。

通过条件：

- 数据暂不可见时不会生成空报表。
- 同步超时、缺历史数据、缺 mapping、公式参数缺失都有明确失败原因。
- 重新生成不会覆盖旧 generation。

### 7.5 第 4 步：主服务器后端下载包

Owner：`backend-ai`。

动作：

- 实现 `历史 / 数据下载` 所需的打包 API：第一版 `POST /api/v1/main-server/download-packages` 同步返回 zip。
- 下载包只从正式 artifact 和快照文件读取，不从 Luckysheet 当前页面导出。
- zip manifest 记录选择项、包含文件、跳过项、生成时间和操作人。

通过条件：

- 支持下载所选和下载全部。
- 缺 artifact 时打包失败并记录缺失项，不生成半真半假的 zip。

### 7.6 第 5 步：前端页面收敛

Owner：`frontend-ai`。

动作：

- 侧边栏 `报表` 改为 `报表设置`，下设 `模板管理` 和 `导入计划`。
- 模板管理接真实模板资产 API，Luckysheet 只做预览和 mapping 配置。
- 导入计划接真实草稿、解析、确认 API。
- 历史 `Excel 报表` 改成左侧报告名列表、右侧只读 Luckysheet 加载后端生成的实际 Excel。
- 移除历史 Excel 报表页单报表下载主入口。
- `历史 / 数据下载` 接真实打包 API。

通过条件：

- 没有前端本地计算正式指标。
- 没有 Luckysheet JSON 作为正式导出。
- i18n 中文、英文、日文齐全。

### 7.7 第 6 步：测试和验收

Owner：`test-ai`。

动作：

- 后端单元测试覆盖 artifact key、模板 hash、上下限解析、公式参数缺失、同步等待和超时。
- 集成测试覆盖计划导入确认后创建检测配置；待测试计划需要先补独立计划模型后再验收。

- 前端 smoke 覆盖模板管理、导入计划、历史 Excel 报表预览、数据下载。
- 主服务器模式 smoke 必须使用 `desktop/src` 的 `main_server` 模式。

通过条件：

- 明确区分“真实同步链路已覆盖”和“仅用本地夹具覆盖”。
- 页面能打开、空态能显示、mock 数据通过，不能算报表能力通过。

通过证据：

- 历史详情报表切换截图或 Playwright JSON。
- Luckysheet 实际加载的 artifact key。
- 下载包 package ID 和 zip 下载结果。
- 无单报表下载入口的 DOM 或截图证据。

#### 节点 H：端到端验收

开发到哪里：

- 后端、前端、打包下载都已通过各自节点。
- 至少有一条从计划导入到历史报表展示的完整链路可跑通。

必须测试：

- 导入计划 -> 创建检测配置 -> 创建待测试计划。
- 启动检测并冻结 report request。
- 等待数据库同步软件把任务、请求、历史、快照同步到主服务器。
- 主服务器报表 job 从 `waiting_for_sync` 到 `succeeded`。
- 历史页展示实际 Excel。
- 数据下载页打包 zip。

通过证据：

- 完整链路的任务 ID、test_no、request_id、job_id、generation_id、package_id。
- 同步等待耗时和同步水位记录。
- 生成 Excel、图片、manifest、zip 的 artifact key。
- 失败重试或重新生成至少覆盖一次。

不得计为端到端通过：

- 只用前端 mock 数据。
- 只打开页面空态。
- 只下载默认模板生成的样例 Excel。
- 只在边缘端本地库验证，未经过主服务器同步库。
- 未记录数据库同步软件延迟和等待状态。

## 9. 废弃和收敛项

- 废弃顶级“报表”作为 job 控制台的产品定位，改为“报表设置”。

## 10. 待确认问题

1. 计划导入支持的文件格式第一版范围：`.xlsx` 是否足够，是否需要 CSV。
2. `10±5%` 的默认业务含义：绝对百分点还是相对误差。
3. 测试计划模型和状态枚举：当前没有独立计划表，建议新增计划模型后再定义 `pending_test` 或等价“待测试”状态；不得直接复用 `sys_detection_tasks.status` 伪造计划态。
4. 数据下载打包页的文件范围和权限边界：第一版应只打包已生成 Excel、曲线图片和必要 JSON 追溯文件，还是同时包含原始模板副本。

已确认收敛项：主服务器可以保留现有默认模板 seed，但只能作为用户显式选择的系统模板，不能在缺客户模板、缺映射或缺文件时静默兜底。报表 job 自动入队已采用主服务器 worker 轮询扫描“已停止、有报表请求、尚无 job”的任务；历史页仍保留补生成/重试入口。曲线图片第一版已采用 Go 静态 PNG 生成并插入 Excel；新模板优先通过 `cell_mapping.chart_sheet/chart_cell` 插到客户业务 sheet，`Report_Charts` 仅作为历史兼容页名。
