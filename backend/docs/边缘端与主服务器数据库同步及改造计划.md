# 边缘端与主服务器数据库同步及改造计划

最后更新：2026-06-02

维护责任：`backend-ai`

本文档固化边缘端和主服务器在数据库同步、控制命令、表所有权和分阶段改造上的当前计划。目标是复用外部数据库同步软件，不在本应用内重新实现数据库同步。

## 1. 当前结论

1. 边缘端仍是现场真实写入源，负责采集、运行态内存、检测执行、现场控制和本地历史入库。
2. 主服务器负责跨边缘查询、报表生成、文件归档、主服务器通知和控制命令编排。
3. 数据库同步软件只负责复制数据，不负责控制命令、权限校验、运行态刷新或冲突业务合并。
4. 检测任务列表可以在主服务器全局可见，但 `sys_detection_tasks` 的运行状态不能通过多主同步直接修改。
5. 配置模板可以规划多向同步；检测运行数据、历史、报警和快照必须保持边缘端单主写。
6. 主服务器对现场的写动作必须走受控 HTTP 命令通道，不能直接写同步库来改变现场。
7. 第一阶段不要求主服务器后端完整建成；边缘端可以先通过本地 smoke 工具模拟主服务器命令调用。

## 2. 表同步分类

### 2.1 边缘端单主镜像表

这些表由边缘端写，主服务器通过同步软件读取镜像。同步模式应选“边缘端 -> 主服务器”单向同步。

| 表 | 写入特点 | 主服务器用途 | 说明 |
| --- | --- | --- | --- |
| `rt_history_data` | 主要 insert | 历史曲线、报表数据源 | 高频采样兼容窄表。 |
| `rt_project_{project_id}_data` | insert/upsert | 历史曲线、报表数据源 | 项目宽表，仍由边缘存储 worker 写。 |
| `sys_detection_tasks` | insert/update | 任务列表、任务状态查询 | 运行状态只能由边缘端服务更新。 |
| `detection_run_standard_items` | insert | 检测标准运行快照 | 启动检测时冻结，运行后不可被模板同步覆盖。 |
| `detection_run_storage_routes` | insert | 本次检测存储快照查询 | 冻结后的运行存储路由。 |
| `detection_run_report_requests` | insert/update | 主服务器报表 worker 消费 | 边缘端登记报表请求，主服务器生成自己的报表任务。 |
| `detection_run_events` | insert | 生命周期时间线 | 任务开始、停止、异常停止等事件。 |
| `detection_run_summaries` | insert/update | 结果汇总、报表到位检查 | 停止或刷新时由边缘端计算。 |
| `detection_run_features` | insert/update | 报表特征值 | 平均值、最大值、最小值等。 |
| `detection_limit_alarms` | insert/update | 报警查询、报表到位检查 | 进入、等级变化、恢复由边缘报警 worker 写。 |
| `task_flow_runs` | insert/update | 任务执行追溯 | 边缘端任务系统执行记录。 |
| `task_flow_sql_logs` | insert | 脚本 SQL 追溯 | 只记录边缘任务脚本执行 SQL。 |
| `sys_audit_logs` | insert | 操作审计镜像 | 主服务器可查询边缘审计，但不作为主服务器审计表。 |
| `sys_notifications` | insert/update | 边缘通知镜像 | 只代表边缘本地通知，不替代主服务器通知中心。 |
| `sys_notification_recipients` | insert/update | 边缘通知读取状态镜像 | 主服务器可读，不应复用为主服务器未读中心。 |

边缘端单主镜像表可以被主服务器查询，但主服务器不得直接写同步库中的这些表。需要变更现场状态时，主服务器发命令给边缘端，边缘端执行后再由同步软件同步结果。

### 2.2 可规划多主的共享配置表

这些表是低频配置或模板，未来可以使用同步软件的多主同步模式，但必须补齐版本和冲突策略。第一阶段可以先不启用多主，等主服务器后端雏形稳定后再接入。

| 表 | 建议策略 | 前置约束 |
| --- | --- | --- |
| `sys_detection_standards` | 未来可多主 | 需要 `row_uid/version/updated_by_node/owner_scope` 或等价字段。 |
| `sys_detection_standard_items` | 未来可多主 | 模板项可同步，但 running 任务只读 `detection_run_standard_items` 快照。 |
| `sys_report_templates` | 未来可多主 | 模板元数据可多主；模板文件资产需另定文件同步或主服务器文件管理。 |
| `sys_station_view_templates` / `sys_station_view_regions` / `sys_station_view_items` / `sys_station_view_assignments` | 未来可多主或中心下发 | 工位画面显示模板属于低频 UI 配置；必须按 `edge_instance_id`、项目归属和业务点位名过滤，详见 `backend/docs/工位画面模板与边缘过滤计划.md`。 |
| `sys_task_flows` | 谨慎多主 | 建议先中心下发或边缘导入，后续再做多主冲突策略。 |
| `sys_task_flow_vars` | 谨慎多主 | 必须和 `sys_task_flows` 同版本同步。 |
| 用户、角色、字典类表 | 未来可多主或中心主导 | 需要统一用户 ID 或外部用户 ID 映射。 |

多主配置表必须遵守：

1. 只能影响未来配置，不得直接改变已运行任务的冻结快照。
2. 每次变更要能追踪来源节点、版本、操作者和更新时间。
3. 冲突不能静默覆盖；至少要有“中心优先、边缘优先、版本优先、人工处理”之一的明确规则。
4. 配置同步到边缘端后，仍需通过边缘端服务 reload 运行态索引或校验引用关系。

### 2.3 边缘端现场配置表

这些表可以被主服务器管理或发起修改，但不建议用多主同步直接改表。主服务器应通过边缘端 HTTP 控制通道提交配置命令，由边缘端校验、落库、刷新运行态，然后再同步回主服务器。

| 表 | 不建议多主的原因 | 推荐变更方式 |
| --- | --- | --- |
| `sys_tags` | 点位发现、写入约束、清洗参数和 `TagManager` 强相关 | 主服务器维护点位资产视图，变更通过边缘端变量配置接口执行。 |
| `sys_storage_routes` | 会影响存储 worker、宽表列和运行快照 | 主服务器发配置命令，边缘端校验表名/列名并 reload。 |
| `sys_gateways` / 网关配置 | 影响 MQTT/KIO 连接和现场采集 | 边缘端本地管理，主服务器命令需严格授权。 |
| `sys_project_members` | 当前用于边缘本地通知成员 | 后续若统一用户体系，再考虑中心主导。 |
| `sys_projects` | 业务分组和运行任务入口 | 可中心规划，但落地到边缘端需通过边缘服务确认；同步到边缘的项目应写入 `edge_instance_id`，用于工位 effective view 自动隐藏其他边缘项目。 |

`sys_tags` 的原则是：主服务器应该持有点位资产视图，不直接持有现场真实写入权。主服务器可建立自己的点位目录，使用 `edge_instance_id + var_id` 或 `edge_instance_id + gateway_id + source_path` 关联边缘点位。

### 2.4 主服务器独有表

这些表由主服务器拥有，不同步回边缘端。

| 类型 | 表方向 |
| --- | --- |
| 边缘节点注册 | `edge_nodes` |
| 主服务器命令记录 | `main_edge_commands` 或等价命令日志 |
| 主服务器报表任务 | `main_report_jobs` |
| 主服务器报表文件 | `main_report_files` |
| 主服务器通知中心 | `main_notifications`、`main_notification_recipients` |
| 跨边缘看板配置 | `main_dashboards`、`main_dashboard_widgets` |
| 主服务器点位目录 | `main_tag_catalog` 或等价资产视图 |

主服务器独有表不要求边缘端现在实现，只作为主服务器后端建设时的边界。

## 3. 检测任务和检测配置的边界

检测任务列表需要在主服务器可见，但可见不等于多主写。

```text
主服务器页面
  -> 主服务器后端
  -> 边缘端 HTTP 控制通道
  -> 边缘端 DetectionRunsService / 任务系统模块
  -> 边缘端写 sys_detection_tasks 和 detection_run_* 快照
  -> 数据库同步软件同步到主服务器镜像库
```

检测配置模板可以规划多向同步：

```text
sys_detection_standards
sys_detection_standard_items
sys_report_templates
```

但检测启动后必须冻结到：

```text
detection_run_standard_items
detection_run_storage_routes
detection_run_report_requests
```

running 任务判断只读冻结快照，不读最新模板。这能保证配置模板同步不会改变正在运行的检测任务。

## 4. 边缘端第一阶段改造

第一阶段只完善边缘端后端，不要求主服务器后端完整。

### 4.1 固定边缘端身份

先在配置层增加稳定身份，后续再决定是否落表或扩展到业务表。

```text
edge_instance_id
edge_code
edge_name
site_no
```

如果主服务器第一阶段按边缘端分库或分 schema，同步来源可以先由 schema 名区分；如果后续合库，再评估给关键表补 `edge_instance_id`。

### 4.2 实现 HTTP 控制通道

按 `backend/docs/边缘端HTTP主服务器控制通道设计.md` 落地 `/api/v1/edge-control/*`。

首批控制能力：

| 能力 | 路由方向 | 复用服务 |
| --- | --- | --- |
| 启动检测 | `/api/v1/edge-control/detection/start` | `DetectionRunsService` 或任务系统启动模块 |
| 停止检测 | `/api/v1/edge-control/detection/stop` | `DetectionRunsService` |
| 异常停止 | `/api/v1/edge-control/detection/abnormal-stop` | `DetectionRunsService` |
| 写变量 | `/api/v1/edge-control/variables/write` | `VariableWriteService` + `KIOWriteService` |
| 报警静音 | `/api/v1/edge-control/detection/mute-alarms` | `DetectionRunsService` + `TaskManager` 运行态静音 |
| 运行中限值调整 | `/api/v1/edge-control/detection/update-limits` | `DetectionRunsService` 更新运行快照 |
| 特征值刷新 | `/api/v1/edge-control/detection/refresh-features` | `DetectionRunsService` 刷新特征和事件 |
| 报表请求登记 | `/api/v1/edge-control/detection/report-requests` | `DetectionRunsService` + 报表请求快照解析 |

handler 只负责鉴权、幂等、参数校验、审计和错误映射；业务执行必须复用现有服务，不能复制一套主服务器专用检测逻辑。

### 4.3 新增命令生命周期表

边缘端新增：

```text
edge_control_commands
```

核心字段：

| 字段 | 说明 |
| --- | --- |
| `command_id` | 主服务器生成的命令 ID。 |
| `client_id` | service client 身份。 |
| `operator_id` / `operator_username` / `operator_name` | 主服务器操作者。 |
| `edge_user_id` | 映射成功后的边缘本地用户。 |
| `action` | `detection.start`、`variable.write` 等。 |
| `target_type` / `target_id` | 项目、任务、变量或报警目标。 |
| `request_json` | 脱敏后的请求。 |
| `status` | `received`、`running`、`success`、`failed`。 |
| `result_json` / `error_code` / `error_message` | 执行结果。 |
| `received_at` / `completed_at` | 生命周期时间。 |

边缘端按 `client_id + command_id` 做幂等，HTTP 重试不得造成重复启动检测、重复下设或重复静音。

### 4.4 增强 service token

复用现有 `sys_service_clients`，补齐或确认：

```text
scopes
allowed_cidrs
enabled
expires_at
last_used_at
token_hash
```

service token 只证明“这是主服务器后端”，不能替代用户 JWT 或 SSO ticket。控制命令仍必须携带实际操作者，并映射到边缘端本地用户后审计。

### 4.5 模拟主服务器的边缘端 smoke

在主服务器后端未完整前，边缘端测试工具可以直接模拟：

```text
service token + command_id + operator + payload
```

验证：

1. 无 token、缺 scope、来源不允许时拒绝。
2. 重复 `command_id` 返回原结果。
3. 启动检测会写 `sys_detection_tasks` 和运行快照。
4. 停止检测会写摘要、特征值、事件和报警恢复。
5. 写变量复用 `VariableWriteService`，物理变量仍受 KIO 写入约束。
6. 命令生命周期表和 `sys_audit_logs` 均可查到记录。
7. `smokehealth`、`smokebackend` 继续通过。

## 5. 主服务器后端第二阶段

主服务器后端最小雏形只需要做到：

1. 维护 `edge_nodes`，保存 `edge_instance_id`、显示名、同步库连接或 schema、HTTP 控制地址、service client 配置引用和启用状态。
2. GET 查询类接口优先读同步镜像库。
3. POST/PATCH/PUT/DELETE 控制类接口转发到边缘端 `/api/v1/edge-control/*`。
4. 记录主服务器自己的命令日志，和边缘端 `edge_control_commands.command_id` 对齐。
5. 报表 worker 消费 `detection_run_report_requests`，检查历史、摘要、特征值、报警是否同步到位，再创建主服务器自己的报表任务和文件记录。

第一版主服务器不需要处理所有多主配置。可以先把同步库当只读镜像，让控制链路跑通。

## 6. 最小测试计划

### 6.1 不依赖主服务器的边缘端测试

| 测试 | 目标 |
| --- | --- |
| service token 单元测试 | 验证 token、scope、CIDR、过期和禁用。 |
| edge-control handler 测试 | 验证 envelope、错误码、幂等和重复命令。 |
| detection start/stop 集成测试 | 验证复用现有检测服务和运行快照冻结。 |
| variable write 集成测试 | 验证虚拟变量、物理变量写入约束和审计。 |
| smokehealth/smokebackend | 保持现有核心后端门禁。 |

### 6.2 使用 MySQL schema 模拟同步

不需要完整主服务器后端，可以先用两个 schema 模拟：

```text
edge_db      边缘端真实库
mirror_db    主服务器镜像库
```

验证同步软件或手工导入后的查询条件、表结构兼容、任务列表可见、报表请求可被发现。

### 6.3 依赖主服务器后端雏形的端到端测试

等主服务器后端具备 `edge_nodes` 和 HTTP control client 后，再验证：

```text
主服务器 API
  -> edge_nodes 找目标边缘
  -> HTTP edge-control
  -> 边缘端执行
  -> 边缘库写入
  -> 同步到主服务器镜像库
  -> 主服务器查询到结果
```

## 7. 暂不实施项

第一阶段暂不做：

1. 不在应用内实现数据库同步。
2. 不整库改成多主。
3. 不给所有业务表立即添加 `edge_instance_id`。
4. 不让主服务器直接写同步库控制现场。
5. 不把 `sys_detection_tasks`、`sys_tags`、`sys_storage_routes` 做多主直接互改。
6. 不提前实现完整主服务器报表中心和通知中心。

## 8. 后续决策点

| 决策 | 推荐时间 |
| --- | --- |
| 主服务器镜像采用分库/分 schema 还是中心合库 | 主服务器查询路由落地前 |
| 哪些共享配置表第一批启用多主同步 | HTTP 控制通道和主服务器最小后端跑通后 |
| 是否给关键表补 `edge_instance_id` | 决定中心合库时 |
| 点位资产目录由主服务器单独建表还是复用镜像视图 | 主服务器点位管理页面建设前 |
| 报表模板文件如何同步或归档 | 主服务器报表 worker 建设前 |

当前默认路线是：先完善边缘端 HTTP 控制通道和边缘端 smoke，再建设主服务器最小后端，最后接最小端到端测试。
